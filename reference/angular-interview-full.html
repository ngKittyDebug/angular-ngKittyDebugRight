General

1. Что такое Angular и для чего он используется?

Angular — opinionated TypeScript-фреймворк от Google для построения клиентских приложений: SPA, PWA, SSR-приложений с гидратацией. В отличие от «тонких» UI-библиотек, Angular поставляет целостный стек: компонентная модель, DI-контейнер, маршрутизацию, формы, HTTP-клиент, i18n, тестовый раннер и CLI. Компилятор (Ivy/AOT) анализирует шаблоны на этапе сборки и генерирует эффективный JS; рантайм управляет жизненным циклом компонентов, графом change detection и инъекцией зависимостей.

Типичные сценарии: enterprise SPA, админки, дашборды, внутренние порталы — там, где важны единые паттерны команды, строгая типизация, предсказуемая архитектура и долгосрочная поддержка. Angular 16–22 сместил дефолт в сторону standalone components, signals и готовности к zoneless change detection — это не «legacy MVC», а современный reactive UI-стек.

Ключевые архитектурные идеи: декларативные шаблоны с data binding, иерархия injectors для scope сервисов, lazy loading на уровне маршрутов и шаблонов (@defer), RxJS для асинхронных потоков, NgRx Signals / signal stores для локального и глобального состояния. Angular не навязывает один способ state management — но DI + facades + signals дают чёткие границы между UI, orchestration и data layers.

Компромиссы:

  • vs React/Vue: больше «batteries included» и структуры из коробки, но выше порог входа и больше ceremony в boilerplate.
  • Выигрыш: единый toolchain (CLI, lint, test), AOT-проверка шаблонов, DI с tree-shaking через providedIn / functional providers.
  • Цена: крупнее initial bundle по сравнению с минималистичными альтернативами; миграции между major-версиями требуют планирования (хотя ng update и schematics сильно помогают).
  • Angular 22: OnPush по умолчанию, signal inputs, standalone-first — снижают «legacy tax» NgModules и Zone.js overhead.
Проект: ngKittyDebug («delulu-church») — Angular 22 SPA: standalone bootstrap через app.config.ts, Taiga UI, NgRx Signals (uiStateStore), Firebase Auth/Firestore, Vitest. Архитектура features/<name>/data + facades + ui с route-scoped providers в app.routes.ts.

2. Что такое Angular CLI и каковы его основные функции?

Angular CLI (ng) — официальный toolchain для создания, разработки, сборки, тестирования и миграции Angular-приложений. Он читает angular.json (workspace config), управляет builders (dev server, production build, test runner), path aliases и schematics — шаблонами генерации и автоматических миграций.

Основные команды: ng new / ng generate (scaffold компонентов, директив, pipes, services с правильными imports и префиксом селектора), ng serve (dev server с HMR/esbuild), ng build (production bundle с code splitting, budgets, source maps), ng test (unit tests — в ngKittyDebug через Vitest builder), ng lint, ng update (major migrations). С Angular 17+ application builder использует esbuild/Vite — быстрее, чем legacy webpack builder.

CLI также генерирует standalone components по умолчанию (Angular 19+), поддерживает SSR/hydration scaffolding (ng add @angular/ssr), schematics для перевода на standalone (ng generate @angular/core:standalone) и на signals. Конфигурация проекта централизована: prefix, style preprocessor options, budgets, fileReplacements для environment — всё в angular.json, не размазано по репозиторию.

# Типичный workflow ngKittyDebug
pnpm start    # ng serve -o, port 4200, proxy.conf.json → deploytarot.com
pnpm build    # production build, проверка budgets
pnpm test     # Vitest через Angular test builder
pnpm generate # ng generate component features/foo/ui/bar --standalone

Компромиссы:

  • CLI vs ручная настройка Vite/Webpack: CLI абстрагирует builder — меньше контроля, но стандартизированные миграции и совместимость с экосистемой Angular.
  • Schematics: быстро генерируют boilerplate с conventions, но «слепое» ng g c без понимания imports приводит к циклическим зависимостям.
  • Monorepo (Nx): для одного SPA CLI достаточен; Nx добавляет affected builds и module boundaries, но усложняет setup.
Проект: префикс селекторов ngKitty из angular.json; pnpm start → ng serve -o; pnpm test → Vitest (jsdom); SCSS includePaths: ["src", "src/styles"] для коротких @use-импортов; pnpm typecheck — отдельный tsc -b, не часть CLI hooks.

3. Что такое модуль в Angular, и какова его роль в приложении?

Исторически NgModule (@NgModule) был единицей компиляции и организации кода: декоратор группировал declarations (компоненты, директивы, pipes), imports (другие модули), exports (публичный API модуля) и providers (DI-токены scope модуля). Root AppModule вызывал bootstrapModule(AppComponent); feature modules (MainModule) lazy-load'ились через loadChildren: () => import(...).then(m => m.MainModule).

С Angular 15+ standalone components заменяют NgModule как primary unit. Компонент сам объявляет imports: [CommonModule, MyPipe, ChildComponent] — зависимости видны в одном файле, tree-shaking точнее (не тащим весь barrel export модуля). Bootstrap: bootstrapApplication(AppComponent, appConfig); providers — в ApplicationConfig.providers или route-level providers. Lazy loading: loadComponent: () => import(...).then(c => c.ProfileComponent) без wrapper-модуля.

На интервью 2026 «модуль» часто означает логический feature boundary, а не @NgModule: папка features/main/ с data/facades/ui — это модуль в архитектурном смысле. NgModules ещё встречаются в legacy-коде и некоторых библиотеках, но новый код — standalone-first. Route-scoped providers заменяют «feature module providers»: один экземпляр facade на маршрут, не singleton на всё приложение.

// Современный bootstrap — без AppModule
export const appConfig: ApplicationConfig = {
  providers: [
    provideRouter(routes, withComponentInputBinding()),
    provideHttpClient(withInterceptors([httpErrorInterceptor])),
  ],
};

// Route-scoped «модуль» через providers
{ path: '', component: MainComponent,
  providers: [MainPageFacade, TarotService] }

Компромиссы:

  • NgModule: удобен для barrel exports в больших legacy monoliths, но скрывает реальные зависимости и мешает tree-shaking.
  • Standalone: явные imports, проще mental model, лучше для новых проектов; миграция legacy требует schematics и временного coexistence.
  • Feature folders vs NgModule: граница фичи = папка + route providers, не декоратор — проще навигация и code review.
Проект: нет AppModule — только app.config.ts + app.routes.ts. Каждая фича (main, altar, sanctum) получает route-scoped providers: MainPageFacade, AltarPageFacade, SanctumRitualService и т.д. Shared domain (CandlesService, ConfessService) — в core/services/ с providedIn: 'root' или route scope по необходимости.

4. Что такое межкомпонентное взаимодействие в Angular? Опишите различные способы передачи данных между компонентами (например, @Input/@Output, сервисы с Observables и т. д.).

Parent → child: @Input() (или signal API input()) передаёт данные вниз по дереву компонентов. Контракт явный и типизированный: card = input.required<TarotCard>(). Child → parent: @Output() / output() эмитит события (drawCards = output<void>()). Односторонний поток данных вниз, события вверх — основа предсказуемого UI.

Между несвязанными компонентами: shared services с signals или Observables — AuthService, uiStateStore, CandlesService. Компоненты инжектируют сервис и читают user() / подписываются на langChanges$. Facades сужают API: UI не знает про HTTP/Firestore, только про MainPageFacade.result() и loadTarot().

Другие каналы: route params / queryParams — данные через URL; с withComponentInputBinding() param автоматически биндится в signal input routed-компонента. Content projection (ng-content) — parent передаёт шаблон в child slot. Template references (@ViewChild) — императивный доступ, escape hatch. Для глобальных событий — RxJS Subject в сервисе, но предпочтительнее signals store с явными методами мутации.

// Signal inputs/outputs (Angular 17.1+)
@Component({ selector: 'ngKitty-tarot-oracle', ... })
export class TarotOracleComponent {
  role = input<Role | null>(null);
  roleChange = output<Role>();
}

// Facade как единственный API для UI
export class MainComponent {
  private readonly facade = inject(MainPageFacade);
  protected readonly result = this.facade.result; // signal
  protected onDraw() { this.facade.loadTarot(); }
}

Компромиссы:

  • Input/Output: идеален для parent-child; не масштабируется на «соседей» без prop drilling через 5 уровней.
  • Shared service: решает cross-cutting state, но глобальный store для локальных данных усложняет тесты и traceability.
  • Facade vs прямой service call: facade добавляет слой, но изолирует UI от transport (HTTP/Firestore) и централизует loading/error.
  • Observable vs signal: Observable — для event streams и HTTP; signals — для синхронного UI state; bridge через toSignal() / toObservable().
Проект: MainComponent → MainPageFacade (не HTTP напрямую). LanguageSwitcherComponent читает/пишет uiStateStore.language. uiStateStore синхронизирует тему/язык с Firestore users/{uid}.uiState при auth. app.config.ts — withComponentInputBinding() для route params.

5. Что такое компоненты в Angular и как они являются основой структуры приложения?

Компонент — минимальная единица UI в Angular: TypeScript-класс с декоратором @Component, HTML-шаблон, стили и metadata (selector, imports, change detection strategy). Angular создаёт instance компонента, привязывает свойства класса к шаблону через bindings, запускает change detection при изменении state. Дерево компонентов = дерево приложения: root AppComponent → LayoutComponent → feature components → leaf UI widgets.

Компонент отличается от директивы наличием шаблона — собственного view. Директива меняет существующий element; компонент создаёт новый view host. Standalone components (дефолт в CLI) явно объявляют imports: [...] — все зависимости (pipes, directives, child components) видны в одном файле, без NgModule barrel.

Архитектурный паттерн в зрелых фичах: smart (container) vs dumb (presentational). Smart component инжектирует facade, держит минимум логики; dumb component получает данные через input() и эмитит события через output() — легко тестировать изолированно. В ngKittyDebug MainComponent — smart; TarotReadingComponent — closer to presentational.

@Component({
  selector: 'ngKitty-main',
  imports: [TarotOracleComponent, TarotReadingComponent, TranslocoPipe],
  templateUrl: './main.component.html',
  styleUrl: './main.component.scss',
})
export class MainComponent {
  private readonly facade = inject(MainPageFacade);
  protected readonly result = this.facade.result;
  protected readonly isLoading = this.facade.isLoading;
}

Компромиссы:

  • Много мелких компонентов: лучше переиспользование и тестируемость, но больше файлов и boilerplate imports.
  • «God component»: меньше файлов, но смешивает UI, HTTP, state — сложно тестировать и рефакторить.
  • Smart/dumb split: чёткие границы, но иногда избыточен для trivial UI (одна кнопка).
Проект: feature layout features/main/ui/: main.component.ts (container) + tarot-oracle, tarot-reading (children). Shared UI: shared/ui/card, core/ui/layout. Префикс ngKitty на всех селекторах.

6. Как настраивается селектор, шаблон и стиль компонента с помощью декоратора @Component?

Декоратор @Component принимает объект metadata. selector — CSS-селектор для использования в шаблонах родителя: 'ngKitty-main' (element), '[ngKittyHighlight]' (attribute), '.ngKitty-panel' (class). CLI генерирует с префиксом из angular.json (ngKitty) для избежания коллизий.

Шаблон: template: \`<h1>{{ title() }}</h1>\` (inline) или templateUrl: './main.component.html' (внешний файл). Inline удобен для tiny components (<10 строк); внешние — для readability, Prettier, syntax highlighting. Стили: styles: ['...'] или styleUrl: './main.component.scss' (singular, Angular 17+). styleUrls (массив) — legacy.

Дополнительные опции: standalone: true (дефолт в новых проектах), imports: [...] (зависимости standalone), encapsulation: ViewEncapsulation.Emulated (дефолт — scoped CSS через уникальные атрибуты), ShadowDom или None, host: { ... } (bindings на host element), changeDetection: ChangeDetectionStrategy.OnPush (в Angular 22 — дефолт, явное указание опционально).

@Component({
  selector: 'ngKitty-main',
  standalone: true,
  imports: [TarotOracleComponent, TranslocoPipe],
  templateUrl: './main.component.html',
  styleUrl: './main.component.scss',
  encapsulation: ViewEncapsulation.Emulated,
  host: {
    class: 'main-page',
    '[attr.aria-busy]': 'isLoading()',
  },
})

Компромиссы:

  • Inline vs external template: inline — меньше файлов, но хуже DX для больших шаблонов; external — стандарт для feature components.
  • Emulated vs ShadowDom encapsulation: Emulated совместим с глобальными Taiga themes; ShadowDom изолирует стили, но ломает CSS variables cascade.
  • styleUrl vs styleUrls: один файл на компонент — проще; несколько — только если реально нужно разделение (редко).
Проект: SCSS с includePaths: ["src", "src/styles"] — короткие @use 'styles/variables'. Taiga themes из node_modules/@taiga-ui/styles/*.less + глобальный src/styles.css. ScanEffectDirective — host bindings для CSS custom properties (--scan-color).

7. Как вы объясните жизненный цикл компонента и его основные методы (например, ngOnInit, ngOnChanges, ngOnDestroy)?

Angular вызывает lifecycle hooks в строгом порядке. После создания instance и первого прохода inputs: ngOnChanges (если есть @Input и они изменились) → ngOnInit (один раз после первого init inputs). Затем content projection: ngAfterContentInit → ngAfterContentChecked. View initialization: ngAfterViewInit (ViewChild доступен) → ngAfterViewChecked. При каждом CD cycle могут вызываться ngDoCheck, ngAfterContentChecked, ngAfterViewChecked. Перед destroy: ngOnDestroy.

Ключевые хуки: ngOnInit — одноразовая setup-логика после DI (подписки, начальная загрузка). ngOnChanges — реакция на изменение @Input (получает SimpleChanges); не вызывается для signal inputs — для них используй effect() или computed(). ngAfterViewInit — DOM ready, можно вызывать focus(), инициализировать chart library. ngOnDestroy — cleanup: unsubscribe, clearInterval, destroy effects.

В signals-era часть логики переезжает: constructor + inject() для DI; effect() для реакции на signal changes (с onCleanup для unsubscribe); afterNextRender() / afterRender() для DOM work без ngAfterViewInit. takeUntilDestroyed() заменяет manual unsubscribe в ngOnDestroy. ngOnInit всё ещё каноничен для side effects, которые не должны быть в constructor.

export class MainPageFacade {
  constructor() {
    effect((onCleanup) => {
      const source = this._sourceResult();
      if (!source) { this._result.set(null); return; }
      const sub = this.translationService.translate(source).subscribe(...);
      onCleanup(() => sub.unsubscribe()); // аналог ngOnDestroy для effect
    });
  }
}

// RxJS + destroyRef — без ngOnDestroy
this.tarotService.loadReading()
  .pipe(takeUntilDestroyed(this.destroyRef))
  .subscribe(...);

Компромиссы:

  • ngAfterViewChecked: вызывается очень часто — тяжёлая логика здесь = perf disaster и ExpressionChanged errors.
  • effect() vs ngOnChanges: effect — для signal inputs; ngOnChanges — legacy @Input; не смешивай без причины.
  • Constructor vs ngOnInit: constructor — только DI/inject; side effects (HTTP, subscriptions) — в ngOnInit/effect, иначе сложнее тестировать.
Проект: MainPageFacade — effect() с onCleanup для translation subscription. HTTP calls — takeUntilDestroyed(destroyRef). SanctumRitualService — rxResource управляет lifecycle stream без ручных хуков.

8. Как работает двустороннее связывание данных в Angular, и в чем отличие от одностороннего связывания данных?

Одностороннее связывание (one-way data flow): данные текут в одном направлении. [property]="expression" — property binding (parent → template/DOM). (event)="handler($event)" — event binding (DOM → component). {{ interpolation }} — одностороннее отображение. Это предсказуемая модель: state меняется в TypeScript, шаблон отражает изменения через CD.

Двустороннее связывание (two-way binding): синтаксический сахар [(ngModel)]="field" = [ngModel]="field" + (ngModelChange)="field = $event". UI и model синхронизируются: пользователь вводит текст → model обновляется → шаблон перерисовывается. Требует FormsModule и подходит для template-driven forms. Banana-in-box [()] — общий паттерн для любого propertyChange output.

В reactive forms двусторонность явная: formControlName="email" связывает control с DOM; изменения идут через valueChanges Observable, не через [(ngModel)]. Signal-based model binding (Angular 17+): [value]="name()" + (input)="name.set($event.target.value)" — one-way + event, OnPush-friendly. Experimental signal forms — будущая альтернатива с типизацией.

// One-way (предпочтительно в OnPush + signals)
<input [value]="email()" (input)="email.set($any($event.target).value)" />

// Two-way template-driven
<input [(ngModel)]="searchQuery" />

// Reactive forms — без ngModel
<form [formGroup]="loginForm">
  <input formControlName="email" />
</form>

Компромиссы:

  • [(ngModel)]: быстро для простых форм и toggles (LanguageSwitcherComponent); плохо масштабируется — нет typed controls, сложнее unit-тесты.
  • Reactive forms: типизация (FormBuilder.nonNullable), sync/async validators, тестируемость — overhead для одного поля.
  • Two-way vs one-way + event: two-way удобнее, но скрывает поток данных; one-way явнее и безопаснее для OnPush.
Проект: registration/login — typed reactive forms + FormBuilder.nonNullable, custom validators, dirtyFormGuard + ModalService. LanguageSwitcherComponent — FormsModule + Taiga select для runtime language switch (единственный ngModel-case).

Документация: Template binding · Forms overview · Reactive forms

9. Отдельные компоненты.

Standalone components (standalone: true в metadata, или дефолт в Angular 19+ CLI) — самодостаточные единицы: сами объявляют imports: [CommonModule, MyPipe, ChildComponent], не требуют NgModule wrapper. Компонент, директива или pipe может быть standalone; они импортируются напрямую в imports другого standalone component или в route loadComponent.

Bootstrapping без AppModule: bootstrapApplication(AppComponent, appConfig), где appConfig: ApplicationConfig содержит providers (router, HTTP, i18n). Lazy loading: loadComponent: () => import('./profile.component').then(c => c.ProfileComponent) — отдельный JS chunk без feature module. Route-level providers создают injector scope для facade/services этой фичи.

Standalone упрощает tree-shaking: импортируешь только то, что используешь. Libraries (Taiga UI, Transloco) экспортируют standalone-compatible API. Миграция legacy: schematics ng generate @angular/core:standalone конвертирует declarations → standalone imports. NgModules не удалены — coexistence возможен, но новый код — standalone-first.

// Standalone component
@Component({
  selector: 'ngKitty-main',
  imports: [TarotOracleComponent, TranslocoPipe],
  templateUrl: './main.component.html',
})
export class MainComponent { ... }

// Lazy route — standalone без NgModule
{
  path: 'altar',
  loadComponent: () => import('./altar.component').then(c => c.AltarComponent),
  providers: [AltarPageFacade],
}

Компромиссы:

  • Standalone: явные imports, лучше tree-shaking, проще onboarding; каждый файл длиннее списком imports.
  • NgModule: barrel re-exports удобны в legacy monoliths, но скрывают реальные зависимости.
  • Route providers: изоляция scope facade, но нужно помнить добавлять providers в app.routes.ts — иначе NullInjectorError.
Проект: все компоненты ngKittyDebug — standalone. Bootstrap: main.ts → bootstrapApplication(AppComponent, appConfig). Lazy routes: profile, login, altar, sanctum, shrift — loadComponent. Eager: MainComponent на path: '' с MainPageFacade в route providers.

10. Что такое ViewChild и ViewChildren?

@ViewChild(selector) получает ссылку на один элемент в template текущего компонента: child component, directive или ElementRef. Доступен после ngAfterViewInit (или static: true — до CD, только если element не в *ngIf). @ViewChildren — QueryList всех matching elements, обновляется при изменении DOM.

Signal API (Angular 17+): viewChild<TarotReadingComponent>('reading'), viewChildren<CardComponent>(CardComponent) — реактивные signals, без timing pitfalls static/dynamic. Читаешь this.readingRef()?.focus() в effect или после render. contentChild() / contentChildren() — для projected content через ng-content, не template children.

ViewChild — escape hatch для императивного доступа: focus(), scrollIntoView(), интеграция с non-Angular widgets (chart libs, Taiga overlay refs). Предпочитай declarative data binding и signal inputs; ViewChild оправдан, когда API библиотеки требует DOM ref или component instance.

// Signal ViewChild (рекомендуется)
export class HostComponent {
  private readonly reading = viewChild(TarotReadingComponent);

  public scrollToReading(): void {
    afterNextRender(() => {
      this.reading()?.elementRef.nativeElement.scrollIntoView();
    });
  }
}

// Legacy decorator
@ViewChild('oracleForm') oracleForm!: TarotOracleComponent;

Компромиссы:

  • ViewChild vs data binding: binding декларативен и тестируем; ViewChild связывает parent с implementation details child.
  • static: true: ранний доступ, но ломается если element за *ngIf — prefer signal viewChild + afterNextRender.
  • ViewChild vs ContentChild: ViewChild — own template; ContentChild — projected slots (ng-content).
Проект: большинство UI — declarative signals (MainComponent читает facade, не ViewChild). ViewChild уместен для Taiga overlay/dialog integration и focus management в forms — при необходимости в login/register specs.

11. В чем разница между ElementRef и Renderer2?

ElementRef — DI-токен, обёртка над native DOM element host'а компонента/директивы. elementRef.nativeElement даёт прямой доступ к DOM API (focus(), scrollTop, getBoundingClientRect()). Angular документирует это как last resort: обходит абстракцию рендерера, ломает SSR/web worker compatibility, создаёт XSS-риск при работе с user-generated content.

Renderer2 — platform-agnostic API для DOM mutations: setStyle(), addClass(), removeClass(), setAttribute(), listen(). Работает в browser, server (no-op или mock), web worker contexts. Инжектируется через RendererFactory2. В modern Angular большинство задач Renderer2 решаются декларативно: [class.active], [style.width.px], host: { ... } в декораторе.

Современная альтернатива: host bindings object в @Component / @Directive — всё в metadata, без императивного DOM. afterNextRender() для one-time DOM setup. ElementRef допустим для trusted low-level cases (focus trap, scroll, third-party lib integration), когда declarative bindings недостаточно.

// Декларативно — предпочтительно (ScanEffectDirective)
@Directive({
  host: {
    '[class.is-scanning]': 'scanEnabled()',
    '[style.--scan-color]': 'scanColor()',
  },
})

// Renderer2 — если нужен imperative access
private readonly renderer = inject(Renderer2);
private readonly el = inject(ElementRef);
this.renderer.addClass(this.el.nativeElement, 'highlight');

// ElementRef — escape hatch
this.el.nativeElement.focus();

Компромиссы:

  • ElementRef.nativeElement: простой и прямой, но platform-coupled и XSS-sensitive.
  • Renderer2: абстракция для SSR, но verbose; в browser-only SPA часто избыточен.
  • Host bindings: декларативны, OnPush-friendly, но не покрывают сложные third-party APIs.
Проект: ScanEffectDirective — CSS custom properties через host bindings, без ElementRef/Renderer2. Стили altar/sanctum — SCSS + Taiga tokens, не imperative DOM.

12. Как работают декораторы HostBinding и HostListener?

@HostBinding('property') привязывает свойство host element: @HostBinding('class.active') isActive = true, @HostBinding('attr.role') role = 'button', @HostBinding('style.color') color = 'red'. @HostListener('event', ['$event']) подписывается на DOM events host'а: @HostListener('click') onClick(), @HostListener('document:keydown.escape') onEscape().

Современная замена (рекомендуется): объект host в metadata @Component / @Directive — всё в одном месте, без отдельных декораторов на методах/полях:

@Directive({
  selector: '[ngKittyScanEffect]',
  host: {
    class: 'scan-effect',
    '[class.is-scanning]': 'scanEnabled()',
    '[style.--scan-color]': 'scanColor()',
    '(mouseenter)': 'onEnter()',
    '(keydown.escape)': 'onEscape($event)',
  },
})

Host bindings работают с signals: '[class.active]': 'isActive()' — CD отслеживает signal read. Это идеально для attribute directives, которые меняют поведение/вид host без собственного template. hostDirectives (Angular 15+) — композиция директив на component host.

Компромиссы:

  • host object vs @HostBinding/@HostListener: object — декларативен, всё в metadata; decorators — legacy style, размазаны по классу.
  • Host listener vs @Output: host listener для internal behavior directive; output — для communication с parent.
  • Global listeners (document:click): мощно, но нужен cleanup — prefer hostListener с narrow scope или fromEvent + takeUntilDestroyed.
Проект: ScanEffectDirective — signal input() + declarative host bindings для CSS classes и custom properties (--scan-duration, --scan-opacity). Подключена на layout (tui-root) для ambient scan animation.

Документация: Host elements · hostDirectives

13. Каков механизм обнаружения изменений в Angular, и в чем разница между Default и OnPush?

Change Detection (CD) — процесс синхронизации state компонента с DOM. Angular обходит дерево компонентов (depth-first), сравнивает текущие значения bindings с предыдущими, обновляет DOM при расхождении. Триггеры: async events (клики, HTTP, timers — через Zone.js или явные notifications), signal writes, markForCheck(), async pipe emit.

Default strategy: компонент проверяется при любом CD cycle в приложении (если путь от root проходит через него). Просто для новичков, но риск лишних проверок в больших apps. OnPush strategy: компонент проверяется только когда: (1) @Input reference изменился, (2) event originated в компоненте или его descendants, (3) async pipe получил новое значение, (4) signal read в template invalidated, (5) explicit markForCheck() / detectChanges().

Angular 22: OnPush — дефолт для новых components. Signals интегрированы в CD graph: чтение signal в template автоматически помечает view «dirty» при signal.set(). provideZoneChangeDetection({ eventCoalescing: true }) — оптимизация Zone.js. Zoneless (provideExperimentalZonelessChangeDetection) — CD только по signals/events, без Zone patching overhead.

// Angular 22 — OnPush default, signals auto-tracked
@Component({
  selector: 'ngKitty-main',
  template: `@if (isLoading()) { <spinner /> }
             @if (result(); as r) { <tarot-reading [data]="r" /> }`,
})
export class MainComponent {
  protected readonly isLoading = inject(MainPageFacade).isLoading; // computed signal
  protected readonly result = inject(MainPageFacade).result;
}

Компромиссы:

  • OnPush + immutable data + signals: предсказуемая perf, меньше лишних checks; требует дисциплины (не мутировать objects in place).
  • Default: проще — «изменил поле, UI обновился»; в больших apps — perf bottlenecks.
  • Zone.js vs zoneless: Zone автоматически триггерит CD после async; zoneless — явнее, но нужны signals/effects для всех async paths.
  • markForCheck(): escape hatch для OnPush при mutable state — code smell, лучше signals.
Проект: app.config.ts — provideZoneChangeDetection({ eventCoalescing: true }). Facades используют signals (MainPageFacade._result, uiStateStore NgRx Signals). UI templates — @if/@for + signal reads, не mutable class fields.

Документация: Change detection · OnPush · Signals

14. Как вы обрабатываете динамические компоненты?

Динамический компонент — тип и/или момент создания определяется в runtime, а не статически в template. Три основных паттерна Angular:

1. ViewContainerRef.createComponent() — императивное создание: inject ViewContainerRef, вызов createComponent(MyComponent, { bindings: [inputBinding('id', () => id())], ... }). Полный контроль lifecycle: destroy(), setInput(), projectableNodes для content projection. Подходит для plugin systems, CMS-driven UI.

2. NgComponentOutlet — декларативный рендер в шаблоне по ссылке на класс: <ng-container *ngComponentOutlet="activeComponent; inputs: { userId: id() }" />. Проще read, меньше boilerplate; inputs/outputs bindings с Angular 17.3+. 3. Dialog/overlay services — компонент вне DOM-иерархии родителя (Taiga TuiDialogService, CDK Overlay). 4. @defer — lazy loading subtree шаблона по триггеру (viewport, idle, interaction) — не dynamic type, но dynamic loading.

// Imperative — createComponent
const ref = this.vcr.createComponent(ConfirmDialogComponent, {
  bindings: [
    inputBinding('message', () => 'Leave without saving?'),
    outputBinding('confirmed', () => this.onConfirm()),
  ],
});

// Declarative — NgComponentOutlet
<ng-container *ngComponentOutlet="
  tabComponent();
  inputs: { data: tabData() }
" />

// Lazy template block — @defer
@defer (on viewport) {
  <ngKitty-heavy-chart [data]="chartData()" />
} @placeholder {
  <div class="skeleton" />
}

Компромиссы:

  • Dynamic vs static @if: dynamic гибче (runtime type selection), но обходит AOT template checking — ошибки bindings только в runtime.
  • createComponent vs outlet: createComponent — полный lifecycle control и projection; outlet — проще, декларативнее.
  • @defer vs route loadComponent: defer — granularity внутри страницы (below-the-fold widgets); route lazy — целые фичи. ngKittyDebug использует route lazy + UserStateStrategy preloading.
  • Overlay/dialog: компонент вне CD tree родителя — нужен focus trap, explicit destroy, accessibility.
Проект: ModalService — TuiDialogService.open() для dirtyFormGuard confirm. Routes — loadComponent lazy (profile, altar, sanctum). Profile — ngTemplateOutlet для секций вместо dynamic component overhead. @defer пока не используется — route-level splitting + preloading достаточны; кандидат — тяжёлые sanctum chunks.

15. Что такое директивы в Angular?

Директива — класс с декоратором @Directive, который расширяет поведение или представление существующего DOM-элемента (host) без собственного шаблона. В отличие от компонента, директива не задаёт view — она «надстраивается» поверх элемента, на котором объявлена.

Формально компонент — частный случай директивы: у него есть template / templateUrl и собственный selector как элемент (ngKitty-header). Директива же обычно выступает атрибутом ([ngKittyScanEffect]) или структурным префиксом (*ngIf).

Зачем нужны:

  • Переиспользование DOM-логики — один раз описать поведение (классы, CSS variables, listeners) и применять на разных host-элементах.
  • Разделение ответственности — компонент отвечает за layout и данные, директива — за cross-cutting UI-эффект (scan-line, blink, tooltip).
  • Структурное управление DOM — создание/уничтожение embedded views через ViewContainerRef (*ngIf, @if).
  • Интеграция с Angular DI и CD — директива участвует в injector tree, получает input()/output(), триггерит change detection так же, как компонент.

Типы: атрибутные (меняют существующий element), структурные (добавляют/убирают nodes), компоненты (директива + template). В Angular 22 новый код предпочитает встроенный control flow (@if, @for) вместо legacy structural directives, но атрибутные custom directives остаются ключевым инструментом.

Компромиссы:

  • Директива vs компонент — директива не имеет template: проще переиспользовать на чужом DOM (например, tui-root), но сложнее тестировать визуально без host component.
  • Директива vs сервис — сервис не знает о DOM; директива нужна, когда логика привязана к host element (стили, events, ARIA).
  • Custom structural directive vs @if — встроенный control flow быстрее и читабельнее; custom structural оправдан для domain DSL (permissions, feature flags).
Проект: ScanEffectDirective — атрибутная standalone-директива на <tui-root ngKittyScanEffect> в app.component.html: scan-line через CSS custom properties без дублирования разметки в каждой feature-странице.

16. В чем разница между структурными и атрибутными директивами?

Атрибутные директивы изменяют уже существующий DOM-элемент: добавляют/убирают CSS-классы, inline-стили, слушают события, меняют ARIA-атрибуты. Element остаётся в дереве — меняется только его поведение или внешний вид.

<div [ngClass]="{ active: isActive() }" ngKittyScanEffect>...</div>

Примеры: ngClass, ngStyle, routerLink, ScanEffectDirective.

Структурные директивы управляют наличием DOM: создают или уничтожают embedded views. Синтаксис с префиксом * — syntactic sugar над ng-template:

<div *ngIf="show()">content</div>
<!-- разворачивается в: -->
<ng-template [ngIf]="show()">
  <div>content</div>
</ng-template>

Примеры: *ngIf, *ngFor, *ngSwitchCase. Под капотом — инжекция TemplateRef + ViewContainerRef, вызов createEmbeddedView() / clear().

Angular 17+ control flow заменяет legacy structural directives встроенными блоками шаблона — они не являются директивами в runtime, компилируются оптимальнее:

@if (user()) { <ngKitty-profile /> }
@for (sin of facade.sins(); track sin.uid) { ... }

Компромиссы:

  • Атрибутные — element всегда в DOM: подписки и CD продолжают работать; хорошо для toggle стилей, плохо для тяжёлых subtree.
  • Структурные / @if — destroy/init cost при переключении, но экономия памяти и CD для скрытого контента.
  • *ngIf vs @if — @if поддерживает @else, @else if, локальные переменные (as user) без ng-template; рекомендуется для нового кода.
  • Один element — одна structural directive — для нескольких structural на одном узле нужен ng-container или вложенные блоки @if.
Проект: шаблоны на @if/@for (shrift.component.html, candles.component.html, layout.component.html); атрибутная ScanEffectDirective на корневом tui-root — app-wide визуальный эффект без structural logic.

18. Объясните ngIf и ngFor и их использование.

*ngIf — structural directive условного рендеринга. При truthy condition создаёт embedded view; при falsy — уничтожает (component destroy hooks, отписки). Поддерживает else и then templates:

<div *ngIf="reading(); else loadingTpl">{{ reading() }}</div>
<ng-template #loadingTpl>Loading...</ng-template>

*ngFor — итерация по коллекции. Для каждого item создаёт view. Критичен trackBy — функция identity для reuse DOM nodes при изменении массива:

<li *ngFor="let sin of sins(); trackBy: trackByUid">{{ sin.text }}</li>

trackByUid(_: number, sin: Sin): string {
  return sin.uid;
}

Без trackBy Angular при любом новом array reference пересоздаёт все DOM nodes — потеря focus, лишний CD, мигание анимаций.

Современная замена — built-in control flow (Angular 17+):

@if (tarotReading(); as result) {
  <ngKitty-tarot-reading [reading]="result" />
} @else if (isLoading()) {
  <span>{{ 'main.loading' | transloco }}</span>
}

@for (card of result.cards; track card.position) {
  <ngKitty-card [card]="card" />
} @empty {
  <p>No cards</p>
}

Ключевые отличия @for от *ngFor:

  • track — обязателен (compile-time check), заменяет trackBy
  • @empty — встроенный блок для пустой коллекции
  • let i = $index, let first = $first — локальные переменные без ngFor microsyntax
  • Компилятор генерирует более эффективный код — меньше overhead ng-template

Компромиссы:

  • @if vs *ngIf — @if читабельнее, поддерживает @else if; legacy синтаксис нужен только в старом коде или библиотеках.
  • track / trackBy — без identity Angular diff'ит по index: insert/delete в середине списка пересоздаёт «хвост».
  • Conditional render vs [hidden] — @if destroy subtree (см. вопрос 19); для частого toggle лёгкого UI иногда выгоднее CSS hide.
Проект: tarot-reading.component.html — @if (tarotReading(); as result) + @for (card of result.cards; track card.position). shrift.component.html — @for (sin of facade.sins(); track sin.uid). candles.component.html — два независимых @for с разными track keys (candle.id, litCandle.instanceId).

19. В чем разница между *ngIf и [hidden]?

*ngIf / @if — структурное условие: при false embedded view не создаётся (или уничтожается). Component tree не существует → ngOnDestroy, отписки, дочерний CD не работают.

[hidden]="condition" — атрибутное binding: element остаётся в DOM, Angular ставит CSS display: none (через property binding). Component инициализирован, subscriptions активны, CD может проверять скрытый subtree.

Компромиссы:

  • [hidden] — быстрый toggle без destroy/init (tabs, accordion panels с частым переключением); платишь памятью и CD.
  • @if — тяжёлые виджеты (charts, maps, rich editors), условные формы, lazy content; destroy cost при каждом показе.
  • @defer — третий вариант: отложенная загрузка + условный render для performance-critical lazy blocks.
Проект: условный UI через @if (layout.component.html — @if (user()) для sidebar chrome; tarot-oracle.component.html — loading state). [hidden] не используется как основной паттерн — предпочтение structural control flow.

20. Какова цель ngSwitch, ngSwitchCase и ngSwitchDefault?

ngSwitch — attribute directive для multi-way branching: один host element с [ngSwitch]="discriminator", дочерние structural directives *ngSwitchCase="value" показывают ровно один matching case, *ngSwitchDefault — fallback.

<div [ngSwitch]="ritualPhase()">
  <p *ngSwitchCase="'idle'">Choose intent</p>
  <div *ngSwitchCase="'judging'">Judging...</div>
  <div *ngSwitchCase="'verdict'">Verdict</div>
  <p *ngSwitchDefault>Unknown phase</p>
</div>

Сравнение — strict equality (===). Только один case активен; остальные views уничтожены.

Современная замена — @switch:

@switch (facade.judgmentPhase()) {
  @case ('idle') { <ngKitty-intent-picker /> }
  @case ('judging') { <ngKitty-spinner /> }
  @case ('verdict') { <ngKitty-verdict [result]="facade.judgment()" /> }
  @default { <p>Unknown</p> }
}

@switch — block syntax без ng-template wrapper, compile-time проверки, лучше читаемость при 3+ ветках.

Компромиссы:

  • @switch vs цепочка @if/@else if — switch читабельнее при многих дискретных значениях enum/string; для 2 веток достаточно @if/@else.
  • Switch vs object map — switch для фиксированных case; map Record<Phase, Component> + ngComponentOutlet — для plugin-like extensibility (сложнее типизация).
  • Performance — все non-matching cases уничтожены; не держит скрытые subtree как [hidden].

Документация: NgSwitch · @switch block

21. В чем разница между ngStyle и ngClass?

[ngClass] — attribute directive для динамического набора CSS-классов. Принимает:

  • Object — { 'active': isActive(), 'disabled': loading() } (ключ — class name, value — boolean)
  • Array — ['btn', isPrimary() ? 'btn-primary' : 'btn-secondary']
  • String — 'class-a class-b'

[ngStyle] — attribute directive для динамического набора inline CSS properties:

[ngStyle]="{
  'font-size.px': size(),
  'opacity': isVisible() ? 1 : 0,
  'color': theme() === 'dark' ? '#fff' : '#000'
}"

Ключи могут использовать unit suffix (.px, .%, .em).

Современная альтернатива — native binding syntax (предпочтительно):

<div
  [class.active]="isActive()"
  [class.disabled]="loading()"
  [style.--scan-opacity]="scanOpacity()"
  [style.width.px]="panelWidth()"
>

Native bindings проще для IDE, меньше directive overhead, лучше tree-shaking. ScanEffectDirective использует именно host: { '[style.--scan-color]': 'scanColor()' } — тот же принцип.

Компромиссы:

  • ngClass / ngStyle — удобны, когда набор классов/стилей вычисляется как один object в computed(); один binding вместо десятка.
  • [class.x] / [style.x] — проще и быстрее для 1–3 статических условий; Angular 22 default.
  • Inline styles vs CSS classes — классы лучше для theme/design tokens; inline — для динамических значений (CSS variables, drag position).
Проект: ScanEffectDirective — declarative [style.--scan-*] host bindings вместо ngStyle. stat-card.component.html — [class.secondary]="i === 1" в profile loop.

Документация: NgClass · NgStyle · Class and style bindings

22. Что такое ngContainer и для чего он используется?

<ng-container> — специальный логический grouping element, который не создаёт DOM node в rendered output. Angular обрабатывает его содержимое, но в browser DevTools вы не увидите wrapper.

Типичные use cases:

  1. Группировка structural directives без лишнего <div> (важно для flex/grid layout):
<ng-container *ngIf="showHeader()">
  <h2>Title</h2>
  <p>Subtitle</p>
</ng-container>
  1. Несколько siblings под одним structural condition — @if { ... } block уже решает это без wrapper.
  2. ngTemplateOutlet — рендер named template с context:
<ng-container
  *ngTemplateOutlet="achieveTemplate; context: { icon: achieve.icon, title: achieve.title }"
/>
  1. Multi-directive host — когда на одном element нельзя повесить две structural directives, одна уходит на ng-container.

С built-in control flow (@if, @for) ng-container для простого conditional/grouping нужен реже — block syntax не требует wrapper. Остаётся актуален для ngTemplateOutlet, i18n multi-node blocks, legacy structural syntax.

Компромиссы:

  • ng-container vs <div> — container не ломает CSS layout; div добавляет box model node.
  • @if { } vs ng-container *ngIf — block syntax чище для нового кода; container + outlet — для template reuse patterns.
  • ng-content vs ng-container — разные механизмы: projection vs logical grouping без DOM.
Проект: profile.component.html — @for achievements + ng-container *ngTemplateOutlet="achieveTemplate; context: {...}" для переиспользуемого шаблона карточки достижения без дублирования разметки.

Документация: ng-container · NgTemplateOutlet

23. Как создать собственные структурные директивы с использованием ng-template?

Structural directive — класс, который получает TemplateRef<C> (шаблон из microsyntax) и ViewContainerRef (контейнер для embedded views). Логика: clear() + createEmbeddedView().

Классический пример — appUnless (инверсия ngIf):

@Directive({ selector: '[appUnless]', standalone: true })
export class UnlessDirective {
  private readonly templateRef = inject(TemplateRef);
  private readonly viewContainer = inject(ViewContainerRef);

  @Input() set appUnless(condition: boolean) {
    this.viewContainer.clear();
    if (!condition) {
      this.viewContainer.createEmbeddedView(this.templateRef);
    }
  }
}
<p *appUnless="isLoggedIn()">Please log in</p>

Как работает microsyntax *:

<section *appUnless="cond; let ctx = context">...</section>
<!-- desugars to: -->
<ng-template [appUnless]="cond" let-ctx="context">
  <section>...</section>
</ng-template>

Context template variables: createEmbeddedView(templateRef, { $implicit: value, custom: data }) — в шаблоне let-item = $implicit, let-x="custom".

Structural directives с input alias: @Input() set appUnless(condition) — setter реагирует на изменение binding и пересоздаёт view.

Компромиссы:

  • Custom structural vs @if — для простого conditional custom directive избыточен; @if быстрее и поддерживается компилятором.
  • Domain DSL — *appHasRole="'admin'", *appFeatureFlag="'altar'" — оправданы: инкапсулируют permission logic, скрывают DOM целиком.
  • ViewContainerRef imperative API — мощный, но сложнее тестировать и отлаживать, чем declarative control flow.
Проект: structural logic через @if/@for, не custom structural directives. Переиспользование шаблонов — ng-template + ngTemplateOutlet в profile (achievements), что близко по механике (TemplateRef), но без custom directive class.

Pipes

24. Что такое пайпы в Angular?

Pipe — класс с декоратором @Pipe, реализующий интерфейс PipeTransform с методом transform(value, ...args). В шаблоне применяется через pipe syntax:

{{ rawValue | pipeName:arg1:arg2 }}

Назначение: presentation-layer transforms — форматирование дат, валют, регистра строк, truncate, mapping enum → label. Разделяет display logic от component class и template expressions.

Ключевые свойства:

  • Pure by default (pure: true) — Angular кэширует результат per binding per CD cycle; пересчёт только при изменении input reference или args.
  • Standalone — импорт в imports компонента (как директивы), NgModule не обязателен.
  • Tree-shakeable — неиспользуемые pipes не попадают в bundle.
  • Chainable — output одного pipe → input следующего (слева направо).

Pipes не должны содержать side effects (HTTP, mutation global state) — нарушает pure contract и ломает кэширование.

Компромиссы:

  • Pipe vs computed() в компоненте — pipe переиспользуем в шаблонах; computed — когда transform нужен и в class, и в template, или зависит от нескольких signals.
  • Pipe vs метод компонента — {{ formatDate(d) }} вызывается каждый CD cycle (unless memoized); pure pipe кэшируется.
  • Pipe vs i18n service — для сложной локализации (Transloco) часто pipe-обёртка (TranslocoPipe) или template syntax; custom pipe мапит domain value → i18n key.
Проект: MachineSpiritStatePipe — domain pipe: boolean → i18n key для статуса machine spirit. Используется в header и altar statistics вместе с TranslocoPipe.

Документация: Pipes overview · @Pipe · PipeTransform

26. В чем разница между 'чистыми' и 'не чистыми' пайпами?

Pure pipe (pure: true — default): Angular считает pipe чистой функцией от (value, ...args). Пересчёт transform() происходит только когда:

  • изменилась reference входного value (primitive — по value),
  • изменилась reference любого argument,
  • начался новый change detection cycle для этого binding (кэш сбрасывается между cycles, но внутри cycle — memoized).

Impure pipe (pure: false): transform() вызывается при каждом change detection для этого binding — как метод компонента в шаблоне. Опасен на hot paths (списки, частый CD).

@Pipe({ name: 'appImpureFilter', pure: false })
export class ImpureFilterPipe implements PipeTransform {
  transform(items: Item[], query: string): Item[] {
    return items.filter(i => i.name.includes(query)); // каждый CD!
  }
}

Когда impure «оправдан» (редко): pipe должен реагировать на mutation объекта без reference change (anti-pattern — лучше immutable updates). AsyncPipe по сути impure по поведению (подписка + emit), но реализован специально с lifecycle management.

Компромиссы:

  • Pure + immutable data — предсказуемая perf; mutation in-place без новой reference → stale pipe output.
  • Impure pipe vs computed() — computed явнее, интегрирован с signals CD; impure pipe скрывает частоту вызовов.
  • Filter/sort в pipe — для больших коллекций лучше computed() в facade с memoization, не impure pipe в @for.
Проект: MachineSpiritStatePipe — pure (default): детерминированный boolean → string key, без side effects. Безопасен в header subtitle, где binding обновляется при изменении isSpiritPleased() signal из altar/layout.

27. Как использовать несколько пайпов одновременно?

Pipes в шаблоне образуют цепочку слева направо — output каждого становится input следующего:

{{ value | pipeA | pipeB:arg | pipeC }}

Эквивалентно вложенным вызовам: pipeC(pipeB(pipeA(value, ...), arg), ...).

Пример из ngKittyDebug — altar statistics:

{{ isSpiritPleased() | machineSpiritState | transloco | uppercase }}
  1. machineSpiritState — true → 'header.status_pleased', false → 'header.status_unstable'
  2. transloco — key → localized string (ru/en)
  3. uppercase — финальный display регистр

Header — @let для промежуточного результата:

@let machineSpiritState = isSpiritPleased() | machineSpiritState | transloco;

{{ 'header.subtitle' | transloco: { machineSpiritState } }}

@let (Angular 18+) — локальная переменная шаблона; избегает дублирования цепочки и улучшает читаемость при передаче в transloco params.

Порядок важен: {{ date | date:'medium' | uppercase }} — uppercase бессмысленен для уже formatted date string. {{ text | slice:0:10 | uppercase }} — корректно.

Компромиссы:

  • Длинная цепочка в template — читаемость падает после 3–4 pipes; вынеси в @let или computed().
  • Pipe chain vs один composite pipe — chain переиспользует built-in pipes; composite pipe — один import, но дублирует Transloco logic.
  • Performance — каждый pure pipe memoized per step; impure pipe в середине chain ломает эффективность для всего downstream.
Проект: цепочка machineSpiritState | transloco | uppercase в altar; @let + transloco interpolation params в header.component.html.

Документация: Chaining pipes · Template variables (@let)

28. Как передать параметры в пайп?

Аргументы передаются через colon-separated syntax после имени pipe:

{{ text | slice:start():end() }}
{{ price | currency:'EUR':'symbol':'1.2-2' }}
{{ items | slice:0:limit() }}

Сигнатура в классе pipe — positional parameters после value:

@Pipe({ name: 'truncate' })
export class TruncatePipe implements PipeTransform {
  transform(value: string, maxLen = 50, suffix = '…'): string {
    if (value.length <= maxLen) return value;
    return value.slice(0, maxLen) + suffix;
  }
}
{{ longQuote | truncate:80:'…' }}

Правила для pure pipe cache:

  • Args сравниваются по reference (objects) или value (primitives).
  • Literal primitives (80, 'EUR') — stable между CD cycles.
  • Args из signal/function calls (limit()) — пересчёт при изменении return value.
  • Inline object literal {{ x | pipe:{a:1} }} — новая reference каждый CD → cache miss (избегай).

Компромиссы:

  • Positional args — лаконично, но не self-documenting после 2+ params; для сложных options — один object arg или config interface.
  • Template args vs DI config — locale/timezone для DatePipe можно через pipe args или inject(LOCALE_ID) в custom pipe.
  • Many params in template — признак, что transform лучше в computed() или facade method.

29. Каковы преимущества асинхронных пайпов? Как применить с Observable и Promise?

AsyncPipe (| async) — подписывается на Observable или Promise, unwrap последнее значение в шаблон, автоматически:

  • unsubscribe при destroy компонента (нет memory leaks),
  • markForCheck при новом emit — работает с OnPush,
  • показывает null до первого emit (или используй @if + as alias).
@if (user$ | async; as user) {
  <p>{{ user.displayName }}</p>
} @else {
  <p>Loading...</p>
}

<!-- Promise -->
{{ configPromise | async }}

Legacy syntax: *ngIf="user$ | async as user" — то же с alias.

Современная альтернатива в signal-first apps:

// component
private readonly authService = inject(AuthService);
readonly user = toSignal(this.authService.user$, { initialValue: null });

// template
@if (user(); as u) { {{ u.displayName }} }

toSignal() — мост RxJS → signals: auto-unsubscribe, явное место подписки в class, проще unit-test facade logic без template.

Компромиссы:

  • async pipe — меньше boilerplate в шаблоне, встроенный lifecycle; но Observable остаётся «снаружи» signals model.
  • toSignal / resource() — единый reactive model, лучше для Angular 22 + OnPush default; чуть больше class code.
  • Multiple async на один Observable — multiple subscriptions (cold stream)! Используй shareReplay или один toSignal.
  • Promise в async pipe — нет unsubscribe (Promise не cancellable), но повторный render безопасен.
Проект: ngKittyDebug преимущественно на signals (MainPageFacade, uiStateStore, altar/shrift facades) — не async pipe в feature templates. RxJS остаётся на HTTP boundary; toSignal в сервисах вроде PriestQuotesService где нужен bridge.

30. Как происходит процесс регистрации собственного пайпа в модуле?

Standalone (Angular 15+, default в ngKittyDebug):

  1. Создать класс с @Pipe({ name: 'myPipe', standalone: true }) — в Angular 19+ standalone: true часто implicit.
  2. Реализовать PipeTransform.transform().
  3. Добавить pipe в массив imports standalone-компонента, где используется.
@Pipe({ name: 'machineSpiritState' })
export class MachineSpiritStatePipe implements PipeTransform {
  transform(value: boolean): string {
    return value ? marker('header.status_pleased') : marker('header.status_unstable');
  }
}

@Component({
  imports: [MachineSpiritStatePipe, TranslocoPipe],
  template: `{{ isSpiritPleased() | machineSpiritState | transloco }}`,
})
export class HeaderComponent { ... }

Исторически (NgModule):

@NgModule({
  declarations: [MachineSpiritStatePipe],
  exports: [MachineSpiritStatePipe], // если нужен другим modules
})
export class SharedModule {}

Standalone-подход убирает SharedModule barrel — каждый component явно декларирует dependencies; лучше tree-shaking и навигация по коду.

Global registration (редко): pipe можно добавить в bootstrapApplication providers только через import в root — отдельного «providePipe» нет; pipes не DI-сервисы, а template declarations.

Компромиссы:

  • Per-component import — verbose при 10+ components; shared re-export file (@shared/pipes/index.ts) без NgModule — компромисс.
  • Pipe vs facade method — display-only transform → pipe; бизнес-логика с DI/state → facade computed(), не pipe.
  • NgModule exports — implicit «всё из SharedModule» раздувает bundle; standalone imports точнее.
Проект: MachineSpiritStatePipe в @shared/pipes/ — imported в HeaderComponent и StatisticsComponent отдельно. Без NgModule; marker keys для Transloco keys manager extraction.

31. Как обрабатывать сложные преобразования в пайпах?

Principles для production pipes:

  1. Keep pure and deterministic — same input → same output, no side effects, no HTTP/Firestore в transform().
  2. Single responsibility — один pipe = один тип transform; композиция через chaining (machineSpiritState | transloco | uppercase).
  3. DI sparingly — inject(LOCALE_ID), inject(TranslocoService) возможны (inject() в field initializer), но усложняют testing; часто лучше pipe → key, отдельный pipe/service → translation.
  4. Heavy work — not in pipe — sort/filter больших arrays, regex на megabytes → computed() в facade с explicit dependencies.

Case study — MachineSpiritStatePipe:

@Pipe({ name: 'machineSpiritState' })
export class MachineSpiritStatePipe implements PipeTransform {
  transform(value: boolean): string {
    return value
      ? marker('header.status_pleased')
      : marker('header.status_unstable');
  }
}

Pipe не переводит сам — возвращает i18n key через marker() (Transloco keys manager для static extraction). Перевод — ответственность TranslocoPipe downstream. Разделение:

  • domain mapping (pleased/unstable) — MachineSpiritStatePipe
  • locale resolution — TranslocoPipe
  • presentation tweak — UpperCasePipe

Testing complex pipes:

const pipe = new MachineSpiritStatePipe();
expect(pipe.transform(true)).toBe(marker('header.status_pleased'));
expect(pipe.transform(false)).toBe(marker('header.status_unstable'));

Pure pipe тестируется как функция без TestBed. Integration с Transloco — отдельный component test с mock loader.

Anti-patterns:

  • Impure pipe с filter/sort коллекции в @for — O(n) каждый CD.
  • Pipe с mutable cache object без invalidation strategy.
  • Pipe, вызывающий transloco.translate() sync — скрытая dependency, stale language switch без pure re-run (лучше key + TranslocoPipe).

Компромиссы:

  • Thin pipe + chain — переиспользуемость и testability; больше символов в template (mitigate @let).
  • Fat pipe with inject(TranslocoService) — один pipe в template, но impure/pure issues при language change, сложнее unit test.
  • Facade computed() instead — spiritStatusLabel = computed(() => ...) — лучше когда label нужен и в TS (aria-label, toast), не только в template.
Проект: MachineSpiritStatePipe — эталон «тонкого» domain pipe: boolean from LayoutService/isSpiritPleased input → i18n key → TranslocoPipe. Altar offerings влияют на spirit state → header subtitle обновляется через signal chain, pipe остаётся pure transform.

Routing

32. Что такое маршрутизация в Angular?

Маршрутизация — client-side механизм сопоставления URL приложения с компонентами (view). Angular Router работает поверх History API браузера: при смене адреса SPA не делает полную перезагрузку страницы, а подменяет содержимое <router-outlet>, обновляет историю и синхронизирует состояние с URL.

Router — не просто «переключатель экранов». Он управляет деревом маршрутов (вложенные children), guards (доступ, dirty forms), resolvers (предзагрузка данных), lazy loading (code splitting через dynamic import()), route data (метаданные для preloading, title, breadcrumbs), а также navigation extras (query params, fragment, state).

В Angular 22 конфигурация маршрутов — декларативный массив Routes, регистрация через provideRouter() в ApplicationConfig, а не через RouterModule.forRoot() в NgModule. Feature-функции (withComponentInputBinding(), withPreloading(), withViewTransitions()) подключаются композицией.

Компромиссы:

  • SPA routing vs MPA: мгновенные переходы и сохранение client state, но сложнее SEO без SSR/prerender и нужна явная обработка deep links.
  • Flat vs nested routes: плоская конфигурация проще читать; вложенные маршруты дают persistent shell (header/sidebar) без дублирования layout в каждой фиче.
  • Eager vs lazy routes: синхронный component: быстрее при первом визите, но увеличивает initial bundle; loadComponent — наоборот.
  • Imperative vs declarative navigation: routerLink в шаблоне проще и безопаснее; Router.navigate() нужен для post-action redirects (logout, submit).
Проект: app.routes.ts — корневой маршрут с LayoutComponent и дочерними feature routes. app.config.ts — provideRouter(routes, withComponentInputBinding(), withViewTransitions(), withPreloading(UserStateStrategy)). Главная (MainComponent) eager; altar, shrift, sanctum, profile, login, register, ball, not-found — lazy через loadComponent.

Документация: Routing overview · Router API · provideRouter

33. Как настроить базовую систему маршрутизации с RouterModule и router-outlet?

Исторически (NgModule): в AppModule импортировали RouterModule.forRoot(routes) (или forChild в feature module). RouterModule регистрировал Router, ActivatedRoute, директивы routerLink, routerOutlet. Shell-компонент содержал <router-outlet></router-outlet> — placeholder, куда router монтирует активный routed component.

Современный подход (Angular 15+, ngKittyDebug / Angular 22):

// app.routes.ts
export const routes: Routes = [
  {
    path: '',
    component: LayoutComponent,
    children: [
      { path: '', pathMatch: 'full', component: MainComponent },
      { path: 'altar', loadComponent: () => import('./features/altar/...').then(c => c.AltarComponent) },
      { path: '**', loadComponent: () => import('./features/not-found/...').then(c => c.NotFoundComponent) },
    ],
  },
];

// app.config.ts
provideRouter(routes, withComponentInputBinding(), withViewTransitions(), withPreloading(UserStateStrategy))

Standalone shell-компонент импортирует RouterOutlet, RouterLink, RouterLinkActive напрямую в декораторе — NgModule не нужен. В шаблоне LayoutComponent: <router-outlet /> внутри <main>; sidebar и header остаются на месте, children swap в outlet.

Named outlets, auxiliary routes — редкий кейс (модалки в URL); для ngKittyDebug достаточно primary outlet.

Компромиссы:

  • RouterModule vs provideRouter: модуль тащит legacy DI surface; provideRouter tree-shakeable и composable через feature functions.
  • forRoot vs forChild: в NgModule-мире forRoot — singleton router; forChild — доп. routes в lazy module. В standalone — один provideRouter в root config, lazy routes в том же Routes массиве.
  • Empty path + pathMatch: 'full': без pathMatch: 'full' пустой path «съедает» все URL; с ним — только exact match на /.
  • withViewTransitions(): плавные CSS View Transitions между routes; на старых браузерах — graceful fallback без анимации.
Проект: LayoutComponent — persistent chrome (header, sidebar, footer) + <router-outlet /> в main-content. Навигация через routerLink="login", routerLink="/profile", routerLinkActive="active". Bootstrap — standalone app.config.ts, без AppModule.

34. Как использовать параметры маршрута и queryParams?

Route params — часть path, описываются сегментами :paramName:

{ path: 'profile/:userId', component: ProfileComponent }

Читаются через ActivatedRoute:

// Observable (реагирует на смену param без destroy компонента)
route.paramMap.pipe(map(p => p.get('userId')))

// Snapshot (одноразово, типично в resolver/guard)
route.snapshot.paramMap.get('userId')

Query params — после ? в URL (/search?q=tarot&lang=ru). Не участвуют в route matching, optional filters/state:

route.queryParamMap.pipe(map(q => q.get('lang')))

router.navigate(['/main'], { queryParams: { lang: 'ru' }, queryParamsHandling: 'merge' })

Angular 16+ / signal inputs (рекомендуемый паттерн в Angular 22): с withComponentInputBinding() route params и query автоматически биндятся на input() компонента:

@Component({ ... })
export class DetailComponent {
  userId = input.required<string>();       // из :userId
  lang = input<string>();                   // из ?lang=
}

Меньше boilerplate: не нужен ngOnInit + subscribe + takeUntilDestroyed. Input обновляется при navigation на тот же component class с другими params (reuse strategy).

Matrix params (;key=value) — legacy, на практике почти не используют; предпочитайте query params.

Компромиссы:

  • Path params vs query params: path — identity ресурса (RESTful, bookmarkable); query — optional state (фильтры, tab). Слишком много query — «грязный» URL; обязательный id в query хуже для SEO и UX.
  • paramMap Observable vs snapshot: snapshot проще, но stale при reuse; Observable — актуален, но нужна отписка или toSignal(paramMap).
  • input binding vs ActivatedRoute: inputs — declarative, OnPush-friendly; ActivatedRoute — нужен для route.parent, firstChild, imperative traversal.
  • queryParamsHandling: 'merge' сохраняет существующие query; 'preserve' при relative navigation; без опции — replace all query.
Проект: withComponentInputBinding() включён глобально в app.config.ts — готовность к param/query inputs без subscribe. Текущие routes без :id (фиксированные path: profile, altar); язык — через uiStateStore + Firestore, не query string. В тестах — activatedRouteMock с paramMap / data.

Child routes рендерятся во <router-outlet> родительского routed component, а не в root outlet приложения. Родитель остаётся смонтированным — идеально для app shell.

export const routes: Routes = [
  {
    path: '',
    component: LayoutComponent,   // shell: header + sidebar + <router-outlet>
    children: [
      {
        path: '',
        pathMatch: 'full',
        component: MainComponent, // outlet LayoutComponent → главная

      },
      {
        path: 'altar',
        canMatch: [authGuard],
        loadComponent: () =>
          import('./features/altar/ui/altar.component').then(c => c.AltarComponent),
        providers: [AltarPageFacade],
      },
      {
        path: 'shrift',
        canMatch: [authGuard],
        loadComponent: () =>
          import('./features/shrift/ui/shrift.component').then(c => c.ShriftComponent),
        providers: [ShriftPageFacade, ConfessFormService],
      },
    ],
  },
];

Relative navigation: из child context routerLink="altar" резолвится относительно activated route. Absolute: routerLink="/profile". Programmatic: router.navigate(['altar'], { relativeTo: route }).

Empty parent path (path: '') — children «наследуют» URL родителя без extra segment. path: 'admin' у parent дал бы /admin/altar.

Nested children — feature может иметь свой outlet и sub-routes (tabs, wizard steps). В ngKittyDebug features — leaf routes без второго уровня nesting.

Компромиссы:

  • Nested vs sibling top-level routes: nested — один layout, shared injector context ближе к parent; siblings — проще guards, но layout дублируется или выносится в wrapper route (как в проекте).
  • Lazy parent vs lazy child: lazy parent грузит shell + child chunk; lazy child при eager parent — только feature chunk (паттерн ngKittyDebug).
  • Route-level providers на child: создают child injector; уничтожаются при уходе с route — хорошо для facades, плохо для «забытых» singletons.
  • Component reuse: при navigation между siblings parent не пересоздаётся — side effects в parent constructor выполняются один раз.

36. Какие существуют стратегии предварительной загрузки?

Preloading — фоновая загрузка lazy route chunks после initial bootstrap, до явного клика пользователя. Router вызывает PreloadingStrategy.preload(route, load) для каждого lazy route; стратегия решает: вернуть load() (начать fetch chunk) или of(null) (пропустить).

Встроенные стратегии:

  • NoPreloading (default) — chunks только on-demand при navigation. Минимальный background traffic.
  • PreloadAllModules — прелоадит все lazy routes в idle time. Название legacy (NgModule era); работает и с loadComponent.

Custom PreloadingStrategy: class с методом preload(route: Route, load: () => Observable<unknown>). Типичные критерии:

  • route.data flags (preload: true, preloadFor: 'auth')
  • Auth state, feature flags, network conditions (Network Information API)
  • Priority queue — сначала «горячие» routes (dashboard), потом редкие (settings)

Подключение: provideRouter(routes, withPreloading(MyStrategy)). Стратегия — injectable service (@Injectable или @Service() в Angular 22).

Компромиссы:

  • NoPreloading vs PreloadAllModules: первый — меньше трафика, выше latency первого клика; второй — быстрее subsequent navigation, но guest может скачать auth-only chunks зря.
  • Preload vs @defer (on viewport): preloading — router-level, после bootstrap; @defer — template-level, по trigger. Можно комбинировать.
  • Custom strategy complexity: точнее контроль (auth-aware), но нужны тесты и sync с guards — иначе preload chunk, который user never can activate.
  • Mobile / slow networks: агрессивный preload на 3G может ухудшить perceived performance; учитывайте navigator.connection или opt-out.
Проект: UserStateStrategy — custom preloading по auth. Routes помечены data: { preloadFor: PreloadFor.AUTH | PreloadFor.GUEST }. Guest получает preload login/register/crystal-ball; authenticated — profile/shrift/altar/sanctum. Main route без preloadFor — never preloaded (eager anyway). Spec: user-state-strategy.service.spec.ts.

Документация: Preloading · PreloadingStrategy · PreloadAllModules · withPreloading

37. Как использовать Route Guards (CanActivate и CanDeactivate)?

Guards — функции/hooks, которые router вызывает на этапах navigation lifecycle. В Angular 15+ — functional guards (CanMatchFn, CanActivateFn, CanDeactivateFn, CanActivateChildFn, ResolveFn) с inject() вместо class-based guards с @Injectable().

Типы и когда вызываются:

  • canMatch — до route matching и до lazy load. Если false / UrlTree — route «не существует» для router, пробует другие конфиги.
  • canActivate — после match, до активации component. Lazy chunk уже может быть загружен.
  • canDeactivate — при уходе с текущего activated route. Возвращает boolean | UrlTree | Observable<boolean> — async для modal confirm.
  • canActivateChild — на child routes parent'а.
// authGuard — CanMatchFn
export const authGuard: CanMatchFn = () => {
  const authService = inject(AuthService);
  const router = inject(Router);
  return authService.isAuthenticated() ? true : router.createUrlTree(['/login']);
};

// guestGuard — inverse: logged-in user → home
export const guestGuard: CanMatchFn = () => {
  const authService = inject(AuthService);
  const router = inject(Router);
  return authService.isAuthenticated() ? router.createUrlTree(['']) : true;
};

// dirtyFormGuard — CanDeactivateFn
export const dirtyFormGuard: CanDeactivateFn<ComponentWithForm> = (component) => {
  if (!component.form.dirty) return true;
  return inject(ModalService).openConfirmModal(/* ... */); // Observable<boolean>
};

Return values: true — allow; false — cancel navigation; UrlTree — redirect (preferred over manual router.navigate в guard — атомарно с navigation).

Route config:

{ path: 'login', canMatch: [guestGuard], canDeactivate: [dirtyFormGuard], loadComponent: ... }
{ path: 'altar', canMatch: [authGuard], loadComponent: ... }

Компромиссы:

  • canMatch vs canActivate для auth: canMatch блокирует lazy load unauthorized chunks — меньше leaked code в network tab; canActivate проще ментально, но chunk уже fetched.
  • Guard vs resolver: guard — permission gate; resolver — data prefetch. Не блокируй UI данными в guard — используйте resolver или component resource().
  • Sync vs async guards: Observable/Promise поддерживаются; router ждёт completion. Длинный async guard = blank screen — показывайте loading через router events.
  • Functional vs class guards: functional — меньше ceremony, tree-shakeable; class — legacy tutorials, DI через constructor.
Проект: authGuard на profile, shrift, altar, sanctum; guestGuard на login, register; dirtyFormGuard на login/register (проверка component.form.dirty + Taiga confirm modal). Тесты через TestBed.runInInjectionContext(() => authGuard(...)) — без полного routing setup.

38. Что такое ActivatedRoute, и как его использовать?

ActivatedRoute — injectable сервис, представляющий один сегмент дерева activated routes. Содержит snapshot текущего route и Observable-потоки, эмитящие при navigation (param change, query change, data change).

Ключевые свойства:

  • paramMap / params — path parameters (ParamMap.get('id'))
  • queryParamMap / queryParams — query string
  • data — static route.data + resolved data
  • fragment — hash (#section)
  • url — URL segments этого route
  • parent, firstChild, children — traversal по дереву
  • snapshot — frozen picture на момент activation (не обновляется при param change на reuse)
  • routeConfig — ссылка на конфиг route
  • outlet — primary или auxiliary
private readonly route = inject(ActivatedRoute);

// Reactive (preferred for changing params)
readonly userId = toSignal(this.route.paramMap.pipe(map(p => p.get('id'))));

// Static data from route config
readonly preloadFor = toSignal(this.route.data.pipe(map(d => d['preloadFor'])));

// Child param from parent context
this.route.parent?.paramMap...

ActivatedRoute vs Router: Router — imperative navigation + global events (events, url); ActivatedRoute — read state текущего component context. В nested routes inject'ится ближайший segment; для root — использовать router.routerState.root.

С Angular 16+: при withComponentInputBinding() params/query мапятся на input() — ActivatedRoute нужен реже (imperative subscribe, parent traversal, library code).

Компромиссы:

  • snapshot vs Observable: snapshot — zero subscription overhead, но stale при RouteReuseStrategy reuse; Observable — correct, но требует lifecycle management.
  • paramMap vs params: ParamMap — typed API (get, has, keys); legacy params object — plain key-value.
  • inject(ActivatedRoute) vs input(): inputs — меньше кода в component; ActivatedRoute — гибче для shared services и nested traversal.
  • route.data typing: по умолчанию Data untyped; в проекте cast через as PreloadFor — trade-off pragmatism vs strict typing interface.
Проект: UserStateStrategy.preload() читает route.data?.['preloadFor'] из route config. В component tests — activatedRouteMock (shared/mocks/activated-route/) вместо real router. withComponentInputBinding() в production config — prefer signal inputs для future param routes.

39. Как обрабатывать ленивую загрузку в маршрутизации?

Lazy loading в Angular Router — code splitting через dynamic import() в route config. Webpack/esbuild создаёт отдельный JS chunk; он fetch'ится только когда router решает активировать route (или preloading strategy вызывает load()).

Два API:

  • loadComponent — lazy standalone component (Angular 14+, primary в Angular 22)
  • loadChildren — lazy child Routes array или legacy NgModule

  path: 'sanctum',

    import('./features/sanctum/ui/sanctum.component').then(c => c.SanctumComponent),

  2. canMatch guards (до load)
  3. loadComponent / loadChildren → dynamic import
  4. Route-level providers → child injector
  5. Component create → render в parent router-outlet
  6. Navigate away → destroy component + destroy route injector (если нет cached reuse)

40. Зачем RxJS в Angular?

RxJS (Reactive Extensions for JavaScript) — библиотека реактивного программирования, где асинхронные события моделируются как Observable — push-based поток значений во времени. Angular встроил RxJS с самого начала, потому что UI, HTTP, маршрутизация и формы по природе событийны: ответ сервера приходит позже, пользователь кликает, меняется язык, таймер срабатывает через N мс.

В Angular RxJS используется на async-границах:

  • HttpClient — каждый запрос возвращает Observable (ленивый, отменяемый через unsubscribe).
  • Router.events, ActivatedRoute.params — потоки навигации.
  • Reactive Forms — valueChanges, statusChanges.
  • HTTP interceptors — цепочка операторов (catchError, map).
  • Guards/resolvers — могут возвращать Observable<boolean | UrlTree>.

Angular 22 не заменяет RxJS signals'ами — они дополняют друг драга. Signals — для синхронного UI state с fine-grained change detection. RxJS — для композиции async pipelines, отмены запросов, параллелизма, таймеров. Мост: @angular/core/rxjs-interop — toSignal, toObservable, takeUntilDestroyed, rxResource.

Компромиссы:

  • RxJS для всего UI state — boilerplate Subjects, ручная отписка, хуже DX в шаблонах; в ngKittyDebug loading/error/result — signals в facades.
  • Signals для всего async — теряются операторы (switchMap, mergeMap, forkJoin); сложнее отменять in-flight HTTP при смене параметров.
  • Promise + async/await — читаемо для one-shot, но нет встроенной отмены и композиции; firstValueFrom — мост, не замена pipeline.
Проект: RxJS на границах: MainPageFacade (tarot HTTP + translation pipeline), createRitualTimelineStream (timer + merge), CandlesService (timer + takeUntilDestroyed), httpErrorInterceptor (catchError). UI state — signals (uiStateStore, facade readonly signals).

41. Что такое Observable, Observer и Subscriptions?

Observable<T> — объект, представляющий ленивый поток значений типа T. До вызова subscribe() producer не выполняется (lazy). Может выдать 0..N значений через next, затем завершиться complete() или прерваться error(err).

Observer<T> — потребитель потока, интерфейс с тремя необязательными callback:

interface Observer<T> {
  next: (value: T) => void;
  error?: (err: unknown) => void;
  complete?: () => void;
}

В subscribe можно передать объект Observer или три отдельных функции: subscribe(next, error, complete).

Subscription — результат subscribe; handle для управления подпиской:

  • unsubscribe() — останавливает поток и вызывает teardown-функцию producer'а.
  • closed — флаг, что подписка уже закрыта.
  • add(fn) — регистрация дополнительного cleanup.

Teardown: в new Observable(subscriber => { ...; return () => cleanup }) возвращаемая функция вызывается при unsubscribe. Критично для setInterval, addEventListener, WebSocket — иначе ресурс остаётся в памяти.

Жизненный цикл: subscribe → (опционально) несколько next → ровно один исход: complete или error → после этого next игнорируются. HTTP GET — типично один next + complete, но unsubscribe до ответа отменяет запрос (XHR/fetch abort).

Компромиссы:

  • HTTP GET — поток конечный, но отмена до ответа всё равно важна при быстрой навигации (takeUntilDestroyed в MainPageFacade).
  • Infinite streams (interval, Subject без complete) — без отписки подписчик и producer остаются в памяти.
  • Множественные subscribe на cold Observable — отдельный запуск producer на каждую подписку (два http.get без share = два HTTP-запроса).
Проект: MainPageFacade.loadTarot() — subscribe({ next, error }) на HTTP; translation effect — subscription.unsubscribe() в onCleanup. SanctumRitualService — rxResource управляет подпиской на ritual timeline.

Документация: Observable · Subscription · HttpClient

43. Можете ли вы привести примеры основных операторов RxJS в Angular? (map, filter, switchMap, mergeMap, catchError, takeUntilDestroyed, finalize, forkJoin, timer, merge)

Оператор — чистая функция вида (source: Observable) => Observable, вызывается в source.pipe(op1, op2, ...). Порядок операторов задаёт порядок обработки событий.

Transformation:

  • map(fn) — синхронное преобразование каждого значения (DTO → view model).
  • switchMap(fn) — inner Observable; при новом outer emit отписывается от предыдущего inner (search, typeahead).
  • mergeMap(fn, concurrency?) — inner Observable параллельно; опциональный лимит N одновременных inner.

Filtering: filter(predicate) — пропускает только значения, удовлетворяющие условию.

Combination:

  • forkJoin({ a: obsA$, b: obsB$ }) — ждёт complete всех источников; один emit с последними значениями.
  • merge(a$, b$, ...) — все события в один поток по мере поступления.
  • timer(delay) — один emit через delay мс (creation operator).

Error / lifecycle:

  • catchError(project) — перехват error, возврат recovery Observable или rethrow.
  • finalize(fn) — вызывается при complete, error или unsubscribe (сброс loading).
  • takeUntilDestroyed(destroyRef) — Angular-оператор; auto-unsubscribe при destroy компонента/directive.
// Проект: параллельный перевод карт и вердикта
forkJoin({
  cards: this.translateCardList(reading.cards, lang),
  verdictText: this.translateText(reading.verdict_text, lang),
}).pipe(map(({ cards, verdictText }) => ({ ...reading, cards, verdict_text: verdictText })));

// Проект: чанки текста — max 2 одновременных HTTP (MyMemory API limit)
from(chunkList.map((chunk, index) => ({ chunk, index }))).pipe(
  mergeMap(({ chunk, index }) =>
    this.translateChunk(chunk, lang).pipe(map((t) => ({ index, translated: t }))),
    2
  ),
  toArray(),
  map((items) => items.sort((a, b) => a.index - b.index).map((i) => i.translated).join(' ')),
  catchError(() => of(text))
);

// Проект: ritual timeline — timer + map + merge
return merge(...lineEvents, verdictEvent);

Компромиссы:

  • forkJoin — быстрый параллелизм, но один failed source валит весь результат; для partial success — per-item catchError.
  • mergeMap без лимита — 100 параллельных HTTP → rate limit; в проекте лимит 2 из-за MyMemory API.
  • switchMap vs mergeMap — switch отменяет устаревшие запросы (search); merge сохраняет все in-flight (независимые чанки перевода).
  • finalize vs catchError — finalize срабатывает всегда (включая unsubscribe); catchError только на error path.
Проект: MyMemoryTranslationService — forkJoin на reading/cards, mergeMap(2) на чанках, catchError(() => of(text)). createRitualTimelineStream — timer + map + merge. MainPageFacade — finalize для сброса loading, takeUntilDestroyed на tarot load. CandlesService / BallComponent — timer + takeUntilDestroyed.

44. Как создать собственный Observable с new Observable()?

Создавайте кастомный Observable, когда внешний API основан на callback/listener, а готовые creation-операторы (fromEvent, timer, defer) не покрывают кейс.

Вариант 1 — композиция существующих операторов (предпочтительно в проекте):

export function createRitualTimelineStream(request: RitualRequest): Observable<RitualSessionState> {
  const judgment = analyzeBranch(request.branch, request.spiritLevel, request.ritualIntent);
  const lineEvents = judgment.litany.map((line, index) =>
    timer((index + 1) * RITUAL_LITANY_LINE_DELAY_MS).pipe(
      map(() => ({ litanyLines: judgment.litany.slice(0, index + 1), judgment: null }))
    )
  );
  const verdictEvent = timer(totalDelay).pipe(
    map(() => ({ litanyLines: judgment.litany, judgment }))
  );
  return merge(...lineEvents, verdictEvent);
}

Вариант 2 — new Observable для callback API (WebSocket, legacy SDK):

new Observable<Message>((subscriber) => {
  const ws = new WebSocket(url);
  ws.onmessage = (e) => subscriber.next(JSON.parse(e.data));
  ws.onerror = (e) => subscriber.error(e);
  ws.onclose = () => subscriber.complete();
  return () => ws.close(); // teardown при unsubscribe
});

Контракт producer:

  • После subscriber.complete() или subscriber.error() — нельзя вызывать next.
  • Teardown вызывается при unsubscribe — освобождайте listeners/timers/сокеты.
  • Если subscribe синхронно отписали до первого emit — teardown всё равно должен отработать.

Компромиссы:

  • Композиция timer/merge/fromEvent — проще тестировать (marble tests / fakeAsync), меньше ручного кода.
  • new Observable — полный контроль, но легко забыть teardown или нарушить контракт complete/error.
  • Resource API — для load-one-result с loading/error signals; для progressive stream (ritual litany) — rxResource + Observable pipeline.
Проект: sanctum timeline — только композиция timer + merge, без new Observable. Подключено через rxResource({ stream: () => createRitualTimelineStream(params).pipe(tap(...)) }) в SanctumRitualService.

45. Что такое Subject и BehaviorSubject?

Subject<T> — одновременно Observable (можно подписаться) и Observer (можно вызвать next/error/complete извне). Это multicast: один источник → много подписчиков. Новый подписчик получает только события после момента подписки.

BehaviorSubject<T> — Subject с обязательным начальным значением:

  • При subscribe сразу emit текущего значения (replay последнего).
  • getValue() — синхронное чтение последнего значения (вне reactive context — осторожно).
  • Типичное legacy-использование: currentUser$ = new BehaviorSubject<User | null>(null).

ReplaySubject(n) — буфер последних n значений; новый подписчик получает replay буфера, затем live события. AsyncSubject — emit только последнее значение при complete.

Отличие от signal: Subject не интегрирован в Angular change detection; обновление через Subject в компоненте не обновит шаблон без async pipe или ручного markForCheck. Signal читается в шаблоне напрямую и участвует в CD graph.

Компромиссы:

  • BehaviorSubject как store — привычно Rx-разработчикам, но нет computed; риск забыть complete на root Subject → утечка.
  • shareReplay(1) вместо Subject для HTTP cache — кэширует последний ответ cold-потока; с refCount: true отписка от source, когда нет подписчиков.
  • Signal / SignalStore — idiomatic Angular 22; Subject оставляют для event bus и legacy interop.
Проект: Subject/BehaviorSubject для app state не используются. Глобальный UI — uiStateStore (NgRx SignalStore). Feature state — signals в facades (MainPageFacade._result). Отписка — takeUntilDestroyed, не destroy$ Subject.

Документация: Subject · BehaviorSubject · Signals

47. Как правильно отписаться от Observable?

Утечка памяти возникает, когда подписка остаётся активной после уничтожения компонента или когда producer держит ссылку на closure с DOM/компонентом.

Способы (от предпочтительного к legacy):

  1. async pipe — подписка в шаблоне; Angular отписывается при destroy view.
  2. takeUntilDestroyed(destroyRef) — оператор в pipe перед subscribe; работает в injection context (constructor, field initializer). Angular 16+.
  3. toSignal(obs$) — подписка управляется инфраструктурой signal; отписка при destroy.
  4. effect + onCleanup — для подписки внутри effect: 
    effect((onCleanup) => {
  const sub = stream$.subscribe((v) => doWork(v));
  onCleanup(() => sub.unsubscribe());
});
  5. takeUntil(notifier$) + Subject — в ngOnDestroy: destroy$.next(); destroy$.complete(). Legacy-паттерн.
  6. Конечные потоки — HTTP после complete отписка не обязательна для GC подписчика, но unsubscribe до ответа отменяет запрос.

Компромиссы:

  • async pipe — нельзя использовать результат в TypeScript-классе без дублирования через toSignal или subscribe.
  • subscribe в facade — допустим с takeUntilDestroyed(destroyRef), если facade создаётся в injection context route/component.
  • Subscribe в root service — сервис не уничтожается; infinite stream без complete держит память всё время сессии.
Проект: MainPageFacade — takeUntilDestroyed(this.destroyRef) на tarot load; translation — effect + onCleanup(() => subscription.unsubscribe()). BallComponent — вложенные timer().pipe(takeUntilDestroyed). CandlesService — takeUntilDestroyed на extinguishing timer. uiStateStore — onCleanup на Transloco load() subscription. Нет destroy$ Subject-паттерна.

Документация: takeUntilDestroyed · takeUntil

49. Как обрабатывать обработку ошибок и логику повтора с RxJS?

Ошибка в Observable — отдельный канал: после subscriber.error(err) поток для этой подписки завершён; последующие next не доставляются.

catchError(project) — перехватывает error и возвращает новый Observable (recovery stream):

.pipe(
  catchError((err: HttpErrorResponse) => {
    if (err.status === 404) return of(fallbackData);
    return throwError(() => err);
  })
)

retry(config) — повторная подписка на source после error. Параметры: count, delay, exponential backoff через timer(retryCount * 1000). Применять retry только к идемпотентным операциям (GET, safe read). POST/PUT без idempotency key — риск дублирования.

finalize(fn) — вызывается при любом завершении: complete, error или unsubscribe. Типично: loading.set(false).

Слои в Angular-приложении:

  1. HTTP interceptor — глобальный toast/log, затем throwError (не глотать).
  2. Facade/service — маппинг в domain error signal или fallback value.
  3. Component — отображает facade.error(), не ловит HTTP напрямую.

Partial failure — когда падает элемент коллекции, а не весь поток:

mergeMap((chunk) =>
  this.translateChunk(chunk).pipe(catchError(() => of(chunk)))
)

Компромиссы:

  • catchError(() => of(null)) — UI не видит failure; лучше явный error signal или rethrow после логирования.
  • retry без лимита count — может перегрузить API; нужны count и backoff delay.
  • Только interceptor — нет контекста фичи; facade всё равно нужен для специфичных сообщений и recovery (tarot empty state vs toast).
  • Firebase errors — не проходят HttpClient; обрабатываются в service через try/catch + error signal (CandlesService._error).
Проект: httpErrorInterceptor — HotToast + throwError, skip /i18n/ URLs. MainPageFacade — HttpErrorResponse в error signal; translation error → fallback на source result. MyMemoryTranslationService — per-chunk и whole-text catchError(() => of(originalText)). LoginPageFacade — try/catch + HotToast для Firebase auth errors.

50. Что такое Dependency Injection в Angular?

Dependency Injection (DI) — паттерн проектирования, при котором класс получает зависимости извне через constructor или функцию inject(), а не создаёт их сам (new AuthService()). Angular реализует DI через систему Injector + Provider: token → factory/class/value → instance.

Цели DI в Angular:

  • Testability — в TestBed подменяем { provide: AuthService, useValue: mock }.
  • Loose coupling — компонент зависит от абстракции (интерфейс/token), не от конкретной реализации.
  • Lifecycle control — singleton (providedIn: 'root') vs per-route (providers на route) vs per-component.
  • Composable configuration — ApplicationConfig.providers собирает app-wide wiring.

В Angular 22 предпочтительный стиль — inject(MyService) в field initializer или constructor вместо constructor parameter injection (оба работают). Functional guards/interceptors/resolvers используют inject() внутри функции.

Компромиссы:

  • DI vs manual singleton — DI даёт иерархию и scope; глобальный mutable singleton без DI — анти-pattern (сложно тестировать).
  • Service locator (injector.get) — скрывает зависимости; предпочитай явный inject() в классе.
  • Over-injection — God-service с 15 зависимостями; лучше facade + focused services.
Проект: bootstrap через bootstrapApplication(AppComponent, appConfig). Глобальные providers: provideRouter, provideHttpClient, uiStateStore, tuiValidationErrorsProvider, provideHotToastConfig. Feature DI — route-scoped facades и API services.

Документация: Dependency Injection · DI in depth

51. Как создать сервис и использовать его в компонентах?

Шаг 1 — объявить injectable класс:

@Service() // Angular 22: обёртка над @Injectable({ providedIn: 'root' })
export class AuthService {
  private readonly auth = inject(Auth);
  public async login(email: string, password: string) { /* ... */ }
}

// Или явно:
@Injectable({ providedIn: 'root' })
export class CandlesService { /* ... */ }

Шаг 2 — внедрить в компонент/facade:

@Component({ selector: 'ngKitty-login', /* ... */ })
export class LoginComponent {
  public readonly facade = inject(LoginPageFacade);
}

@Service({ autoProvided: false }) // не root — регистрируется на route
export class LoginPageFacade {
  private readonly authService = inject(AuthService);
  private readonly notifications = inject(HotToastService);
}

Сервис — обычный TypeScript-класс с metadata @Injectable (или @Service). Angular создаёт instance при первом inject в scope соответствующего injector'а. Singleton в root — один instance на всё приложение.

Компромиссы:

  • @Service() vs @Injectable({ providedIn: 'root' }) — декоратор Angular 22 сокращает boilerplate; autoProvided: false для route-scoped сервисов.
  • Constructor injection vs inject() — inject() работает в field initializers и functional providers; constructor — классический стиль.
  • Component inject facade, не service — UI не должен знать про AuthService + Router + toast; один LoginPageFacade.
Проект: кастомный @Service() из @angular/core — единообразие (CandlesService, LoginFormService, facades). Компоненты inject только facade: LoginComponent → LoginPageFacade. Shared domain: CandlesService в core/, providedIn: 'root'.

52. В чем разница между providedIn: 'root', providedIn: 'any' и регистрацией в providers?

  • providedIn: 'root' — singleton на всё приложение; регистрация в root environment injector. Tree-shakeable: если сервис нигде не inject'ится, bundler может удалить класс.
  • providedIn: 'any' — новый instance per lazy-loaded bundle (редко используется; legacy pattern для изоляции между chunks).
  • providers: [MyService] в @Component, route или ApplicationConfig — instance per injector scope. Route providers уничтожаются при navigation away.
  • @Service({ autoProvided: false }) — Angular 22: класс injectable, но не auto-registered в root; нужна явная регистрация в route/component providers.

NgModule era: providers: [S] в @NgModule — instance per module injector. В standalone apps — route/component/app.config providers.

Компромиссы:

  • Root singleton (AuthService, CandlesService) — shared state, один Firestore listener; но harder to reset между tests без override.
  • Route providers (MainPageFacade, TarotService) — изоляция feature, fresh instance per visit; нельзя inject из другого route без shared root service.
  • providedIn: 'any' — почти never needed в standalone Angular 22; prefer explicit route scope.
Проект: root: AuthService, CandlesService, uiStateStore, LoginFormService. Route-scoped (autoProvided: false): MainPageFacade + TarotService + MyMemoryTranslationService на path: ''; LoginPageFacade на /login; SanctumRitualService на /sanctum.

53. Что такое useClass, useValue и useFactory?

Provider — объект { provide: TOKEN, ... }, описывающий, как создать dependency:

  • useClass — Angular создаёт instance указанного класса (или alias): { provide: AuthService, useClass: MockAuthService }.
  • useValue — константа или готовый объект: { provide: API_URL, useValue: '/api' }.
  • useFactory — функция создаёт instance динамически: { provide: X, useFactory: () => new X(inject(Y)), deps: [Y] }.
  • useExisting — alias: тот же instance, что у другого token.
// app.config.ts — factory с inject()
tuiValidationErrorsProvider(() => {
  const transloco = inject(TranslocoService);
  return {
    required: () => transloco.translate('validation.required'),
    confirmPasswordError: (key) => transloco.translate(key as string),
  };
});

// TestBed — useValue mock
{ provide: HotToastService, useValue: hotToastServiceMock }

Компромиссы:

  • useClass mock — новый instance per injector; useValue — shared object (осторожно с mutable state между тестами).
  • useFactory — гибко для conditional DI, но сложнее читать; overuse → spaghetti wiring.
  • useExisting — DRY для alias tokens; не создаёт второй instance.
Проект: tuiValidationErrorsProvider — useFactory с inject(TranslocoService). UI_STATE token — factory: () => initialUiState. Tests: { provide: HotToastService, useValue: mock }, { provide: CandlesService, useValue: candlesServiceMock }.

54. Объясните концепцию Injector и иерархии провайдеров.

Angular DI — иерархическая система инжекторов. При inject(MyService) фреймворк ищет провайдер снизу вверх.

Два типа инжекторов:

  • Environment injectors — вне DOM: platform → root (app.config.ts) → route injectors (providers на каждом route).
  • Element injectors — у каждого экземпляра компонента или директивы в DOM-дереве.

Алгоритм разрешения:

  1. Старт в element injector текущего компонента/директивы.
  2. Подъём по DOM к родительским компонентам (element injector chain).
  3. Если не найден — переход в environment injector ветки (route injector → parent routes → root).
  4. NullInjectorError — token нигде не зарегистрирован.

Shadowing: дочерний providers: [X] создаёт новый экземпляр X для поддерева; родительский экземпляр не затрагивается.

viewProviders vs providers: viewProviders видны только view children компонента, не projected content (ng-content).

Компромиссы:

  • Route injector — изоляция feature state; но сервис недоступен вне route subtree без root registration.
  • Component providers — новый instance per component instance; дороже по памяти, но изоляция для reusable widgets.
  • Root singleton — простой shared state; shadowing на route может accidentally создать «два AuthService» если неосторожно зарегистрировать на route.
Проект: root injector — app.config.ts providers. Route injectors — app.routes.ts: main route tree получает MainPageFacade; login — LoginPageFacade. LayoutComponent — shell без feature providers; children routes создают свои injectors.

55. Что такое DI-токен, и как его использовать?

InjectionToken<T> — typed key для зависимостей, которые не являются классом (строки, конфиги, интерфейсы):

export const UI_STATE = new InjectionToken('UiState', {
  factory: () => initialUiState,
});

export const MY_MEMORY_TRANSLATION_URL = new InjectionToken<string>(
  'MyMemoryTranslationUrl',
  { factory: () => environment.myMemoryUrl }
);

// Usage
private readonly uiState = inject(UI_STATE);
private readonly url = inject(MY_MEMORY_TRANSLATION_URL);

Токены также используются для:

  • Multi providers — HTTP_INTERCEPTORS, ENVIRONMENT_INITIALIZER.
  • Interface tokens — InjectionToken<Logger> + useClass: ConsoleLogger.
  • Configuration objects — API URLs, feature flags из environment.

Компромиссы:

  • InjectionToken vs string token — string tokens ('UiState') коллидируют; InjectionToken type-safe и уникален.
  • factory на token — lazy default value; но сложнее override в tests без явного provider.
  • Interface без token — TypeScript interfaces стираются at runtime; DI не может inject interface без token + implementation.
Проект: UI_STATE — начальное состояние для uiStateStore (withState(() => inject(UI_STATE))). MY_MEMORY_TRANSLATION_URL — URL MyMemory API inject'ится в MyMemoryTranslationService. VALIDATION_ERRORS_DICT — не token, а shared dictionary для tuiValidationErrorsProvider.

56. Как использовать декораторы @Optional, @Self и @SkipSelf для управления DI? (also inject(..., {optional,self,skipSelf}))

Angular позволяет управлять областью поиска и обязательностью dependency:

  • @Optional / { optional: true } — если provider не найден, inject возвращает null вместо NullInjectorError.
  • @Self / { self: true } — искать только в текущем element injector, не подниматься к родителям.
  • @SkipSelf / { skipSelf: true } — пропустить текущий injector, искать у parent.
  • @Host / { host: true } — искать до host component (для директив в projected content).
// Modern style (Angular 14+)
private readonly parentTheme = inject(ThemeService, { optional: true, skipSelf: true });
private readonly localControl = inject(NgControl, { optional: true, self: true });

// Legacy constructor style
constructor(@Optional() @SkipSelf() parent: ParentComponent | null) {}

Типичные кейсы:

  • Optional parent component ref в reusable library widget.
  • Custom form control: inject(NgControl, { self: true, optional: true }) для CSS classes validation state.
  • Избежание circular DI — skipSelf для получения parent instance того же типа.

Компромиссы:

  • Optional everywhere — скрывает misconfiguration; null-checks размазаны по коду.
  • Self/SkipSelf — мощно для library components, но усложняет mental model иерархии.
  • Explicit providers vs flags — лучше правильный scope provider, чем skipSelf как workaround.
Проект: явных @Optional/@Self/@SkipSelf в ngKittyDebug нет — scope решается через route providers и root services. Паттерн актуален для Taiga UI form controls и shared library components; в interview объясняем через inject(..., { optional: true, self: true }).

57. Как внедрять зависимости на основе условий?

Angular DI статичен at compile time — нельзя if (prod) inject(A) else inject(B) в field initializer без паттерна. Подходы:

  • useFactory — factory читает environment и возвращает нужную реализацию: 
    { provide: Logger, useFactory: () =>
  isDevMode() ? inject(ConsoleLogger) : inject(RemoteLogger)
}
  • Environment files — environment.ts / environment.prod.ts с разными values для tokens (useValue: environment.apiUrl).
  • Route-level providers — разные impl per feature route.
  • Strategy pattern — один service inject'ит Map strategies, выбирает runtime по ключу.

Anti-patterns: if/else с new Service() в constructor; conditional providers array spread в runtime без чёткой структуры.

Компромиссы:

  • useFactory — гибко, но wiring opaque; сложнее навигация в IDE vs plain class.
  • Environment file swap at build — простой prod/dev split; не runtime toggle.
  • Runtime conditional inject — через Injector.runInContext или lazy getter; rare, prefer factory.
Проект: isDevMode() в provideTransloco({ prodMode: !isDevMode() }). MyMemoryTranslationService — early return of(reading) если target lang EN (runtime condition в методе, не DI). Firebase config — из environment.ts через static import.

58. Что такое мульти-провайдер и как его настроить?

Multi provider — несколько registrations для одного token; injector собирает их в массив:

providers: [
  { provide: HTTP_INTERCEPTORS, useClass: LogInterceptor, multi: true },
  { provide: HTTP_INTERCEPTORS, useClass: AuthInterceptor, multi: true },
]

// Modern Angular (v15+): functional interceptors
provideHttpClient(withInterceptors([httpErrorInterceptor]))

Другие multi tokens:

  • HTTP_INTERCEPTORS — class-based (legacy).
  • ENVIRONMENT_INITIALIZER — bootstrap hooks (multi: true).
  • NG_VALUE_ACCESSOR, NG_VALIDATORS — form extensibility.
  • APP_INITIALIZER — async bootstrap (deprecated pattern; prefer provideAppInitializer).

Порядок multi providers важен: interceptors выполняются в порядке registration (first in chain — outermost).

Компромиссы:

  • Class interceptors + multi — verbose; functional HttpInterceptorFn + withInterceptors([...]) проще и tree-shakeable.
  • Много interceptors — сложно отследить порядок side effects; документируй chain.
  • Multi vs single provider array — withInterceptors([a, b]) эквивалентен ordered chain без DI multi token.
Проект: provideHttpClient(withInterceptors([httpErrorInterceptor])) — один functional interceptor. tuiValidationErrorsProvider — Taiga multi provider для validation messages. provideAppInitializer — init uiStateStore + AuthService.initialize().

59. Как реализовать внедрение зависимостей для отдельных компонентов?

DI scope можно ограничить конкретным компонентом или route:

  • @Component({ providers: [LocalService] }) — новый instance LocalService per component instance и его view children.
  • viewProviders: [LocalService] — только view children, не projected content.
  • Route providers — scope на всё поддерево route; destroyed при navigation away (если route выгружен).
  • Lazy loadComponent — providers на lazy route изолированы в chunk.
// app.routes.ts — route-scoped facade + API

  path: '',
  component: MainComponent,
  providers: [MainPageFacade, TarotService, MyMemoryTranslationService],

// Component-scoped (пример)
@Component({
  providers: [WidgetStateService], // per widget instance

Компромиссы:

  • Route providers — fresh state per visit; но нельзя share facade между routes без root service.
  • Component providers — изоляция для reusable widgets; каждый instance = новый service (memory).
  • Root facade — anti-pattern; facade state переживёт navigation и leak'нет между features.
Проект: canonical pattern — route providers в app.routes.ts: MainPageFacade + TarotService на main; ShriftPageFacade + ConfessFormService на shrift; SanctumPageFacade + ritual services на sanctum. @Service({ autoProvided: false }) предотвращает accidental root registration.

62. Что такое FormControl, FormGroup и FormArray?

Reactive Forms строятся из иерархии AbstractControl:

  • FormControl<T> — одно поле: value, validators, state (valid, dirty, touched). Atomic unit.
  • FormGroup — объект полей: { email: FormControl, password: FormControl }. Aggregated validity: group invalid если любой child invalid.
  • FormArray — массив controls/groups одного типа: динамический список (skills, phone numbers, sin entries).
// Login — typed FormGroup
this.fb.nonNullable.group<LoginForm>({
  email: this.fb.nonNullable.control('', [Validators.required, Validators.pattern(EMAIL_PATTERN)]),
  password: this.fb.nonNullable.control('', [Validators.required, Validators.pattern(PASSWORD_PATTERN)]),
});

// Register — nullable controls + group validator
this.fb.group<RegisterFormGroup>({
  name: this.fb.control(null, [Validators.required, Validators.maxLength(30)]),
  passwordConfirmation: this.fb.control(null, [Validators.required]),
}, { validators: passwordConfirmationValidator('password', 'passwordConfirmation') });

Общие API: value, getRawValue() (включая disabled), setValue/patchValue, reset, markAsDirty/Touched/Pristine, disable/enable, valueChanges, statusChanges (Observable).

Компромиссы:

  • nonNullable vs nullable controls — nonNullable упрощает типы (string vs string | null); nullable нужен для optional fields (register name до ввода).
  • FormArray — гибко для dynamic lists; но verbose template (@for + formArrayName).
  • Nested FormGroups — mirror domain structure; deep nesting усложняет get('a.b.c') paths.
Проект: LoginFormService — nonNullable.group<LoginForm>. RegisterFormService — nullable group<RegisterFormGroup> с cross-field validator. Confess/sanctum — отдельные FormServices per feature.

63. В чем различия в работе с валидацией для Template-driven и Reactive Forms?

Template-driven:

  • Validators через HTML attributes: required, minlength, pattern на ngModel.
  • Custom — directive с NG_VALIDATORS multi provider.
  • Ошибки в шаблоне: #email="ngModel", @if (email.invalid && email.touched).
  • Модель control создаётся Angular implicitly — доступ через template reference variable.

Reactive Forms:

  • Validators в TypeScript: Validators.required, custom ValidatorFn, group-level validators.
  • Ошибки: form.controls.email.errors, form.get('email')?.hasError('required').
  • updateOn: 'change' | 'blur' | 'submit' — когда запускать validation.
  • Централизованные сообщения — tuiValidationErrorsProvider маппит error keys на i18n strings.

Общее: validation state (VALID, INVALID, PENDING, DISABLED) одинаков; разница в том, где объявляются validators и как читаются errors.

Компромиссы:

  • Template validators — быстро для demo; custom cross-field — awkward.
  • Reactive + tuiValidationErrorsProvider — DRY i18n messages; но нужна настройка provider map.
  • Inline error strings в шаблоне — дублирование; проект использует Taiga tui-error + global provider.
Проект: tuiValidationErrorsProvider в app.config.ts — required, minlength, maxlength, pattern (password vs email), confirmPasswordError через Transloco. Login/register — tui-error на уровне FormControl, не всей формы.

64. Как реализовать собственные валидаторы для форм?

ValidatorFn — синхронная функция:

type ValidatorFn = (control: AbstractControl) => ValidationErrors | null;

export const passwordConfirmationValidator = (
  controlName: string,
  matchingControlName: string
): ValidatorFn => {
  return (abstractControl: AbstractControl): ValidationErrors | null => {
    if (!isFormGroup(abstractControl)) return null;
    const control = abstractControl.controls[controlName];
    const matchingControl = abstractControl.controls[matchingControlName];
    // сравнение values, setErrors на matchingControl, return null на group
  };
};

Уровни:

  • Control-level — control('', [myValidator]).
  • Group-level (cross-field) — group({ ... }, { validators: myGroupValidator }).
  • AsyncValidatorFn — возвращает Observable<ValidationErrors | null> или Promise; control → PENDING.

Factory validators — функция возвращает ValidatorFn с параметрами (passwordConfirmationValidator('password', 'passwordConfirmation')).

Тестирование: pure validator — unit test без TestBed: создай FormGroup, вызови validator, assert control.errors.

Компромиссы:

  • setErrors в group validator — императивно ставит ошибку на sibling control; мощно, но фильтруй чужие errors (confirmPasswordError vs required).
  • Return errors on group vs child — return на group проще для form.errors; setErrors на child — точнее для tui-error per field.
  • Validator в template directive — для TD forms; reactive prefer TS validators in FormService.
Проект: passwordConfirmationValidator в shared/validators/password-confirmation.validator.ts — group-level, сохраняет unrelated errors на matchingControl, ключ confirmPasswordError маппится в tuiValidationErrorsProvider. Spec: password-confirmation.validator.spec.ts без TestBed.

65. Как можно извлечь и обработать данные из форм после их отправки?

Reactive Forms submit flow:

  1. Guard: if (form.invalid || isLoading()) return;
  2. Extract: form.getRawValue() — typed object (включая disabled fields; value их исключает).
  3. Transform: map to DTO / domain model в facade.
  4. Side effect: API call (AuthService.login), navigation, toast.
  5. Reset state: form.markAsPristine(), form.reset() после success.
// LoginPageFacade
public async login() {
  if (this.loginForm.invalid || this.isLoading()) return;
  this.isLoading.set(true);
  const { email, password } = this.loginForm.getRawValue();
  try {
    await this.authService.login(email, password);
    this.loginForm.markAsPristine();
    await this.router.navigate(['/']);
    this.notifications.success(/* transloco */);
  } catch (error) {
    this.notifications.error(/* transloco + toErrorMessage */);
  } finally {
    this.isLoading.set(false);
  }
}

Template-driven: (ngSubmit)="onSubmit(form)" с #form="ngForm"; form.value — объект полей.

Prevent default: (ngSubmit) на <form> автоматически preventDefault; не используй bare (click) на submit без проверки validity.

Компромиссы:

  • getRawValue vs value — raw включает disabled; для submit обычно raw, если disabled fields нужны.
  • Facade vs component submit — logic в facade тестируется без DOM; component только bind (ngSubmit)="facade.login()".
  • Server errors — не через form validators; HotToast в facade (LoginPageFacade), потому что это async domain error, не field validation.
Проект: LoginPageFacade.login(), RegisterPageFacade.signup() — getRawValue() + auth + HotToast + markAsPristine. dirtyFormGuard на login/register — блокирует navigation если form.dirty.

66. Что такое двустороннее связывание данных в контексте Template-driven Forms?

Two-way binding — синтаксис [(ngModel)]="property" (banana-in-a-box): объединяет property binding [ngModel]="property" и event binding (ngModelChange)="property = $event".

В Template-driven forms ngModel создаёт FormControl и синхронизирует:

  • Model → View: при изменении TS property обновляется input.
  • View → Model: при user input обновляется property и FormControl.
<!-- Template-driven two-way -->
<input [(ngModel)]="user.name" name="name" required>

<!-- Reactive equivalent (explicit one-way + event) -->
<input [formControl]="form.controls.name">
// or signal model() in Angular 17.2+ for non-form binding

Требования TD: FormsModule, уникальный name attribute в ngForm для регистрации control. Reactive equivalent — formControlName / [formControl]; two-way не нужен, потому что FormControl сам sync'ит value.

model() signal (Angular 17.2+) — two-way для non-form component inputs: <child [(value)]="mySignal" /> через model() input — не путать с ngModel.

Компромиссы:

  • [(ngModel)] — быстро для prototypes; смешивание с Reactive FormGroup на одной форме — deprecated.
  • Reactive one-way — explicit control; нет magic sync, но полный контроль validators/state.
  • model() signals — two-way для component composition; не заменяет form validation pipeline.
Проект: production forms — Reactive (formControlName), не [(ngModel)]. Two-way binding используется через signal model() / input()+output() в UI components (tarot role/intent), не в auth forms.

67. Как использовать FormBuilder?

FormBuilder — injectable helper для создания FormControl/FormGroup/FormArray с меньшим boilerplate:

@Service()
export class LoginFormService {
  private readonly fb = inject(FormBuilder);

  public readonly loginForm = this.fb.nonNullable.group<LoginForm>({
    email: this.fb.nonNullable.control('', [Validators.required, Validators.pattern(EMAIL_PATTERN)]),

}

API:

  • fb.control(initial, validators, asyncValidators)
  • fb.group(controls, options?) — options: validators, asyncValidators, updateOn
  • fb.array([control1, control2])
  • fb.nonNullable — controls с default value, тип без | null

Компромиссы:

  • FormBuilder vs manual FormGroup — FB короче; manual — explicit для learning/debugging.
  • nonNullable.group — stricter types; nullable group нужен когда fields start as null (register).
  • Form in Service vs Component — service (FormService pattern) — reusable, testable; form in component — ok для trivial one-off.
Проект: LoginFormService, RegisterFormService, ConfessFormService, SanctumFormService — каждый inject'ит FormBuilder, expose readonly form. Facades inject FormService и re-export form для UI.

69. Как обрабатывать асинхронную валидацию?

AsyncValidatorFn — функция, возвращающая Observable<ValidationErrors | null> или Promise<ValidationErrors | null>:

const uniqueEmailValidator: AsyncValidatorFn = (control) => {
  if (!control.value) return of(null);
  return this.http.get<boolean>(`/api/check-email?email=${control.value}`).pipe(
    map((exists) => (exists ? { emailTaken: true } : null)),
    catchError(() => of(null)) // fail open vs fail closed — business decision
  );
};

this.fb.control('', [Validators.required], [uniqueEmailValidator]);

Поведение:

  • Control переходит в PENDING пока async validator не complete.
  • Sync validators выполняются первыми; async — только если sync valid.
  • Angular отменяет предыдущий async validation при новом value (debounce built-in).
  • updateOn: 'blur' — async validation только после blur (меньше HTTP).

Server-side errors после submit (auth failure, 409 conflict) — не async validator; это domain error → toast/notification в facade (HotToastService), не control.setErrors.

Компромиссы:

  • Async validator vs submit-time check — async validator — proactive UX (email taken before submit); submit check — проще, меньше HTTP.
  • fail open (catchError(() => of(null))) — form submittable при API down; fail closed — блокирует submit.
  • debounceTime в validator — extra HTTP reduction; Angular уже cancel'ит stale requests.
Проект: async validators в forms не используются — нет email-uniqueness API. Firebase auth errors (wrong password, email exists) обрабатываются в LoginPageFacade / RegisterPageFacade через try/catch + HotToastService + Transloco — правильный слой для server-side failures. Client-side validation — sync validators + passwordConfirmationValidator + tuiValidationErrorsProvider.

Lazy Loading

70. Что такое Lazy Loading?

Lazy Loading (ленивая загрузка) — паттерн отложенной загрузки кода feature до момента, когда он реально нужен пользователю. В Angular SPA это реализуется на уровне router + bundler: каждый lazy route становится отдельным async chunk, не включённым в main bundle.

Зачем:

  • Уменьшение initial bundle size → быстрее parse/compile/execute JS на cold start
  • Улучшение Time to Interactive (TTI) и Core Web Vitals (LCP, INP)
  • Логическое разделение codebase по feature boundaries
  • Изоляция DI scope (route-level providers)

Механизм: import('./feature') — ECMAScript dynamic import, bundler статически анализирует и emit'ит chunk + loading stub. Router orchestrates когда вызвать import.

Не путать с:

  • Deferrable views (@defer) — lazy template blocks, не routes
  • On-demand module federation — micro-frontends, другой уровень
  • Server lazy loading — SSR streaming, отдельная тема

Компромиссы:

  • Smaller bootstrap vs first-visit latency: пользователь на landing не платит за sanctum code; первый визит на /sanctum — extra network round-trip.
  • Granularity: слишком мелкие chunks → HTTP overhead; слишком крупные → теряется смысл lazy.
  • Lazy everything: over-splitting landing page ухудшит UX; critical path лучше eager.
  • Preloading as mitigation: custom strategy (auth-aware) балансирует без PreloadAllModules waste.
Проект: ngKittyDebug — SPA на Netlify, без SSR. Tarot main page eager; остальные features lazy. Цель — быстрый first paint для anonymous visitor + preload auth/guest routes через UserStateStrategy после AuthService.initialize().

Документация: Lazy-loaded routes · Preloading · Deferrable views

71. Как настроить ленивую загрузку для конкретного модуля?

Legacy (NgModule era):

{
  path: 'admin',
  loadChildren: () =>
    import('./admin/admin.module').then(m => m.AdminModule),
}

AdminModule импортировал RouterModule.forChild(adminRoutes); bundler создавал chunk на весь module graph.

Modern Angular 22 (standalone, ngKittyDebug):

// Один component
{
  path: 'profile',
  canMatch: [authGuard],
  loadComponent: () =>
    import('./features/profile/profile.component').then(c => c.ProfileComponent),
  providers: [provideTranslocoScope('profile'), ProfileFacade],
}

// Sub-route tree (alternative)
{
  path: 'settings',
  loadChildren: () =>
    import('./features/settings/settings.routes').then(m => m.SETTINGS_ROUTES),
}

Checklist настройки lazy feature:

  1. Standalone component с explicit imports: [...]
  2. Route entry с loadComponent и корректным export name в .then(c => c.XxxComponent)
  3. Route-level providers для facade/services
  4. Guards (canMatch) если нужен access control до load
  5. i18n scope через provideTranslocoScope('feature')
  6. Path alias в import() — работает (@features/registration/...), но relative path явнее для chunk naming

Компромиссы:

  • loadComponent vs NgModule loadChildren: standalone проще, без module ceremony; loadChildren нужен для multi-route feature package.
  • Barrel exports (index.ts): удобны, но могут accidentally pull deps в wrong chunk — import конкретный file.
  • Default export vs named: Angular examples — named export; .then(m => m.Component) — typo = runtime error.
  • Route providers vs providedIn: 'root': facade на route — fresh state per visit; root — singleton across app.
Проект: все перечисленные features через loadComponent: profile, login, register, shrift, altar, sanctum, crystal-ball, not-found. Register использует path alias @features/registration/ui/register-page/register-page.component. Каждый route — свой provideTranslocoScope + facade provider(s).

72. Какие изменения в системе маршрутизации необходимы?

Переход на lazy loading требует изменений в route config, bootstrap, feature structure и иногда DI strategy — не только замена component: на loadComponent:.

1. Route configuration (app.routes.ts):

  • Заменить синхронный component: FeatureComponent на loadComponent: () => import(...).then(...)
  • Или loadChildren для nested route arrays
  • Добавить canMatch guards до lazy boundary
  • Перенести feature providers из providedIn: 'root' / AppModule в providers: [...] на route
  • Добавить data metadata для preloading (preloadFor)

2. Application bootstrap (app.config.ts):

  • provideRouter(routes, withPreloading(...), withComponentInputBinding(), ...)
  • Регистрация custom PreloadingStrategy если нужен selective preload
  • Dev-only: withDebugTracing() для диагностики

3. Feature structure:

  • Standalone components (default в Angular 22 CLI)
  • Убрать NgModule wrapper (или оставить только для legacy lib compat)
  • Canonical layout: features/<name>/data/, facades/, ui/

4. Build — без manual config: Angular application builder (esbuild) автоматически code-splits по dynamic import(). Budgets в angular.json контролируют размер chunks.

5. Testing: guards test через runInInjectionContext; component tests — direct import (eager test), не lazy loader.

Компромиссы:

  • Big-bang vs incremental migration: можно lazy-ить route-by-route; main оставить eager (как в проекте).

73. Каковы преимущества использования ленивой загрузки?

  • Меньший initial bundle: браузер загружает только shell + critical route; sanctum/shrift/altar code — later.
  • Быстрее startup: меньше JS parse/compile на слабых устройствах — критично для mobile PWA.
  • Parallel loading: browser может fetch lazy chunks параллельно после idle (preloading).
  • Feature isolation: route-level injector — facades живут только на visit; меньше memory leak risk.
  • Team scalability: features/altar/, features/sanctum/ — независимые boundaries, меньше merge conflicts.
  • Security UX: canMatch + lazy — unauthorized chunks не fetch'атся (defense in depth, не замена server auth).
  • i18n scope splitting: provideTranslocoScope('altar') — translations загружаются с feature.
  • Cache efficiency: deploy новой версии — изменённые chunks invalidate selectively, не весь monolith.

Компромиссы (когда lazy — не silver bullet):

  • Critical landing route (Tarot main) — eager быстрее, чем lazy + preload dance.
  • Micro-features (<5 KB) — overhead dynamic import может превысить выигрыш.
  • Shared state across routes — route-scoped providers требуют explicit root services.
  • Debugging — stack traces across async chunks сложнее.
Проект: anonymous user видит main + layout без загрузки auth-only sanctum/altar code. Authenticated user получает preload auth routes (PreloadFor.AUTH) — subsequent navigation без spinner. Facades (AltarPageFacade, SanctumPageFacade) изолированы per route visit.

74. Что такое стратегия предварительной загрузки, и какие основные стратегии существуют (NoPreloading, PreloadAllModules)?

Preloading strategy — pluggable policy, определяющая какие lazy routes prefetch'ить в background после initial navigation, когда router idle, и как приоритизировать.

Router iterates lazy routes → вызывает strategy.preload(route, loadFn):

  • Return loadFn() (Observable) — начать загрузку chunk
  • Return of(null) — skip

NoPreloading (default):

  • Ничего не prefetch'ит
  • Chunk load только при explicit navigation (или routerLink click)
  • Минимальный background network; худший first-click latency на lazy route

PreloadAllModules:

  • Prefetch все lazy routes после bootstrap
  • Subsequent navigation feels instant
  • Guest скачает auth-only code; mobile user платит трафиком за routes, которые never visits
  • Имя «Modules» — historical; работает с loadComponent

Custom (рекомендуется для real apps): conditional logic — auth state, route.data, priority, network type. В ngKittyDebug — UserStateStrategy с PreloadFor.AUTH | GUEST.

Компромиссы:

  • NoPreloading: best for strict bandwidth / unknown user intent; worst for perceived nav speed.
  • PreloadAllModules: best for small apps with few routes; worst for large apps with role-based access.
  • Custom auth-aware: best UX/bandwidth ratio; requires maintenance + tests (user-state-strategy.service.spec.ts).
  • Timing: preload runs after app stable — race with AuthService.initialize(); strategy must read current auth synchronously.
Проект: вместо NoPreloading/PreloadAllModules — UserStateStrategy. Routes tagged: login/register/crystal-ball → PreloadFor.GUEST; profile/shrift/altar/sanctum → PreloadFor.AUTH. Routes без tag (main, not-found) — never preloaded. Enum PreloadFor в preload-for.model.ts.

75. Как использовать PreloadingStrategy с Angular Router?

Шаг 1 — реализовать стратегию:

@Service()
export class UserStateStrategy implements PreloadingStrategy {
  private readonly authService = inject(AuthService);

  public preload(route: Route, load: () => Observable<unknown>) {
    const isAuthenticated = this.authService.isAuthenticated();
    const preloadFor = route.data?.['preloadFor'] as PreloadFor;

    if (preloadFor === PreloadFor.GUEST) {
      return isAuthenticated ? of(null) : load();
    }
    if (preloadFor === PreloadFor.AUTH) {
      return isAuthenticated ? load() : of(null);
    }
    return of(null);
  }
}

Шаг 2 — зарегистрировать в router config:

provideRouter(
  routes,
  withComponentInputBinding(),
  withViewTransitions(),
  withPreloading(UserStateStrategy),
)

Шаг 3 — пометить routes metadata:

{ path: 'altar', loadComponent: ..., data: { preloadFor: PreloadFor.AUTH } }
{ path: 'login', loadComponent: ..., data: { preloadFor: PreloadFor.GUEST } }

Как это работает internally: после initial navigation router scheduler idle callback → для каждого route с loadComponent/loadChildren вызывает preload. Если strategy returns load() — тот же loader, что при navigation, создаёт chunk fetch. Duplicate calls cached router'ом.

Testing: mock AuthService.isAuthenticated, spy на load fn, assert call/no-call per route data.

Компромиссы:

  • providedIn: 'root' vs @Service(): strategy must be injectable; проект использует @Service() (Angular 22).
  • Sync auth check: если auth async — preload may run before token ready; нужен replay signal или delay preload until init.
  • route.data typing: string enum vs magic strings — enum безопаснее.
  • Over-preloading: sanctum chunk heavy (sound services) — даже auth preload может быть aggressive; можно добавить priority tiers.
Проект: UserStateStrategy в core/services/preloading-strategy/. Подключена в app.config.ts через withPreloading(UserStateStrategy). Полное покрытие spec: guest route + unauthenticated → load; guest + authenticated → skip; auth route inverse; no preloadFor → skip.

76. Какие недостатки ленивой загрузки?

  • First-visit latency: dynamic import = extra HTTP request + parse; пользователь видит loading state (если нет preloading/skeleton).
  • Complexity: route config, guards, providers, chunk paths — больше moving parts чем monolith import.
  • DI scope confusion: route-level vs root providers — bugs типа «state потерялся» или «singleton не singleton».
  • Duplicate dependencies: без proper shared chunks Taiga/RxJS могут дублироваться в multiple lazy bundles → larger total download.
  • Debugging: stack traces через async boundaries; source maps essential; wrong export name — runtime only error.
  • Testing overhead: integration tests across lazy boundaries; guards need injection context setup.
  • Flash of unauthorized content: если guard async/slow — нужен resolver or sync auth signal.
  • SEO ( без SSR ): lazy routes не индексируются отдельно; для ngKittyDebug (Netlify SPA) — acceptable.
  • Preloading misconfiguration: PreloadAllModules wastes bandwidth; wrong custom logic preloads blocked routes.

Когда НЕ lazy-load:

  • Critical path route (main landing) — eager in project.
  • Tiny components без deps — overhead > benefit.
  • Shared dialog/modal used everywhere — root or shared chunk, не per-feature lazy.
  • Services that must survive route change — providedIn: 'root' (AuthService, ConfessService).
Проект: sanctum route тянет 5 route providers (sound, ritual, quotes) — тяжёлый chunk; preload только для auth. Shared domain services (ConfessService, CandlesService) intentionally в root — shrift/altar/profile reuse без duplicate instances.

78. Что такое NgModule?

NgModule (@NgModule decorator) — историческая единица компиляции и организации Angular приложения. Metadata container, описывающий:

  • declarations — components, directives, pipes, принадлежащие module (legacy: не standalone)
  • imports — другие NgModules, чьи exports доступны в templates declarations
  • exports — public API module для importers
  • providers — DI bindings (module injector; forRoot vs forChild nuances)
  • bootstrap — root component(s) для platformBrowserDynamic().bootstrapModule(AppModule)
  • schemas — CUSTOM_ELEMENTS_SCHEMA etc.

Роль в архитектуре (до standalone):

  • Encapsulation — что видно снаружи через exports
  • Lazy loading unit — loadChildren: () => import('./FeatureModule')
  • Compilation boundary для AOT compiler
  • SharedModule pattern — re-export CommonModule + shared components

Angular 22 / ngKittyDebug: приложение standalone-first — нет AppModule, нет feature NgModules. Bootstrap через bootstrapApplication(AppComponent, appConfig). «Модуль» в разговорной речи = features/shrift/ folder, не @NgModule class.

Компромиссы:

  • NgModule vs standalone: modules скрывают dependencies (barrel imports); standalone — explicit imports: [] per component, лучше tree-shaking.
  • Legacy libs: некоторые npm packages ещё export NgModule — import module в standalone component imports: [LegacyModule].
  • Learning curve: tutorials 2020 era — NgModule-heavy; interview 2026 — know history + modern replacement.
  • Lazy loading: NgModule lazy → standalone lazy (loadComponent) — проще mental model.
Проект: zero NgModules в app code. Routing, HTTP, i18n, Taiga — через provide* functions в app.config.ts. Feature boundaries — folders + route config, не module classes.

81. Что такое HttpClientModule и зачем он нужен? (provideHttpClient)

Исторически: HttpClientModule — NgModule-способ зарегистрировать HttpClient и связанные DI-токены в приложении. Он подключал HttpClientXsrfModule, регистрировал class-based interceptors через multi-provider HTTP_INTERCEPTORS и делал HttpClient доступным для инъекции во всём дереве компонентов.

Современный подход (Angular 15+, в ngKittyDebug — Angular 22): в standalone-приложениях вместо модуля используется provideHttpClient() в ApplicationConfig (app.config.ts). Функционально это тот же HTTP-слой, но с tree-shaking неиспользуемых частей и композицией через feature-функции:

  • withInterceptors([fn1, fn2]) — functional interceptors (HttpInterceptorFn)
  • withXhr() / withFetch() — выбор транспортного бэкенда
  • withXsrfConfiguration() — настройка CSRF-токенов
  • withJsonpSupport(), withRequestsMadeViaParent() — специализированные сценарии
// app.config.ts — ngKittyDebug
provideHttpClient(
  withXhr(),
  withInterceptors([httpErrorInterceptor])
)

Зачем вообще нужен провайдер: HttpClient — не singleton «из коробки»; Angular создаёт его через DI с цепочкой interceptors, JSON-парсером, XSRF и backend-адаптером. Без provideHttpClient / HttpClientModule инъекция HttpClient упадёт с NullInjectorError.

Компромиссы

  • HttpClientModule vs provideHttpClient — модуль тащил весь пакет разом; functional providers подключают только нужное и лучше tree-shakeable.
  • Class interceptors vs HttpInterceptorFn — class-based ещё работают через withInterceptorsFromDi(), но functional проще тестировать (TestBed.runInInjectionContext) и не требуют @Injectable().
  • withXhr vs withFetch — XHR даёт progress events и привычен для SPA; Fetch лучше для SSR/edge и современных платформ. В ngKittyDebug явно выбран XHR — static Netlify SPA без SSR.
Проект: app.config.ts — provideHttpClient(withXhr(), withInterceptors([httpErrorInterceptor])). Глобальный toast об HTTP-ошибках через functional interceptor. Tarot (/api/reading), MyMemory translation и Transloco i18n loader — все через один настроенный HttpClient.

82. Как можно делать HTTP-запросы с помощью HttpClient?

Инжектируем HttpClient через inject(HttpClient) (или constructor DI) и вызываем типизированные методы — get<T>(), post, put, patch, delete, head, options. Каждый метод возвращает cold Observable: сеть не трогается, пока нет subscribe (или пока Observable не «подхвачен» через async pipe / firstValueFrom).

// TarotService — тонкий API-слой
private readonly httpClient = inject(HttpClient);

public loadReading(role = this.role(), intent = this.intent()): Observable<TarotResponseApi> {
  return this.httpClient.get<TarotResponseApi>(this.url, {
    params: { role, intent },
  });
}

Опции запроса:

  • headers — HttpHeaders или plain object
  • params — HttpParams для query string
  • responseType — 'json' | 'text' | 'blob' | 'arraybuffer'
  • observe — 'body' | 'events' | 'response' (progress, full HttpResponse)
  • reportProgress — события загрузки/выгрузки
  • context — HttpContext для метаданных interceptors (opt-out toast, auth skip и т.д.)

Архитектурный паттерн в Angular: компонент не вызывает HttpClient напрямую — только через API service (тонкая обёртка) → facade (orchestration, loading/error signals) → UI. Это упрощает тестирование и переиспользование.

Компромиссы

  • Observable vs Promise — HttpClient возвращает Observable для отмены (unsubscribe), retry и композиции; firstValueFrom — мост к async/await, но теряется lazy/cancel semantics если не аккуратно.
  • Thin service vs fat facade — сервис только HTTP; бизнес-логика (перевод, merge chunks) в facade/service выше. Иначе API-слой раздувается и его сложнее мокать.
  • Dev proxy vs Netlify redirect — в dev proxy.conf.json проксирует /api/reading → deploytarot.com; в prod — redirect в netlify.toml. Один и тот же URL в коде, разная инфраструктура.
Проект: три HTTP-потребителя: TarotService (GET tarot через /api/reading), MyMemoryTranslationService (параллельный перевод чанков через forkJoin + mergeMap), TranslocoHttpLoader (статические JSON /i18n/{lang}.json). Все route-scoped или root, но UI всегда через facade.

83. Можете ли вы объяснить разницу между Observables и Promises в HTTP-запросах?

HttpClient по дизайну возвращает Observable<T>, потому что HTTP в UI — это асинхронная задача с возможностью отмены, повторов и композиции нескольких запросов.

ObservablePromise
Lazy — выполняется при subscribeEager — стартует сразу при создании
0..N значений во времени (observe: 'events')Ровно одно settle-состояние
Отменяется через unsubscribeНе отменяется (обход через AbortSignal)
Богатый pipeline операторов (retry, switchMap, mergeMap)Только then/catch/finally
Multicast через операторы (shareReplay)Один потребитель на chain

Мосты между мирами:

  • firstValueFrom(obs$) / lastValueFrom(obs$) — Observable → Promise (для async/await в guards, resource() loader)
  • from(promise) — Promise → Observable
  • toSignal(obs$) — Observable → signal с auto-unsubscribe
// MainPageFacade — Observable + takeUntilDestroyed
this.tarotService.loadReading().pipe(
  finalize(() => this._isTarotLoading.set(false)),
  takeUntilDestroyed(this.destroyRef)
).subscribe({ next: ..., error: ... });

// PriestQuotesService — Promise в resource() loader
loader: async ({ params: lang, abortSignal }) => this.loadQuotes(lang, abortSignal)

Компромиссы

  • Не конвертируй всё в Promise — при destroy компонента mid-flight запрос продолжит выполняться и может обновить уже уничтоженный UI. Используй takeUntilDestroyed() или async pipe.
  • Observable для одного значения — кажется избыточным, но даёт единый API с progress events и interceptors chain. Resource API (resource()) скрывает Promise-обёртку за signals.
  • RxJS в facade vs signals — в ngKittyDebug HTTP остаётся Observable на границе; результат, loading, error — signals. Чёткое разделение: RxJS для async streams, signals для UI state.
Проект: MainPageFacade — tarot load через Observable + takeUntilDestroyed; translation trigger через effect + subscribe внутри. PriestQuotesService — Firestore через async/await в resource() loader. Два стиля, один принцип: не смешивать без явного моста.

84. Как обрабатывать ошибки во время HTTP-запросов?

Defense in depth — несколько слоёв, каждый со своей ответственностью:

  1. HTTP Interceptor — сквозная UX-логика: глобальный toast, логирование, redirect при 401. Важно: catchError + throwError(() => error) — не глотать, чтобы caller тоже мог обработать.
  2. Service / Facade — маппит HttpErrorResponse в domain error signal или fallback value.
  3. Component — показывает error state из facade; редко ловит HTTP напрямую.
// httpErrorInterceptor — глобальное уведомление, re-throw
return next(request).pipe(
  catchError((error: HttpErrorResponse) => {
    if (request.url.includes('/i18n/')) {
      return throwError(() => error); // без toast
    }
    notificationService.error(`${translocoService.translate(...)} ${toErrorMessage(error)}`);
    return throwError(() => error);
  })
);

// MainPageFacade — доменная обработка
.subscribe({
  error: (err) => {
    this._error.set(err instanceof HttpErrorResponse ? err.message : 'Unknown');
  },
});

HttpErrorResponse содержит: status, statusText, url, error (body), headers. Типизируй через instanceof HttpErrorResponse, не через truthy check.

Операторы RxJS для ошибок: catchError (recovery/fallback), retry({ count, delay }) (только для идемпотентных GET), finalize (loading.set(false) при любом исходе).

Компромиссы

  • Только interceptor — теряется контекст фичи; пользователь видит generic toast, но facade не знает, что показать inline. Нужны оба слоя.
  • catchError в каждом сервисе — дублирование; разделяй: interceptor = UX, facade = domain recovery.
  • Skip i18n в interceptor — осознанное решение ngKittyDebug: отсутствие перевода не должно спамить toast; fallback на default lang достаточен.
  • Firestore errors — не HTTP; обрабатываются в CandlesService / facades через error signals + effect → HotToast (отдельный стек от HTTP).
Проект: httpErrorInterceptor пропускает /i18n/. MainPageFacade различает HttpErrorResponse и unknown errors в error() signal. Translation — per-chunk catchError(() => of(text)) (partial failure), whole-text fallback при полном сбое. toErrorMessage helper — единый формат сообщений.

85. Какие техники оптимизации HTTP и кэширования?

  • Дедупликация запросов — shareReplay(1) для hot shared streams; Resource API автоматически отменяет предыдущий loader при смене params.
  • In-memory cache — Map<key, data> по URL/params/lang; инвалидация при мутации или logout.
  • HTTP cache headers — уважать Cache-Control, ETag; interceptors могут добавлять If-None-Match.
  • Lazy loading routes — loadComponent откладывает загрузку feature chunk до визита на route.
  • Batching / concurrency limit — forkJoin для параллельных независимых запросов; mergeMap(fn, n) для ограничения параллелизма.
  • Prefetch / PreloadingStrategy — кастомная стратегия для вероятных следующих маршрутов.
  • Request cancellation — switchMap отменяет устаревшие запросы; abortSignal в resource() loader.
// PriestQuotesService — Map cache + resource dedup по lang
private readonly cache = new Map<string, PriestQuotesByPool>();

public readonly quotesByPool = resource({
  params: () => this.activeLang(),
  loader: async ({ params: lang, abortSignal }) => {
    if (this.cache.has(lang)) return this.cache.get(lang)!;
    // ... Firestore fetch, cache.set(lang, groupedQuotes)
  },
});

// MyMemoryTranslationService — mergeMap(..., 2) лимит concurrency
from(chunks).pipe(mergeMap((chunk) => this.translateChunk(chunk), 2));

Компромиссы

  • Кэш vs актуальность — stale-while-revalidate: показать кэш, обновить в фоне. Перекэширование user-specific данных после logout — баг.
  • Map cache vs HTTP cache — in-memory быстрее, но теряется при refresh; HTTP cache headers работают между сессиями, но сложнее инвалидировать.
  • mergeMap без лимита — 100 параллельных HTTP → rate limit API и исчерпание browser connection limit (~6 на origin). В проекте: concurrency 2 для MyMemory.
  • Resource vs shareReplay — Resource встроенно управляет reload/cancel; shareReplay требует ручной инвалидации и осторожности с memory leaks (refCount).
Проект: PriestQuotesService — Map<lang, quotes> перед Firestore + resource() с params по activeLang. MyMemoryTranslationService — чанки 500 байт с mergeMap(..., 2). UserStateStrategy — selective preloading auth/guest routes. Tarot — без кэша (каждый draw уникален).

86. Какова цель HttpInterceptor и как он работает?

HttpInterceptor — middleware между вашим кодом и сетью. Каждый interceptor получает (req, next) и возвращает Observable<HttpEvent<unknown>>. Вызов next(req) передаёт запрос дальше по цепочке; изменять req только через req.clone({...}) — request immutable.

Типичные задачи interceptors:

  • Добавление auth headers (Bearer token)
  • Глобальная обработка ошибок (toast, logging)
  • Retry на 503 / network errors
  • Base URL prefixing
  • Loading indicator (start/stop)
  • Request/response logging (dev only)

Современный стиль (Angular 15+): HttpInterceptorFn — обычная функция с inject() для зависимостей. Регистрация через withInterceptors([fn1, fn2]). Порядок важен: первый в массиве обрабатывает исходящий запрос первым, входящий ответ — последним (стек).

export const httpErrorInterceptor: HttpInterceptorFn = (request, next) => {
  const notificationService = inject(HotToastService);
  const translocoService = inject(TranslocoService);

  return next(request).pipe(
    catchError((error: HttpErrorResponse) => {
      // ... toast logic
      return throwError(() => error);
    })
  );
};

Компромиссы

  • Functional vs class interceptors — functional проще unit-тест (runInInjectionContext), нет boilerplate @Injectable. Class interceptors через withInterceptorsFromDi() — для legacy libs.
  • Один fat interceptor vs несколько маленьких — разделение по concern (auth, error, logging) проще поддерживать, но больше overhead на chain.
  • Interceptor vs facade error handling — interceptor для cross-cutting UX; facade для domain-specific recovery. Не дублируй toast в обоих местах без opt-out механизма.
Проект: один functional interceptor httpErrorInterceptor в app.config.ts. Инжектит HotToastService + TranslocoService для локализованного toast. Фильтрует /i18n/ URL — i18n failures silent на UX-уровне.

87. В каких сценариях interceptor для обработки ошибок?

Хорошо подходит для interceptor:

  • Глобальный toast/snackbar на любую HTTP-ошибку
  • Централизованное логирование в Sentry/Datadog
  • 401 Unauthorized → logout + redirect на login
  • 503 → retry с exponential backoff
  • Нормализация формата ошибки (API возвращает разные shapes)

Плохо подходит для interceptor:

  • Feature-specific validation messages («email уже занят» на register vs «неверный пароль» на login)
  • Ошибки, которые на одном экране глотаются (fallback value), а на другом показываются
  • Бизнес-логика принятия решений (retry vs show form error)
  • Non-HTTP errors (Firestore, WebSocket) — другой стек

Opt-out механизмы:

  • HttpContext token — req.context.set(SKIP_ERROR_TOAST, true)
  • URL pattern filtering — как в ngKittyDebug для /i18n/
  • Separate HttpClient instance без interceptors (редко, для edge cases)

Компромиссы

  • Global toast vs inline error — toast хорош для unexpected errors; expected validation errors лучше inline в форме. Interceptor не знает контекст — нужен opt-out.
  • Re-throw vs swallow — interceptor должен re-throw после toast, иначе facade не узнает об ошибке и UI останется в loading state.
  • Interceptor vs ErrorHandler — в ngKittyDebug сознательно ушли от global ErrorHandler к interceptor + facade signals: более предсказуемый UX, меньше «ловушек» для non-HTTP errors.
Проект: httpErrorInterceptor — toast для всех HTTP errors кроме /i18n/. Firestore errors в CandlesService → error() signal → AltarPageFacade effect → HotToast (отдельный путь, не через HTTP interceptor). Два стека ошибок — осознанное разделение transport vs domain persistence.

88. Как обрабатывать аутентификацию через HTTP-интерсепторы?

Классический паттерн REST + JWT:

export const authInterceptor: HttpInterceptorFn = (req, next) => {
  const token = inject(AuthService).getToken();
  if (!token) return next(req);
  return next(req.clone({
    setHeaders: { Authorization: `Bearer ${token}` }
  }));
};

Auth (кто ты): interceptor прикрепляет token/cookie к каждому API-вызову автоматически — UI-код не думает об headers.

Authorization (что тебе можно): обычно на сервере; на клиенте — route guards (canMatch, canActivate) блокируют маршруты, а не interceptors. Interceptor обрабатывает 401/403 глобально (logout, redirect).

Refresh token flow: interceptor ловит 401 → вызывает refresh endpoint → retry original request с новым token. Осторожно с infinite loops и concurrent requests during refresh (queue pattern).

Компромиссы

  • Firebase Auth vs Bearer JWT — Firebase SDK управляет tokens internally; Firestore/Auth calls не через HttpClient → auth interceptor не нужен. Guards (authGuard, guestGuard) достаточны для UI protection.
  • Interceptor vs per-request header — interceptor DRY для REST API; для mixed auth (some endpoints public) нужен HttpContext skip token.
  • Client-side guards ≠ security — guards только скрывают UI; реальная authZ на сервере/Firestore rules. На собеседовании важно это проговорить.
Проект: Firebase Auth через SDK (AuthService.initialize() в provideAppInitializer), не Bearer headers. authGuard / guestGuard как CanMatchFn с inject(AuthService) — защита маршрутов altar, shrift, profile, sanctum. HTTP interceptor в проекте — только error toast, не auth. Firestore security rules — server-side authZ.

91. Что такое TestBed?

TestBed — изолированная среда Angular для тестов: компилятор шаблонов + DI-контейнер (Component testing basics). По сути mini-приложение для одного теста.

Основной workflow:

  1. TestBed.configureTestingModule({ imports, providers }) — конфигурация как mini-app
  2. await TestBed.compileComponents() — компиляция шаблонов (нужно при templateUrl)
  3. TestBed.createComponent(MyComponent) или TestBed.inject(MyService)
  4. fixture.detectChanges() — запуск change detection
beforeEach(() => {
  TestBed.configureTestingModule({
    imports: [TranslocoTestingMock],
    providers: [
      AltarPageFacade,
      { provide: CandlesService, useValue: candlesServiceMock },
      { provide: HotToastService, useValue: hotToastServiceMock },
    ],
  });
  facade = TestBed.inject(AltarPageFacade);
});

Продвинутые API:

  • TestBed.overrideComponent() — подменить template/providers конкретного компонента
  • TestBed.runInInjectionContext(() => ...) — тест functional guards/interceptors/resolvers с inject()
  • TestBed.tick() — flush signal effects (Angular 19+)
  • TestBed.flushEffects() — выполнить все pending effects синхронно

Компромиссы

  • configureTestingModule в beforeEach — каждый тест получает чистый injector; не кэшируй config с mutable state между тестами.
  • TestBed vs pure unit — validators/pipes тестируй без TestBed (быстрее); facades/components — с TestBed для DI.
  • compileComponents async — добавляет latency; для standalone components с inline templates часто не нужен.
Проект: facade specs используют минимальный TestBed config: только facade + mocked dependencies + TranslocoTestingMock. Guards тестируются через TestBed.runInInjectionContext(() => authGuard(...)). resetCandlesServiceMock() / resetUiStateStoreMock() — сброс shared mock state в beforeEach.

92. Как тестировать компоненты с ComponentFixture и DebugElement?

  • detectChanges() — запускает CD для этого компонента и детей (OnPush/signals)

93. Как тестировать директивы и пайпы?

Pure pipes — тестируй как обычную функцию, TestBed не нужен:

const pipe = new MachineSpiritStatePipe();
expect(pipe.transform(5)).toBe('pleased');

Pure pipe пересчитывается только при изменении input reference — важно для performance-aware tests.

Impure pipes — вызываются каждый CD cycle; тестируй через component fixture или проверяй pure: false в metadata.

@Component({
  template: '<div ngKittyScanEffect>content</div>',

})

const fixture = TestBed.createComponent(HostComponent);

Компромиссы

  • Pure pipe без TestBed — быстрый unit-тест функции transform, но не проверяет binding и CD в шаблоне.
  • Host component для directive — реалистичный DOM-контекст, но больше setup, чем тест одной функции.

97. Как обеспечить изоляцию тестов?

Тесты должны быть детерминированными и не влиять друг на друга:

  • Свежий TestBed — beforeEach с новой конфигурацией; afterEach(() => TestBed.resetTestingModule()) при кастомных override
  • HTTP cleanup — httpMock.verify() в afterEach: нет незавершённых запросов
  • Mocks reset — resetCandlesServiceMock(), vi.clearAllMocks() / mockReset() в beforeEach
  • No shared mutable state — не мутируй singleton mocks без restore; writable signals создавай per-test
  • Random/time — vi.setSystemTime() для date-dependent logic (spirit decay timers)
  • DOM cleanup — Vitest/jsdom изолирует; при manual DOM append — cleanup в afterEach

Arrange-Act-Assert — один logical scenario на тест; несколько expect ok, если проверяют один flow.

Typed mocks — satisfies MockedObject<Partial<T>> ловит drift API при refactor сервиса.

Компромиссы

  • Shared mock objects vs factory — shared быстрее писать, но требует explicit reset; factory (createCandlesServiceMock()) безопаснее, но verbose.
  • Integration tests — реальные сервисы медленнее, но ловят wiring; unit с mocks быстрее, но mocks могут врать.
  • Root singleton override — providedIn: 'root' services нужно явно override в TestBed providers, иначе тесты делят state.

98. Что такое Angular Signals?

Signals — reactive primitive в Angular 16+ (stable с Angular 19): синхронное реактивное состояние с fine-grained dependency tracking. Основа state model современного Angular.

Ключевые API:

  • signal(initial) — writable state container
  • computed(() => ...) — derived state, кэшируется, пересчитывается только при изменении deps
  • linkedSignal() — writable derived, сбрасывается при изменении source signal
  • effect(() => ...) — side effects (DOM sync, logging, subscriptions)
  • resource() / rxResource() — async data loading с built-in loading/error/status

Как работает: чтение signal (count()) в computed/template/effect регистрирует dependency. При set/update Angular помечает только зависимые views/computed как dirty — не full tree change detection scan.

Signals интегрированы в templates ({{ count() }}), component inputs (input()), router (component input binding), forms (experimental signal forms), NgRx Signals (signalStore).

Компромиссы

  • Signals vs RxJS — signals для sync/reactive UI state; RxJS для event streams, HTTP, complex async pipelines. Не заменяют друг друга — дополняют.
  • Signals vs BehaviorSubject — signals синхроннее, проще API, встроены в CD; BehaviorSubject — multicast, cold/hot semantics, богаче operators.
  • Migration cost — legacy @Input/@Output + OnPush + async pipe работают; signals — opt-in постепенно. ngKittyDebug — signals-first с первого спринта.
Проект: signals everywhere — CandlesService (candleCounts, litCandleList, spiritSatisfaction, error), MainPageFacade (loading, result, error, linkedSignal), uiStateStore (NgRx Signals signalStore для theme/language), TarotService (role, intent signals). Facades expose asReadonly() public API.

99. Как читать и изменять значение signal?

const count = signal(0);

count();              // read — возвращает текущее значение
count.set(5);         // replace — полная замена
count.update(v => v + 1);  // mutate based on current value
count.mutate(arr => arr.push(item)); // in-place mutate для objects/arrays

Read — вызов как функции signal(). В computed/template/effect создаёт dependency edge. Вне reactive context — просто читает snapshot без tracking.

Write — только через set, update, mutate. Прямое присваивание (count = 5) не работает — signal это функция-обёртка.

Readonly wrapper: private readonly _error = signal(null); public readonly error = this._error.asReadonly(); — внешний код может read, но не write. Стандартный паттерн facades/services.

Signal types: WritableSignal<T>, Signal<T> (readonly), ComputedSignal<T> (derived, no write).

Компромиссы

  • set vs update — set когда знаешь новое значение целиком; update когда нужен previous value (increment, toggle).
  • mutate vs update — mutate для in-place изменения objects/arrays (performance); но иммутабельный update безопаснее для change detection debugging.
  • Public writable vs asReadonly — never expose writable signals from facades; UI только reads через readonly/computed.
Проект: CandlesService — _candleCounts.set(...), candleCounts.asReadonly() для UI. MainPageFacade — _sourceResult.set(tarotResponse) triggers linkedSignal reset. TarotService.role.set(TarotRole.QA) — writable signals для user input state.

100. Какова основная выгода signals вместо примитивов?

Проблема с примитивами в class:

// ❌ Change detection не знает об изменении
class MyComponent {
  count = 0;
  increment() { this.count++; } // UI может не обновиться с OnPush
}

Без signals/Zones/ChangeDetectorRef.markForCheck Angular не отслеживает, что count изменился. Нужен Zone.js patch, manual markForCheck, или immutable object replacement.

Signal решает это:

// ✅ Framework отслеживает reads и updates
count = signal(0);
increment() { this.count.update(v => v + 1); }
// Template: {{ count() }} — автоматически обновляется
  • Fine-grained reactivity — обновляются только views, прочитавшие этот signal
  • Computed caching — computed(() => expensiveCalc(this.a(), this.b())) пересчитывается только при изменении deps
  • Explicit data flow — видно, что reactive (count() в template), а что static
  • Path to zoneless — signals + events trigger updates без Zone.js monkey-patching

Компромиссы

  • Signals не заменяют RxJS — для event streams, HTTP, debounce, merge — RxJS; signals — sync UI state.
  • Syntax overhead — count() vs count в template; но explicitness — feature, не bug.
  • Interop с legacy — toSignal(obs$) / toObservable(signal) — мост, но добавляет complexity на границах.
Проект: facades expose readonly loading = this._loading.asReadonly(), readonly isLoading = computed(() => tarotLoading() || translationLoading()). CandlesService.totalOfferings — computed от candleCounts. OnPush default в Angular 22 + signals = minimal CD overhead.

102. Как подписаться на signal?

Signals не имеют subscribe API — это не Observable. «Подписка» на изменения signal:

СпособНазначение
effect(() => { ... signal(); })Side effects при изменении
computed(() => ...)Derived state (preferred over effect for data)
Template {{ signal() }}View binding — auto-updates
toObservable(signal)Bridge signal → Observable для RxJS pipeline
// ❌ signal.subscribe() — не существует

// ✅ effect для side effects
effect(() => {
  const err = this.candlesService.error();
  if (err) this.toast.error(toErrorMessage(err));
});

// ✅ computed для derived data
isLoading = computed(() => this._tarotLoading() || this._translationLoading());

// ✅ toObservable для RxJS interop
langChanges$ = toObservable(this.uiStateStore.language);

Обратный мост: toSignal(obs$) — Observable → signal с auto-unsubscribe при destroy.

Компромиссы

  • effect vs computed — derived data только через computed; effect — для side effects (DOM, logging, subscriptions). Мутация signals в effect → risk circular updates.
  • toObservable overhead — создаёт Observable wrapper; используй только на границе с RxJS code, не для каждого signal.
  • Manual subscribe on toObservable — нужен unsubscribe или takeUntilDestroyed; prefer effect/computed в Angular code.
Проект: AltarPageFacade — effect на CandlesService.error() → HotToast. MainPageFacade — effect на _sourceResult + activeLang → translation subscribe. PriestQuotesService — toSignal(translocoService.langChanges$) для bridge lang → resource params.

103. Можно ли читать signal из computed без создания зависимости? (untracked)

Да — untracked(() => otherSignal()) внутри computed или effect. Читает current value без регистрации dependency — computed/effect не пересчитается при изменении untracked signal.

total = computed(() => {
  const items = this.items();           // dependency ✓
  const multiplier = untracked(() => this.config().multiplier); // no dependency ✗
  return items.length * multiplier;
});

effect(() => {
  const current = this.count();
  const previous = untracked(() => this.previousCount()); // read without tracking
  if (current !== previous) console.log(`${previous} → ${current}`);
  this.previousCount.set(current);
});

Use cases:

  • Logging/debugging — прочитать value без trigger recompute
  • Compare with previous value
  • Read config/metadata that shouldn't trigger derived recalculation
  • Break circular dependencies между effects

Компромиссы

  • untracked vs separate computed — если value должна быть reactive dependency — не используй untracked; это opt-out, не default.
  • Staleness risk — untracked value может быть stale в computed; осознанный trade-off для performance или decoupling.
  • Overuse — если computed не пересчитывается когда должен — проверь, не untracked ли нужный signal.
Проект: untracked пока не используется явно в ngKittyDebug — паттерн для interview и edge cases. Альтернатива в проекте: разделение concerns через отдельные computed (isLoading от двух loading signals) вместо untracked reads.

104. Обнаружение изменений signal с использованием API effect()

effect((onCleanup) => {
  const lang = store.language();
  const subscription = translocoService.load(lang).subscribe(() => {
    translocoService.setActiveLang(lang);
  });
  onCleanup(() => subscription.unsubscribe());
});

effect() — регистрирует side effect, который re-runs при изменении любого прочитанного signal:

  • Выполняется после change detection (scheduling: sync или microtask)
  • Tracking: все signal reads внутри effect body → dependencies
  • onCleanup(fn) — вызывается перед re-run и при destroy; для unsubscribe, clear timers
  • allowSignalWrites: true — opt-in для записи signals внутри effect (default: forbidden in dev mode)

Rules of effects:

  1. Не мутируй unrelated signals в effect → circular updates. Derived state — через computed.
  2. Subscriptions/timers — всегда cleanup через onCleanup.
  3. Effects не должны быть единственным источником truth — они react, not act.

Компромиссы

  • effect vs computed — если результат effect — data для UI, это должен быть computed. Effect — для imperative side effects.
  • effect vs ngOnInit subscribe — effect auto-tracks deps и re-runs; manual subscribe нужен unsubscribe и ngOnChanges-like logic.
  • Testing effects — TestBed.flushEffects() / TestBed.tick(); не полагайся на timing без flush.
Проект: uiStateStore — три effects в withHooks.onInit: sync profile → store state, sync theme → ThemeService/DOM, sync language → Transloco load + setActiveLang (с onCleanup unsubscribe). AltarPageFacade — effect на CandlesService.error() → HotToast. MainPageFacade — effect на tarot result + lang → translation pipeline.

105. Какова связь между signals и обнаружением изменений?

Классический Angular CD: Zone.js патчит async APIs → trigger full tree check (или subtree с OnPush + immutable inputs). Дорого на больших apps.

Signals + CD:

  1. Template/control flow reads signals → view records dependency graph
  2. Signal change → помечает только dependent views as dirty
  3. CD runs только для dirty views — не full tree walk
  4. OnPush default (Angular 22) работает naturally с signals

linkedSignal — writable derived signal, сбрасывается при изменении source:

// MainPageFacade — сброс tarot result при смене role/intent
private readonly _sourceResult = linkedSignal<TarotResponseApi | null>(() => {
  this.role();    // deps
  this.intent();
  return null;  // reset value when deps change
});

Path to zoneless: provideExperimentalZonelessChangeDetection() (Angular 18+) — signals + DOM events trigger updates без Zone.js (~30KB savings). ngKittyDebug пока на Zone (provideZoneChangeDetection({ eventCoalescing: true })), но architecture signals-first готов к migration.

Компромиссы

  • Signals + Zone — работают вместе сейчас; Zone — safety net для non-signal code (RxJS subscribe callbacks). Zoneless требует audit всех async paths.
  • linkedSignal vs manual reset — linkedSignal declarative; manual effect(() => { role(); result.set(null); }) — imperative, risk bugs.
  • Async pipe still works — не нужно мигрировать все Observables; signals и async pipe coexist.
Проект: MainPageFacade.linkedSignal — auto-reset tarot при смене role/intent. CandlesService computed (totalOfferings, isSpiritPleased) — derived без manual CD. provideZoneChangeDetection({ eventCoalescing: true }) — coalesced events пока Zone active.

108. Опишите новые возможности @if, @for, @switch, @defer.

Built-in control flow (Angular 17+) — заменяет structural directives из CommonModule (*ngIf, *ngFor, *ngSwitch). Компилируется в optimized instructions, лучше tree-shaking.

@if (isLoading()) {
  <ngKitty-spinner />
} @else if (error()) {
  <p>{{ error() }}</p>
} @else {
  <ngKitty-tarot-reading [result]="result()" />
}

@for (candle of candleList(); track candle.id) {
  <ngKitty-candle [candle]="candle" />
} @empty {
  <p>Нет свечей</p>
}

@switch (role()) {
  @case (TarotRole.DEVOPS) { <span>DevOps</span> }
  @case (TarotRole.QA) { <span>QA</span> }
  @default { <span>Unknown</span> }
}
