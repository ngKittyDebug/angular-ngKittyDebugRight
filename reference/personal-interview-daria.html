S0 Старт проекта и роль тимлида

Что делала

  • Инициализировала Angular 22 workspace: standalone, strict TS, префикс ngKitty.
  • Настроила path aliases (@core/*, @features/*, @shared/*) — импорты предсказуемы при росте фич.
  • Добавила withComponentInputBinding() в роутер — route params напрямую в signal inputs.
  • Netlify: static SPA + redirect /api/reading → tarot API.
  • CI: quality-check с typecheck, lint, test, build.
  • Написала docs/Стайлгайд архитектура проекта.md — feature / core / shared, facade pattern, однонаправленные зависимости.

Почему feature-based + facade, а не «всё в компонентах»

  • Page-компонент только собирает UI; бизнес-логика в facade/service → проще тестировать без DOM.
  • core не зависит от features — shared domain (CandlesService, ConfessService) переиспользуется altar/shrift/profile.
  • Route-scoped providers для feature API/facade — инстанс живёт с маршрутом, не засоряет root injector.
  • Альтернатива «smart/dumb везде без facade» — на 5+ фичах дублируется loading/error/toast в каждом компоненте.

Что сказать на собеседовании

«As team lead I defined the architecture contract: features own UI + facade + data, core holds cross-cutting services like auth and candles. We use route-level providers so facades are scoped to pages. This let us onboard two other developers without everyone inventing their own state pattern.»

S1–2 Алтарь — CandlesService и интерактивный UI

Что делала

  • Собрала фичу altar целиком: страница, prayer, instructions, statistics, candle component.
  • Drag-and-drop свечей на алтарь → зажигание, анимации wick/flame, таймер затухания.
  • CandlesService в core/ — shared domain: счётчики свечей, список горящих, «удовлетворённость Духа Машины».
  • Persist в Firestore users/{uid}.candleCounts + spirit satisfaction; загрузка при смене пользователя через effect.
  • Decay: timer + effect(onCleanup) периодически снижает уровень благословения — геймификация без отдельного backend.
  • Computed: totalOfferings, blessingLevel, isSpiritPleased — UI только читает сигналы.
  • Machine spirit state в header — связка altar → layout через сервис и pipe.

Технический поток (end-to-end)

User drag candle → CandlesService.offerCandle()
  → optimistic update signals (_litCandleList, _candleCounts)
  → increaseSpiritSatisfaction()
  → setDoc Firestore (withTimeout 7s)
  → on error: _error signal → AltarPageFacade effect → HotToast

Почему signals + effect, а не NgRx store для свечей

  • Состояние локально для домена «свечи», не нужен time-travel и middleware — signal + computed проще и быстрее в Angular 22.
  • effect для sync с UserProfileService.user() — реактивная перезагрузка при login/logout без подписок в компонентах.
  • Decay через timer в effect с onCleanup — автоматическая отписка при destroy / level 0; альтернатива setInterval в компоненте — утечки и дубли при OnPush.
  • CandlesService в core, не в features/altar — profile и header тоже читают blessing level без circular imports.

Почему withTimeout на Firestore, а не бесконечный loading

  • Firestore SDK не даёт встроенного deadline на getDoc/setDoc — при плохой сети UI зависал.
  • withTimeout(promise, 7000) — reject с понятным сообщением → error signal → toast.
  • Альтернатива global loading spinner — пользователь не понимает, что зависло; toast + сброс error точечнее.

Что сказать на собеседовании

«I built the altar as a signals-first domain service. CandlesService owns all candle state, syncs to Firestore when the user profile changes, and runs a decay timer for the Machine Spirit satisfaction meter. The UI is dumb — it calls facade methods and binds to readonly signals. I chose effects over manual subscriptions because cleanup is automatic and it fits Angular 22 defaults.»

S3 Санктум — ритуал, RxJS timeline, Resource API

Что делала

  • Новая фича sanctum: суд над git-веткой, litany построчно, вердикт, digital priest.
  • createRitualTimelineStream — merge нескольких timer + map: каждая строка litany появляется с задержкой, затем verdict.
  • SanctumRitualService оборачивает поток в rxResource — loading/error/reload из коробки, UI читает ritualSession.value().
  • Звук: SanctumSoundService + Web Audio (organ tones); unlock AudioContext на user gesture.
  • PriestQuotesService — resource() с loader по языку Transloco, in-memory cache per lang, Firestore withTimeout.
  • Рефакторинг: digital priest из shared в feature, domain layer branch judgment, тесты + mocks.
// Упрощённо: timeline = merge построчных событий + финальный verdict
createRitualTimelineStream(request) {
  const judgment = analyzeBranch(branch, spiritLevel, intent);
  const lineEvents = judgment.litany.map((line, i) =>
    timer((i + 1) * DELAY).pipe(map(() => ({ litanyLines: slice(0, i+1), judgment: null })))
  );
  const verdictEvent = timer(totalDelay).pipe(map(() => ({ litanyLines, judgment })));
  return merge(...lineEvents, verdictEvent);
}

Почему RxJS timeline, а не setTimeout в компоненте

  • Декларативное расписание: merge + timer описывает «когда какое состояние» — легко менять DELAY в config без переписывания imperative кода.
  • Поток cold: каждый новый ritual = новая подписка через rxResource — нет гонок от старых таймеров.
  • tap для звука рядом с событиями — side effects отделены от state mapping.
  • Альтернатива async/await + sleep в цикле — сложнее отменить при уходе со страницы; rxResource отменяет stream при смене params.

rxResource vs ручной signal loading/error

  • rxResource даёт status, value, error, перезапуск при смене params — меньше boilerplate чем три сигнала вручную.
  • requestId в RitualRequest — форсирует reload даже при тех же branch/intent (повторный ритуал).
  • Для Firestore quotes — resource() (Promise loader), для анимации ритуала — rxResource (Observable stream): правильный примитив под тип async.

Что сказать на собеседовании

«Sanctum ritual is an Observable timeline: each litany line is a timed emission merged into one stream. I wrapped it in rxResource so the page gets loading state and cancellation for free. Priest quotes use the Promise-based resource API with language as params and a Map cache — we don't refetch Firestore on every line of litany. Sound is synchronized via tap on the same stream, not separate timers.»

S4 Обработка ошибок — единый стек

Что делала

  • httpErrorInterceptor (functional) — все HTTP ошибки → HotToast; исключение /i18n/ (иначе двойной шум при смене языка).
  • toErrorMessage — нормализация HttpErrorResponse / Error / unknown в строку для toast.
  • withTimeout — обёртка Promise для Firestore с 7s deadline.
  • Firestore ошибки не в interceptor — в facade через effect на service.error или try/catch в методах (shrift, altar, sanctum, auth).
  • Создала AltarPageFacade с toast на ошибки CandlesService — эталон для остальных фич.
  • Отказалась от глобального ErrorHandler для UX-ошибок — пользователю нужен контекст фичи, не generic crash screen.
// HTTP — централизованно
httpErrorInterceptor → catchError → HotToast → rethrow

// Firestore — контекст фичи
CandlesService._error.set(err) → AltarPageFacade effect → toast с ключом 'altar'
ShriftPageFacade try/catch on addSin/deleteSin → toast с ключом 'shrift'

Почему два канала (HTTP interceptor vs facade), а не один global handler

  • HTTP и Firestore — разные источники: interceptor видит только HttpClient; Firebase SDK бросает в Promise, не через HTTP pipeline.
  • Текст toast с контекстом фичи (notifications.failure + scope altar/shrift) — пользователь понимает, где сломалось.
  • Rethrow после toast в interceptor — facade/main может ещё выставить локальный error state для empty UI.
  • Global ErrorHandler хорош для непойманных исключений, но плох как единственный UX для ожидаемых сетевых сбоев.

Почему HotToast вместо TuiNotificationService

  • Единый glassmorphism стиль, stack, auto-dismiss — меньше кастомной вёрстки в каждой фиче.
  • Проще мокать в тестах facades (HotToastService stub).
  • Taiga остаётся для форм и layout — уведомления вынесены в специализированную библиотеку.

Что сказать на собеседовании

«We split errors by transport: HttpClient goes through a functional interceptor with i18n skip for translation files. Firebase operations use shared toErrorMessage and withTimeout helpers, but toasts are shown at the facade layer so the message includes feature context. I explicitly rejected a single global handler for user-facing network errors because altar and shrift need different copy and recovery flows.»

S4 Формы, валидация, уведомления

Что делала

  • tuiValidationErrorsProvider в app.config.ts — все тексты ошибок Taiga форм через Transloco (required, minlength, pattern password/email, confirmPassword).
  • Рефактор login/register: tui-error привязан к конкретному FormControl, не к форме целиком.
  • Миграция с TuiNotification на @ngxpert/hot-toast в auth facades и по проекту.
  • Profile form: error handling на полях (совместно с командой).
  • @Service() decorator — единообразное объявление injectable классов в Angular 22.

Почему tuiValidationErrorsProvider глобально, а не строки в шаблоне

  • Один словарь VALIDATION_ERRORS_DICT + i18n — смена языка меняет все формы без дублирования ключей в HTML.
  • Password pattern получает контекст min/max length из констант — DRY с валидатором.
  • tui-error на control level — показывается только затронутое поле; альтернатива одна ошибка на форму — хуже UX на register с confirm password.

Что сказать на собеседовании

«I centralized reactive form error messages in tuiValidationErrorsProvider with Transloco, so login, register, and profile share the same validation copy. Each field uses tui-error bound to its FormControl — users see errors next to the input. For async auth failures we use HotToast in the facade, not field validators, because those are server-side errors.»

S4 Тестирование — моки и facade specs

Что делала

  • Расширила покрытие: auth, confess, candles, theme, layout, shrift UI, ghost-coder, form facades.
  • Инфраструктура моков: *.service.mock.ts, reset helpers, расширенный Firebase auth/Firestore mock.
  • Facade-тесты проверяют оркестрацию (toast на error, вызов service), не детали Firestore.
  • Vitest + isolation в angular.json — быстрые unit без поднятия всего приложения.
  • CI build step в quality-check — ловит budget/regression до merge.

Почему тестируем facade, а не компонент с реальным Firestore

  • Facade — публичный API страницы; мок CandlesService/ConfessService → тест стабилен без emulator.
  • Component test оставляем для binding и Taiga; бизнес-сценарий «error → toast» — в facade spec (altar-page.facade.spec.ts).
  • Альтернатива e2e на каждый toast — медленно для учебного проекта; unit facade даёт 80% уверенности за секунды.

Что сказать на собеседовании

«I added shared service mocks and facade unit tests. We test error-to-toast wiring in AltarPageFacade by setting error on a mock CandlesService and asserting HotToast was called — no Firebase emulator needed. TestBed uses route-scoped providers mirroring production.»

Shared UX — scan effect, i18n, тема

Что делала

  • ScanEffectDirective — host binding, CSS variables, prefers-reduced-motion в SCSS; навешен на app.component для атмосферы CRT.
  • uiStateStore (NgRx Signals): theme + language, sync с Firestore users/{uid}.uiState, effects на Transloco и ThemeService.
  • i18n ключи для machine spirit, altar, sanctum, crystal ball route.
  • Тема light/dark через Taiga tuiTheme на root.

Почему directive на root, а не CSS в каждой фиче

  • Один host class scan-effect — DRY; фичи не знают про эффект.
  • Signal inputs (scanEnabled, scanDuration) — можно отключить на reduced-motion или в settings позже.
  • uiStateStore в root — язык/тема глобальны; persist только для authenticated user через UserProfileService.

★ Готовые ответы — типовые вопросы интервью о проекте

«Расскажи о самой сложной задаче»

Situation: Sanctum — многосоставной UX: форма, пошаговая litany, вердикт, звук, цитаты священника из Firestore, зависимость от spirit level с алтаря.

Task: Свести всё в предсказуемый state flow без spaghetti setTimeout и без дублирования loading/error.

Action: Вынесла timeline в чистую RxJS функцию, обернула в rxResource, quotes — в resource() с кэшем по языку, звук в tap. Facade отдаёт UI только computed signals.

Result: Повторный ритуал работает через requestId, отмена при уходе со страницы, тесты на stream и facade, bundle budgets подняты осознанно.

«Как у вас устроен state management?»

«Мы не тащим один NgRx на всё. Глобально — uiStateStore на NgRx Signals для темы и языка. Feature state — signals в сервисах (CandlesService, ConfessService) или rxResource/resource в sanctum. UI не ходит в Firestore напрямую: только facade → service. Так проще тестировать и не смешивать HTTP и Firebase error paths.»

«Почему Angular 22 / signals?»

«Проект стартовал на Angular 22 с OnPush по умолчанию. Signals дают явный граф зависимостей: computed для производных значений (blessing level, isJudging), effect для side effects (persist, decay, toast). Меньше async pipe в шаблонах для локального UI state. RxJS остаётся для event streams и HTTP, мост через rxResource и takeUntilDestroyed.»

«Что бы ты улучшила сейчас?»

«Profile feature ещё WIP — нужен полноценный ProfilePageFacade по образцу altar. Altar сейчас частично вызывает CandlesService из facade, можно довести до 100% facade API. Для Firestore — рассмотреть centralized retry policy, но без потери контекстных toast. Добавить @defer на тяжёлые sanctum chunks если bundle вырастет.»

Почему этот ответ силён

Показываешь зрелость: знаешь tech debt, но можешь объяснить почему не сделала в спринте (приоритет error stack и sanctum).

«Как ты работала в команде как тимлид?»

«Я задала архитектурный стайлгайд и паттерн facade + error handling, ревьюила PR, мержила в develop. Фичи распределены: я — altar, sanctum, инфраструктура ошибок; коллеги — profile, части shrift/main. Общие сервисы в core, чтобы не было copy-paste Firestore логики. Документация в docs/ и README синхронизирована с реальным кодом.»
