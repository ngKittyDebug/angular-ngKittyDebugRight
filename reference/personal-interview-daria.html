S0 Старт проекта и роль тимлида

Что делала

  • Инициализировала Angular 22 workspace: standalone, strict TS, префикс ngKitty.
  • Настроила path aliases (@core/*, @features/*, @shared/*) — импорты предсказуемы при росте фич.
  • Добавила withComponentInputBinding() в роутер — route params напрямую в signal inputs.
  • Netlify: static SPA + redirect /api/reading → tarot API.
  • CI: quality-check с typecheck, lint, test, build.
  • Написала docs/Стайлгайд архитектура проекта.md — feature / core / shared, facade pattern, однонаправленные зависимости.

Почему feature-based + facade, а не «всё в компонентах»

  • Page-компонент только собирает UI; бизнес-логика в facade/service → проще тестировать без DOM.
  • core не зависит от features — shared domain (CandlesService, ConfessService) переиспользуется altar/shrift/profile.
  • Route-scoped providers для feature API/facade — инстанс живёт с маршрутом, не засоряет root injector.
  • Альтернатива «smart/dumb везде без facade» — на 5+ фичах дублируется loading/error/toast в каждом компоненте.

Что сказать на собеседовании

«As team lead I defined the architecture contract: features own UI + facade + data, core holds cross-cutting services like auth and candles. We use route-level providers so facades are scoped to pages. This let us onboard two other developers without everyone inventing their own state pattern.»

S1–2 Алтарь — страница, UI и CandlesService

Что делала

  • CandlesService в core/services/candles — shared domain (altar + header + sanctum spirit level + будущий profile).
  • Модели и конфиги: типы свечей, CandleCounts, spirit satisfaction, константы decay/extinguish.
  • Анимации wick/flame, responsive layout алтаря, statistics с total offerings и blessing level.
  • Позже (S4): AltarPageFacade с effect на CandlesService.error() → HotToast; Firestore через withTimeout(7s).
  • MachineSpiritStatePipe + isSpiritPleased в header через LayoutService — алтарь влияет на chrome всего приложения.

  providers: [provideTranslocoScope('altar'), AltarPageFacade]

Технический поток подношения свечи

Drag / click / Enter → CandlesComponent.offerCandle()
  → emit candleListChanged
  → AltarPageFacade.offerCandle() → CandlesService.offerCandle()

CandlesService:
  1. Сразу добавить LitCandle в _litCandleList (визуал «горит»)
  2. timer(CANDLE_EXTINGUISH_TIME) + takeUntilDestroyed
  3. completeOffering():
     - убрать из lit list
     - increment candleCounts + increaseSpiritSatisfaction
     - если user logged in → setDoc Firestore (merge, withTimeout)
     - если guest → только local state
     - при ошибке Firestore → rollback counts/spirit, _error.set(err)

Почему двухфазное подношение (горит → затухает → persist), а не сразу increment

  • UX: пользователь видит ритуал — свеча горит несколько секунд, потом гаснет и засчитывается в statistics.
  • Counts не меняются до завершения таймера — нельзя «накликать» 10 свечей за секунду в статистике.
  • Один timer на instanceId через takeUntilDestroyed — при destroy сервиса таймеры не утекают.
  • Альтернатива «сразу persist» — меньше магии, но теряется игровой feedback и сложнее откатывать визуал при ошибке.

Почему dumb CandlesComponent + fat CandlesService, а не всё в компоненте

  • CDK и a11y остаются в UI; Firestore, decay, rollback — в сервисе → unit-тесты без TestBed DOM.
  • Сервис в core — header читает isSpiritPleased, sanctum читает blessingLevel без import из features/altar.
  • Facade — тонкий слой для toast и делегирования; page component не вызывает CandlesService напрямую.
  • Альтернатива smart component с inject Firestore — дублирование при втором consumer (profile).

Почему rollback при ошибке Firestore, а не silent fail

  • Optimistic UI только для «горящей» свечи; counts и spirit — после таймера, но до ack от Firestore.
  • При fail восстанавливаем previousCounts и previousSpiritSatisfaction — UI не врёт пользователю.
  • _error signal → facade → toast с ключом altar — понятно, что не сохранилось.

Spirit satisfaction decay — зачем timer в effect

  • Геймификация: уровень благословения падает со временем, мотивирует возвращаться на алтарь.
  • effect(onCleanup) подписывается на timer(DECAY_INTERVAL) только когда level > 0.
  • Persist decay в Firestore — sanctum может использовать spirit level как input в branch judgment.

Что сказать на собеседовании

«Altar is a lazy-loaded feature with a thin page component and a presentational candles widget using CDK drag-drop and keyboard support. Domain logic lives in CandlesService in core — candle counts, lit candles, Machine Spirit satisfaction with decay, and Firestore sync on user change via effect. Offering is two-phase: immediate visual flame, then after a timer we persist counts with rollback on Firestore failure. AltarPageFacade shows contextual toasts on service errors. The header reads isSpiritPleased from the same service, so altar state is global game state, not page-local.»

S1 Main — Tarot API, facade и перевод расклада

Что делала

  • Реализовала главную страницу — первый user-facing flow проекта после layout.
  • TarotService — thin HttpClient wrapper: GET /api/reading?role=&intent=; role/intent как signal в сервисе.
  • Proxy dev (proxy.conf.json) + Netlify redirect prod → deploytarot.com — без backend в репо.
  • MainPageFacade — единственный API для UI: loading, error, result, loadTarot().
  • UI: TarotOracleComponent (выбор role/intent), TarotReadingComponent (карты, flip animation, verdict, empty state).
  • MyMemoryTranslationService — перевод ответа API с EN на активный язык (MyMemory public API).
  • Route providers: MainPageFacade, TarotService, MyMemoryTranslationService — scoped к главной, не root.

Технический поток draw cards

User picks role/intent (TarotService signals)
  → MainComponent.onDrawCards() → MainPageFacade.loadTarot()

loadTarot:
  _isTarotLoading = true, _error = null
  TarotService.loadReading().pipe(finalize, takeUntilDestroyed)
  → next: _sourceResult.set(tarotResponse)
  → error: _error.set (HttpErrorResponse.message)

_sourceResult = linkedSignal(() => { role(); intent(); return null })
  → смена role/intent сбрасывает результат без ручного clear

effect (constructor):
  when _sourceResult + activeLang change:
    _isTranslationLoading = true
    MyMemoryTranslationService.translateReading(source, lang)
      → finalize: _isTranslationLoading = false
      → next: _result.set(translated)
      → error: _result.set(source)  // fallback на английский

isLoading = computed(tarotLoading || translationLoading)

MyMemoryTranslationService — детали

  • Если язык EN — of(reading), без HTTP.
  • Текст режется на chunks по 500 bytes (UTF-8 через TextEncoder) — лимит MyMemory API.
  • mergeMap(..., 2) — максимум 2 параллельных запроса перевода (rate limit + не блокировать UI).
  • forkJoin для карт и verdict; toArray + sort by index — склеить chunks в правильном порядке.
  • catchError(() => of(text)) на chunk и на card — при fail показываем оригинал, не ломаем весь расклад.
  • Фильтр MYMEMORY WARNING в ответе — не показываем мусор от API.

Почему linkedSignal для source result, а не обычный signal

  • linkedSignal пересчитывается при смене role() или intent() и возвращает null — старый расклад не висит при новых настройках оракула.
  • Не нужны ручные setRole/setIntent с clear — меньше методов в facade, декларативная связь.
  • Translation effect реагирует на новый source — pipeline «fetch → translate → display» линейный.
  • Альтернатива: один signal + watch role/intent в effect с manual reset — больше императивного кода и риск забыть сброс.

Почему два флага loading (tarot vs translation)

  • Tarot API и MyMemory — разные endpoints с разной latency; пользователь видит прогресс «карты» и «перевод».
  • computed(isLoading) блокирует кнопку draw на всём pipeline — нельзя спамить запросы.
  • Translation error не блокирует показ — fallback на EN текст в _result.

Почему перевод в отдельном сервисе, а не в TarotService

  • Single responsibility: TarotService только deploytarot API; translation — отдельный HTTP client к MyMemory.
  • Тестируется изолированно: chunking, mergeMap concurrency, fallback.
  • MainPageFacade orchestrates — UI не знает про chunk size и langpair.
  • Альтернатива backend proxy с переводом — out of scope (static SPA + Netlify redirect только для tarot).

Что сказать на собеседовании

«Main page follows our facade pattern: TarotService wraps the external reading API through a dev proxy and Netlify redirect. MainPageFacade owns loading and error signals. I used linkedSignal so changing role or intent clears the previous reading automatically. After fetch, an effect pipes the response through MyMemoryTranslationService — text is chunked to 500 bytes, translated with mergeMap concurrency 2, and reassembled in order. If translation fails, we fall back to English content so the user still sees cards. HTTP errors hit our interceptor for toast and set a local error signal for empty UI.»

S2 uiStateStore — тема, язык, persist

Что делала

  • Завела глобальный uiStateStore на @ngrx/signals — theme + language.
  • UI_STATE InjectionToken с factory initialUiState — удобно подменять в тестах.
  • withMethods: setTheme, setLanguage, toggleTheme — каждый метод patchState + async persistUiState.
  • withHooks.onInit — три effect для синхронизации с внешним миром.
  • Интеграция: LanguageSwitcherComponent, LayoutService.toggleTheme, AppComponent.theme → tuiTheme на root.
  • provideAppInitializer inject store при старте — store живёт до первого render.
  • Рефактор language handling: enum Languages, связка с Transloco и login flow.

Три effect при инициализации

1. userProfileService.user() → patchState(profile?.uiState ?? initialUiState)
   Login: подтянуть theme/lang из Firestore users/{uid}.uiState
   Logout: сброс на initialUiState

2. store.theme() → themeService.setTheme()
   Применить CSS/Taiga theme глобально

3. store.language() → translocoService.load(lang).subscribe → setActiveLang
   Подгрузить JSON переводов; onCleanup unsubscribe

Persist — когда пишем в Firestore

setTheme / setLanguage / toggleTheme:
  patchState локально (UI мгновенно)
  persistUiState():
    if (!userProfileService.user()) return  // гость — только local
    userProfileService.updateUiState(uid, { theme, language })

Почему NgRx signalStore для UI state, а не BehaviorSubject или localStorage

  • Theme + language — truly global; нужен один source of truth для header, app root, Transloco.
  • signalStore даёт methods + hooks в одном месте — меньше boilerplate чем root service с manual subjects.
  • Persist в Firestore только для auth user — настройки следуют за аккаунтом на других устройствах.
  • localStorage без auth — рассинхрон с Firestore profile; мы выбрали server truth после login.
  • Feature stores (candles, tarot) не в uiStateStore — разделение «chrome preferences» vs «domain data».

Почему language effect грузит Transloco, а не только setActiveLang

  • translocoService.load(language) — async fetch /i18n/{lang}.json перед switch.
  • Без load — ключи мелькают или показывают fallback.
  • onCleanup unsubscribe — при быстрой смене языка не применяется устаревший bundle.
  • HTTP к /i18n/ исключён из error interceptor toast — иначе шум при каждой смене языка (см. раздел interceptor).

Почему LayoutService читает store, а компоненты не inject store напрямую

  • Layout — orchestration layer: theme, user, spirit pleased, mobile nav в одном месте.
  • Header получает themeChanged output → layoutService.toggleTheme() → store.
  • Меньше прямых зависимостей от store в leaf components — проще менять persist logic.

Что сказать на собеседовании

«uiStateStore is a root signalStore for theme and language. On init, an effect hydrates state from the Firebase user profile; another applies theme to ThemeService; a third loads Transloco bundles when language changes. User actions patch state immediately for snappy UI, then persist to Firestore users/{uid}.uiState if authenticated. Guests keep local state only until login. I used an InjectionToken for initial state so tests can override defaults without mocking Firestore.»

S3 Санктум — ритуал, RxJS timeline, Resource API

Что делала

  • Новая фича sanctum: суд над git-веткой, litany построчно, вердикт, digital priest.
  • createRitualTimelineStream — merge нескольких timer + map: каждая строка litany появляется с задержкой, затем verdict.
  • SanctumRitualService оборачивает поток в rxResource — loading/error/reload из коробки, UI читает ritualSession.value().
  • Звук: SanctumSoundService + Web Audio (organ tones); unlock AudioContext на user gesture.
  • PriestQuotesService — resource() с loader по языку Transloco, in-memory cache per lang, Firestore withTimeout.
  • Рефакторинг: digital priest из shared в feature, domain layer branch judgment, тесты + mocks.
// Упрощённо: timeline = merge построчных событий + финальный verdict
createRitualTimelineStream(request) {
  const judgment = analyzeBranch(branch, spiritLevel, intent);
  const lineEvents = judgment.litany.map((line, i) =>
    timer((i + 1) * DELAY).pipe(map(() => ({ litanyLines: slice(0, i+1), judgment: null })))
  );
  const verdictEvent = timer(totalDelay).pipe(map(() => ({ litanyLines, judgment })));
  return merge(...lineEvents, verdictEvent);
}

Почему RxJS timeline, а не setTimeout в компоненте

  • Декларативное расписание: merge + timer описывает «когда какое состояние» — легко менять DELAY в config без переписывания imperative кода.
  • Поток cold: каждый новый ritual = новая подписка через rxResource — нет гонок от старых таймеров.
  • tap для звука рядом с событиями — side effects отделены от state mapping.
  • Альтернатива async/await + sleep в цикле — сложнее отменить при уходе со страницы; rxResource отменяет stream при смене params.

rxResource vs ручной signal loading/error

  • rxResource даёт status, value, error, перезапуск при смене params — меньше boilerplate чем три сигнала вручную.
  • requestId в RitualRequest — форсирует reload даже при тех же branch/intent (повторный ритуал).
  • Для Firestore quotes — resource() (Promise loader), для анимации ритуала — rxResource (Observable stream): правильный примитив под тип async.

Что сказать на собеседовании

«Sanctum ritual is an Observable timeline: each litany line is a timed emission merged into one stream. I wrapped it in rxResource so the page gets loading state and cancellation for free. Priest quotes use the Promise-based resource API with language as params and a Map cache — we don't refetch Firestore on every line of litany. Sound is synchronized via tap on the same stream, not separate timers.»

S4 HTTP interceptor — эволюция и связка с Main

Что делала (итерации)

  1. v1 — functional httpErrorInterceptor + черновик global ErrorHandler.
  2. v2 — убрала global ErrorHandler для UX-ошибок: слишком generic, нет контекста фичи, дубли с facade.
  3. v3 — финальный interceptor: HotToast + toErrorMessage + skip /i18n/ + rethrow.
  4. Параллельно: withTimeout для Firestore, toasts в facades (altar, shrift, auth), README-таблица «кто за что отвечает».

Код interceptor — что делает

export const httpErrorInterceptor: HttpInterceptorFn = (request, next) => {
  return next(request).pipe(
    catchError((error: HttpErrorResponse) => {
      if (request.url.includes('/i18n/')) {
        return throwError(() => error);  // без toast
      }
      hotToast.error(transloco('http_error_label') + toErrorMessage(error));
      return throwError(() => error);    // subscriber всё ещё видит error
    })
  );
};

Как interceptor стыкуется с Main и uiStateStore

  • Tarot API (/api/reading) — ошибка → toast из interceptor + MainPageFacade._error для empty/error UI.
  • MyMemory translation — HTTP fail на chunk → catchError в сервисе возвращает оригинальный текст; расклад не пустой.
  • Transloco /i18n/*.json — skip toast; иначе при каждой смене языка (uiStateStore effect) пользователь видит ложные ошибки.
  • Firestore — interceptor не участвует; facade + CandlesService.error signal.
// Два слоя для HTTP
Interceptor:  user-visible toast (global copy)
Facade:       local error signal (feature UI state)

// Firestore — только facade + service error signal
CandlesService._error → AltarPageFacade effect → toast 'altar'
ConfessService throw → ShriftPageFacade try/catch → toast 'shrift'

Почему functional interceptor (HttpInterceptorFn), а не class-based

  • Angular 15+ recommended: inject() внутри функции, без class boilerplate.
  • Регистрация provideHttpClient(withInterceptors([httpErrorInterceptor])) — tree-shakable, явный список.
  • Легко тестировать через TestBed.runInInjectionContext.

Почему rethrow после toast, а не swallow error

  • MainPageFacade.loadTarot subscribe error handler выставляет _error — UI показывает empty state.
  • Если проглотить — facade думает, что success; loading сбросится через finalize, но result останется stale.
  • Facade может решить не дублировать toast (interceptor уже показал) — только local state.

Почему skip /i18n/, а не отдельный HttpClient без interceptor

  • Transloco loader использует тот же HttpClient — один клиент, один pipeline.
  • URL filter проще второго client instance и duplicate providers.
  • 404 на missing locale — dev issue; не нужен scary toast пользователю при switch lang.

Почему убрали global ErrorHandler после первой версии

  • ErrorHandler ловит всё подряд — including programming bugs; toast на каждый throw = noise.
  • Firestore и form errors уже handled в facades с правильным copy.
  • Оставили provideBrowserGlobalErrorListeners() для dev diagnostics, UX — через interceptor + facades.

★ Готовые ответы — типовые вопросы интервью о проекте

«Расскажи о самой сложной задаче»

Situation: Sanctum — многосоставной UX: форма, пошаговая litany, вердикт, звук, цитаты священника из Firestore, зависимость от spirit level с алтаря.

Task: Свести всё в предсказуемый state flow без spaghetti setTimeout и без дублирования loading/error.

Action: Вынесла timeline в чистую RxJS функцию, обернула в rxResource, quotes — в resource() с кэшем по языку, звук в tap. Facade отдаёт UI только computed signals.

Result: Повторный ритуал работает через requestId, отмена при уходе со страницы, тесты на stream и facade, bundle budgets подняты осознанно.

«Как у вас устроен state management?»

«Глобально — uiStateStore на NgRx Signals: theme и language с persist в Firestore после login. Main — MainPageFacade с linkedSignal и effect для tarot + translation pipeline. Altar — CandlesService в core с signals, computed, decay timer. Sanctum — rxResource для ritual timeline. UI не ходит в API/Firestore напрямую: page → facade → service. HTTP errors — interceptor; Firestore — error signal + facade toast.»

«Почему Angular 22 / signals?»

«Проект стартовал на Angular 22 с OnPush по умолчанию. Signals дают явный граф зависимостей: computed для производных значений (blessing level, isJudging), effect для side effects (persist, decay, toast). Меньше async pipe в шаблонах для локального UI state. RxJS остаётся для event streams и HTTP, мост через rxResource и takeUntilDestroyed.»

«Что бы ты улучшила сейчас?»

«Profile feature ещё WIP — нужен полноценный ProfilePageFacade по образцу altar. Altar сейчас частично вызывает CandlesService из facade, можно довести до 100% facade API. Для Firestore — рассмотреть centralized retry policy, но без потери контекстных toast. Добавить @defer на тяжёлые sanctum chunks если bundle вырастет.»
