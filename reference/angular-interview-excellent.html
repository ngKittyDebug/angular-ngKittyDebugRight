HTTP

1. Что такое HttpClientModule и зачем он нужен?

Исторически: HttpClientModule — NgModule-способ зарегистрировать HttpClient и его DI-токены. Он подключал HttpClientXsrfModule, связывал interceptors через DI multi-providers и делал HttpClient доступным для инъекции во всём приложении.

Современный подход (Angular 15+): в standalone-приложениях вместо модуля используется provideHttpClient() в ApplicationConfig. Функционально то же самое, но с выкидыванием неиспользуемого кода из бандла (tree-shaking) и композицией через feature-функции: withInterceptors(), withFetch(), withXsrfConfiguration().

Компромиссы:

модульный подход тащил всё разом; функциональные providers позволяют подключать только нужное. Interceptors переехали с class-based HTTP_INTERCEPTORS на HttpInterceptorFn — проще тестировать, не нужен @Injectable().

Проект: app.config.ts — provideHttpClient(withXhr(), withInterceptors([httpErrorInterceptor])). Явно выбран XHR-бэкенд; глобальный toast об ошибках через functional interceptor.

Документация: provideHttpClient · HttpClientModule (legacy)

2. Как делать HTTP-запросы через HttpClient?

Инжектируем HttpClient и вызываем типизированные методы — get<T>(), post, put, patch, delete, head, options. Каждый возвращает cold Observable (ленивый поток: сеть не трогаем, пока нет subscribe) — обычно один emit, затем complete или error.

private readonly http = inject(HttpClient);

getReading(params: TarotParams): Observable<TarotResponse> {
  return this.http.get<TarotResponse>(this.tarotUrl, { params: { ... } });
}

Опции: headers, params (HttpParams), responseType, observe ('body' | 'events' | 'response'), reportProgress, context (метаданные запроса для interceptors).

Компромиссы:

vs fetch: withFetch() использует Fetch API — лучше для SSR/edge; XHR даёт progress загрузки. vs Promise: Observable поддерживает отмену через unsubscribe, retry, композицию — критично при destroy компонента.

Проект: тонкий API-слой — TarotService (GET tarot), MyMemoryTranslationService (параллельный перевод чанков через forkJoin), TranslocoHttpLoader (i18n JSON).

Документация: Making HTTP requests · HttpClient API

HttpClient возвращает Observable, потому что HTTP в UI — это потоковая задача: progress events, retry, гонки запросов, объединение нескольких вызовов. lastValueFrom() / firstValueFrom() — мост к Promise, когда нужен async/await (guards, loader в resource()).

Компромиссы:

Не конвертируй всё в Promise — потеряешь отмену при destroy компонента посреди запроса. Предпочитай takeUntilDestroyed() или async pipe.

4. Как обрабатывать ошибки HTTP-запросов?

Слои (defense in depth):

  1. Interceptor — сквозная UX-логика (toast, логирование, redirect при auth). Пробрасывает ошибку дальше, чтобы caller тоже мог обработать.
  2. Service/Facade — маппит HttpErrorResponse в доменные error signals/сообщения.
  3. Component — показывает error state из facade; редко ловит HTTP напрямую.
// Interceptor — глобальное уведомление, re-throw
return next(req).pipe(
  catchError((error: HttpErrorResponse) => {
    if (!req.url.includes('/i18n/')) showToast(error);
    return throwError(() => error);
  })
);

// Facade — доменная обработка
.pipe(
  catchError((err) => {
    this._error.set(err instanceof HttpErrorResponse ? err.message : 'Unknown');
    return EMPTY;
  }),
  finalize(() => this._loading.set(false))
)

Компромиссы:

Только interceptor: теряется контекст фичи — facade всё равно нужен для специфичных сообщений. catchError в каждом сервисе: дублирование — разделяй ответственность.

Проект: httpErrorInterceptor пропускает /i18n/ (отсутствие перевода не должно показывать toast). MainPageFacade различает HttpErrorResponse и неизвестные ошибки, записывая в signal.

Документация: Handling request failure

5. Оптимизация HTTP-запросов и кэширование?

  • Дедупликация запросов — shareReplay(1) для hot shared streams; Resource API дедуплицирует по params.
  • In-memory cache — Map по URL/params/lang; инвалидация при мутации.
  • HTTP cache headers — уважать Cache-Control; interceptors могут добавлять If-None-Match.
  • Lazy loading — loadComponent откладывает загрузку чанка до визита на route.
  • Batching — объединить N вызовов в один (forkJoin) или ограничить concurrency (mergeMap(n)).
  • Prefetch — кастомная PreloadingStrategy для вероятных следующих маршрутов.

Компромиссы:

Кэш vs актуальность: паттерн stale-while-revalidate — показать кэш, обновить в фоне. Перекэширование i18n или user-specific данных даёт баги.

Проект: PriestQuotesService — Map<lang, quotes> перед Firestore. MyMemoryTranslationService — чанки с лимитом concurrency. UserStateStrategy выборочно прелоадит auth/guest routes.

Документация: HTTP setup · HTTP security

6. Что такое HttpInterceptor и как он работает?

Interceptor стоит в цепочке между вашим кодом и бэкендом. Каждый получает (req, next) и возвращает Observable<HttpEvent<unknown>>. Вызов next(req) передаёт запрос дальше; изменять req только через req.clone({...}) (immutable).

Современный стиль: HttpInterceptorFn — обычная функция с inject() для зависимостей. Регистрация через withInterceptors([fn1, fn2]). Порядок важен: первый в массиве обрабатывает исходящий запрос первым, входящий ответ — последним.

Компромиссы:

Class interceptors (HTTP_INTERCEPTORS) ещё работают, но functional предпочтительнее — нет DI-класса, проще unit-тест через TestBed.runInInjectionContext.

Документация: HTTP interceptors · HttpInterceptorFn

7. Когда использовать interceptor для обработки ошибок?

Хорошо подходит: глобальный toast/snackbar, централизованное логирование, 401 → logout/redirect, retry на 503, нормализация формата ошибки.

Плохо подходит: фича-специфичные validation messages, ошибки которые на одном экране глотаются, а на другом показываются, бизнес-логика принятия решений.

Компромиссы:

Используй HttpContext tokens для opt in/out на уровне запроса (SKIP_ERROR_TOAST). В проекте фильтрация по URL-паттерну для i18n — та же идея.

Документация: Interceptors guide

8. Аутентификация и авторизация через interceptors?

export const authInterceptor: HttpInterceptorFn = (req, next) => {
  const token = inject(AuthService).getToken();
  if (!token) return next(req);
  return next(req.clone({
    setHeaders: { Authorization: `Bearer ${token}` }
  }));
};

Auth (кто ты): прикрепить token/cookie к каждому API-вызову.

Authorization (что тебе можно): обычно на сервере; на клиенте — guards (canMatch, canActivate) блокируют маршруты, а не interceptors. Interceptor обрабатывает 401/403 глобально.

Компромиссы:

Firebase Auth в проекте идёт через SDK напрямую, не через Bearer headers — interceptors менее центральны. Для REST API с JWT auth interceptor — стандарт.

Проект: authGuard / guestGuard как CanMatchFn с inject(AuthService) — auth на уровне route, не HTTP interceptor.

RxJS

9. Что такое RxJS и зачем он в Angular?

RxJS (Reactive Extensions for JavaScript) — библиотека для описания и композиции асинхронных последовательностей значений через тип Observable<T>. Каждое значение доставляется подписчикам по мере появления; поток завершается сигналом complete или error.

Где Angular использует RxJS напрямую:

  • HttpClient — методы get/post/... возвращают Observable
  • Router — events, paramMap, queryParamMap; guards/resolvers могут возвращать Observable
  • Reactive Forms — valueChanges, statusChanges
  • async pipe — подписка в шаблоне с автоматической отпиской
  • HTTP interceptors — цепочка операторов над Observable<HttpEvent>
  • PreloadingStrategy.preload() возвращает Observable

Angular 16+ и signals: синхронное UI-состояние (loading, result, theme) — в signal() / computed(). RxJS остаётся на границах с асинхронным миром: HTTP, таймеры, DOM-события, длинные пайплайны. Мост — @angular/core/rxjs-interop:

APIНазначение
toSignal(obs$, { initialValue })Подписка на Observable → запись в signal; отписка при destroy
toObservable(signal)Каждое изменение signal → emit в Observable
takeUntilDestroyed(destroyRef)Оператор: завершить поток при destroy компонента/контекста
rxResource({ stream })Observable как источник данных для Resource API

Компромиссы:

  • Signals для state — проще читать шаблон и CD; нет встроенных операторов отмены/ретрая/композиции потоков.
  • RxJS для async pipelines — мощная композиция (switchMap, forkJoin), но выше порог входа и риск утечек без дисциплины отписки.
  • Дублирование — хранить то же состояние и в Subject, и в signal: два источника правды, сложнее отладка.
Проект: RxJS — TarotService, MyMemoryTranslationService (HTTP + forkJoin/mergeMap), createRitualTimelineStream (timer + merge), BallComponent (timer). Signals — MainPageFacade (loading/result/error). toSignal(langChanges$) в PriestQuotesService.

10. Observable, Observer и Subscription

Observable<T> — объект, который при вызове subscribe(observer) запускает функцию-подписчик (producer). До subscribe producer не выполняется (lazy). Может выдать 0..N значений типа T, затем complete() или error(err).

Observer<T> — интерфейс потребителя:

interface Observer<T> {
  next: (value: T) => void;
  error?: (err: unknown) => void;
  complete?: () => void;
}

В subscribe можно передать объект или три отдельных callback: subscribe(next, error, complete).

Subscription — результат subscribe; методы:

  • unsubscribe() — остановить поток и вызвать teardown-функцию producer'а
  • closed — флаг, что подписка уже закрыта
  • add(fn) — зарегистрировать дополнительный cleanup

Teardown: в new Observable(subscriber => { ...; return () => cleanup }) возвращаемая функция вызывается при unsubscribe. Нужна для setInterval, addEventListener, WebSocket — иначе ресурс остаётся висеть.

Жизненный цикл одной подписки: subscribe → (опционально) несколько next → ровно один из исходов: complete или error → после этого next игнорируются.

const sub = this.http.get<TarotResponse>('/api/reading').subscribe({
  next: (data) => this._result.set(data),
  error: (err) => this._error.set(err),
  complete: () => this._loading.set(false),
});
// при destroy компонента до ответа:
sub.unsubscribe(); // отменяет HTTP-запрос (XHR abort)

Компромиссы:

  • HTTP GET — поток конечный (один next + complete), но unsubscribe до ответа всё равно отменяет запрос — важно при быстрой навигации.
  • Infinite streams (interval, Subject без complete) — без отписки подписчик и producer остаются в памяти.
  • Множественные subscribe на один cold Observable — отдельный запуск producer на каждую подписку (см. вопрос 15).

Документация: Observable · Subscription

КомпозицияОператоры в .pipe() — декларативный граф преобразованийЦепочка then/catch/finally
Множественные потребителиCold по умолчанию; multicast через share/SubjectОдин потребитель на settled promise
Синхронные значенияof(1) может emit синхронно в том же stack frameExecutor синхронный; then-callback — в microtask

Мосты RxJS ↔ Promise:

  • firstValueFrom(obs$) / lastValueFrom(obs$) — Promise из Observable (ошибка, если 0 или >1 значений для first/last)
  • from(promise) — Observable: один next + complete или error
  • async pipe — подписка в шаблоне без ручного Promise

В Angular HttpClient возвращает Observable, потому что один HTTP-запрос может порождать несколько событий (HttpEventType: Sent, UploadProgress, ResponseHeader, Response), поддерживает отмену через unsubscribe и встраивается в interceptor pipeline.

Компромиссы:

  • async/await + firstValueFrom — читаемо для one-shot в resource().loader или guard; теряется пошаговая композиция операторов и отмена «из коробки» в цепочке.
  • Observable в компоненте — async pipe или takeUntilDestroyed; голый subscribe без cleanup на infinite stream — утечка.
  • Guards/resolvers — Angular принимает boolean | UrlTree | Observable | Promise; Observable удобен, если нужно дождаться нескольких async источников через операторы.

12. Базовые RxJS-операторы в Angular

Оператор — чистая функция вида (source: Observable) => Observable, вызывается в source.pipe(op1, op2, ...). Порядок операторов задаёт порядок обработки событий.

Creation (новый Observable без upstream): of, from, timer, interval, fromEvent, defer (отложенное создание при subscribe), EMPTY, throwError.

Transformation:

  • map(fn) — преобразует каждое значение (sync)
  • switchMap/mergeMap/concatMap/exhaustMap — преобразует в inner Observable и «разворачивает» (см. вопрос 19)
  • scan(accumulator) — аккумулятор по потоку (как reduce, но emit на каждом шаге)

Filtering: filter, take(n), takeUntil(notifier$), takeWhile, distinctUntilChanged (пропуск, если значение равно предыдущему), debounceTime(ms) (ждёт паузу между событиями), throttleTime(ms) (не чаще чем раз в N мс).

Combination:

  • forkJoin({ a: obsA$, b: obsB$ }) — ждёт complete всех источников; один emit с последними значениями; если любой error — весь forkJoin error
  • combineLatest([a$, b$]) — emit при первом значении каждого и при каждом последующем изменении любого
  • merge(a$, b$) — все события в один поток по мере поступления
  • concat(a$, b$) — сначала полностью a$, после complete — b$
  • race(a$, b$) — подписка на все; побеждает первый emit; остальные отписываются

Utility / error: tap (side effect без изменения значения), finalize (всегда при complete/error/unsubscribe), catchError, retry, shareReplay({ bufferSize, refCount }).

// Проект: параллельный перевод карт и вердикта
forkJoin({
  cards: this.translateCardList(reading.cards, lang),
  verdictText: this.translateText(reading.verdict_text, lang),
}).pipe(map(({ cards, verdictText }) => ({ ...reading, cards, verdict_text: verdictText })));

// Проект: чанки текста — max 2 одновременных HTTP
from(chunkList.map((chunk, index) => ({ chunk, index }))).pipe(
  mergeMap(({ chunk, index }) =>
    this.translateChunk(chunk, lang).pipe(map((t) => ({ index, translated: t }))),
    2 // concurrency limit
  ),
  toArray(),
  map((items) => items.sort((a, b) => a.index - b.index).map((i) => i.translated).join(' ')),
);

Компромиссы:

  • forkJoin — быстрый параллелизм, но один failed source валит весь результат; для partial success — mergeMap + per-item catchError.
  • combineLatest — удобен для форм (поле A + поле B), но emit на каждое изменение — нужен debounceTime или фильтр, чтобы не спамить.
  • debounceTime vs throttleTime — debounce ждёт тишину (search input); throttle ограничивает частоту (scroll/resize).
Проект: MyMemoryTranslationService — forkJoin на уровне reading/cards, mergeMap(2) на чанках, catchError(() => of(text)) на чанке и на всём тексте. createRitualTimelineStream — timer + map + merge. MainPageFacade — finalize для сброса loading.

13. Кастомный Observable через new Observable()

Создавайте кастомный Observable, когда внешний API основан на callback/listener, а готового creation-оператора нет (fromEvent, timer, defer не покрывают кейс).

Вариант 1 — композиция существующих операторов (предпочтительно в проекте):

export function createRitualTimelineStream(request: RitualRequest): Observable<RitualSessionState> {
  const judgment = analyzeBranch(request.branch, request.spiritLevel, request.ritualIntent);
  const lineEvents = judgment.litany.map((line, index) =>
    timer((index + 1) * RITUAL_LITANY_LINE_DELAY_MS).pipe(
      map(() => ({ litanyLines: judgment.litany.slice(0, index + 1), judgment: null }))
    )
  );
  const verdictEvent = timer(totalDelay).pipe(
    map(() => ({ litanyLines: judgment.litany, judgment }))
  );
  return merge(...lineEvents, verdictEvent);
}

Вариант 2 — new Observable для callback API:

new Observable<Message>((subscriber) => {
  const ws = new WebSocket(url);
  ws.onmessage = (e) => subscriber.next(JSON.parse(e.data));
  ws.onerror = (e) => subscriber.error(e);
  ws.onclose = () => subscriber.complete();
  return () => ws.close(); // teardown
});

Контракт producer:

  • После subscriber.complete() или subscriber.error() — нельзя вызывать next
  • Teardown вызывается при unsubscribe — освобождайте listeners/timers/сокеты
  • Если subscribe синхронно отписали до первого emit — teardown всё равно должен отработать

Компромиссы:

  • Композиция timer/merge/fromEvent — проще тестировать (мокаете время через marble tests / fakeAsync), меньше ручного кода.
  • new Observable — полный контроль, но легко забыть teardown или нарушить контракт complete/error.
  • Resource API — для load-one-result с loading/error signals; для progressive stream (ritual) — rxResource + Observable pipeline.
Проект: sanctum timeline — только композиция timer + merge, без new Observable. Подключено через rxResource({ stream }) в SanctumRitualService.

Документация: Creating Observables · Observable

14. Subject и BehaviorSubject

Subject<T> — одновременно Observable (можно подписаться) и Observer (можно вызвать next/error/complete извне). Это multicast: один источник → много подписчиков. Новый подписчик получает только события после момента подписки.

BehaviorSubject<T> — Subject с обязательным начальным значением:

  • При subscribe сразу emit текущего значения (даже если новых next не было)
  • getValue() — синхронное чтение последнего значения (вне reactive context — осторожно)
  • Типичное legacy-использование: currentUser$ = new BehaviorSubject<User | null>(null)

ReplaySubject(n) — буфер последних n значений; новый подписчик получает replay буфера, затем live события.

AsyncSubject — хранит только последнее значение и emit его один раз при complete.

Отличие от signal: Subject не интегрирован в Angular change detection; обновление через Subject в компоненте не обновит шаблон без async pipe или ручного markForCheck. Signal читается в шаблоне напрямую и участвует в CD graph.

Когда Subject ещё уместен: event bus между несвязанными модулями; обёртка callback API; legacy код с takeUntil(destroy$).

Компромиссы:

  • BehaviorSubject как store — привычно Rx-разработчикам, но нет computed/DevTools signals; риск забыть complete на root Subject.
  • shareReplay(1) вместо Subject для HTTP cache — кэширует последний ответ cold-потока; с refCount: true отписка от источника, когда нет подписчиков.
  • Multicast без Subject — оператор share() / publish() на cold Observable.
Проект: Subject/BehaviorSubject для app state не используются. Отписка — takeUntilDestroyed, не destroy$ Subject.

Документация: Subject · BehaviorSubject

15. Hot vs Cold Observables

Различие определяется тем, разделяют ли подписчики один producer (Hot and cold):

Cold (по умолчанию)Hot
ProducerЗапускается заново на каждый subscribeОдин producer на всех подписчиков
ДанныеПодписчик получает полную последовательность с началаПодписчик получает только события после момента подписки (кроме replay-буфера)
ПримерыHttpClient.get, of, ajax, deferDOM events, Subject, shared socket stream
Два subscribe на HttpClient без shareДва отдельных HTTP-запроса—

Cold → hot (share):

const cached$ = this.http.get<Data>('/api/data').pipe(
  shareReplay({ bufferSize: 1, refCount: true })
);
// первый subscribe — HTTP-запрос
// второй subscribe до complete первого — тот же запрос, тот же результат
// refCount: true — когда subscribers = 0, отписка от source

ConnectableObservable (publish() + connect()) — ручной старт multicast: без connect() подписчики не получают данных. В прикладном коде чаще shareReplay.

Проверка на интервью: «Что произойдёт при двух subscribe на http.get?» — два запроса. «Что добавит shareReplay(1)?» — один запрос, общий последний результат.

Компромиссы:

  • shareReplay без refCount — подписка на source не снимается при уходе всех consumers → утечка (особенно на long-polling/WebSocket wrapper).
  • Кэш HTTP через shareReplay — ускоряет повторный доступ, но нужна стратегия инвалидации; иначе stale data.
  • In-memory Map cache (как в PriestQuotesService) — явный контроль TTL/инвалидации vs неявный replay буфер.
Проект: каждый loadTarot() — новый cold HTTP. PriestQuotesService — Map-кэш по языку, не shareReplay. Ritual timeline — hot-подобное поведение через merge таймеров в одной подписке rxResource.

Документация: Hot and cold · shareReplay

16. Как правильно отписываться от Observable

Утечка памяти возникает, когда подписка остаётся активной после уничтожения компонента или когда producer держит ссылку на closure с DOM/компонентом.

Способы (от предпочтительного к legacy):

  1. async pipe — подписка в шаблоне; Angular отписывается при destroy view. Подходит для отображения потока в UI.
  2. takeUntilDestroyed(destroyRef) — оператор в pipe перед subscribe; работает в injection context (constructor, field initializer). Angular 16+.
  3. toSignal(obs$) — подписка управляется инфраструктурой signal; отписка при destroy.
  4. effect + onCleanup — для подписки внутри effect: 
    effect((onCleanup) => {
  const sub = stream$.subscribe((v) => doWork(v));
  onCleanup(() => sub.unsubscribe());
});
  5. takeUntil(notifier$) + Subject — в ngOnDestroy: destroy$.next(); destroy$.complete(). Legacy-паттерн.
  6. Конечные потоки — HTTP после complete отписка не обязательна для GC подписчика, но unsubscribe до ответа отменяет запрос.

Когда отписка не критична: one-shot firstValueFrom; поток уже завершился до destroy; root-сервис живёт lifetime приложения и поток infinite by design (с осторожностью).

Компромиссы:

  • async pipe — нельзя использовать результат в TypeScript-классе без дублирования через toSignal или subscribe.
  • subscribe в компоненте — нужен явный cleanup; в facade допустим с takeUntilDestroyed(destroyRef), если facade создаётся в injection context компонента/route.
  • Subscribe в root service — сервис не уничтожается; infinite stream без complete держит память всё время сессии.
Проект: MainPageFacade — takeUntilDestroyed(this.destroyRef) на tarot load. Translation — effect + onCleanup. BallComponent — timer().pipe(takeUntilDestroyed). CandlesService — takeUntilDestroyed на Firestore listener.

Документация: takeUntilDestroyed · takeUntil

18. Обработка ошибок и retry в RxJS

Ошибка в Observable — отдельный канал: после subscriber.error(err) поток для этой подписки завершён; последующие next не доставляются.

catchError(project) — перехватывает error и возвращает новый Observable (recovery stream):

.pipe(
  catchError((err: HttpErrorResponse) => {
    if (err.status === 404) return of(fallbackData);   // подмена потока
    return throwError(() => err);                     // проброс дальше
  })
)

retry(config) / retryWhen — повторная подписка на source после error. Параметры: count, delay, exponential backoff через timer(retryCount * 1000).

Применять retry только к идемпотентным операциям (GET, safe read). POST/PUT без idempotency key — риск дублирования записей на сервере.

finalize(fn) — вызывается при любом завершении: complete, error или unsubscribe. Типично: loading.set(false).

Слои в Angular-приложении:

  1. HTTP interceptor — глобальный toast/log, затем throwError (не глотать)
  2. Facade/service — маппинг в domain error signal или fallback value
  3. Component — отображает facade.error(), не ловит HTTP напрямую

Partial failure — когда падает элемент коллекции, а не весь поток:

mergeMap((chunk) =>
  this.translateChunk(chunk).pipe(
    catchError(() => of(chunk)) // fallback на исходный текст чанка
  )
)

Компромиссы:

  • catchError(() => of(null)) — UI не видит failure; лучше явный error signal или rethrow после логирования.
  • retry без лимита count — может перегрузить API; нужны count и backoff delay.
  • Только interceptor — нет контекста фичи; facade всё равно нужен для специфичных сообщений и recovery.
Проект: httpErrorInterceptor — toast + rethrow, кроме /i18n/. MainPageFacade — различает HttpErrorResponse и unknown errors в signal. Translation — per-chunk catchError(() => of(text)), whole-text fallback при полном сбое.

Документация: catchError · retry · finalize

19. Higher-order mapping operators — в чём разница?

Higher-order mapping — оператор принимает значение из outer stream и возвращает inner Observable; результат inner подписок «разворачивается» в output stream (Higher-order observables).

На каждое значение outer Observable оператор решает: подписаться на новый inner, ждать ли завершения предыдущего inner, запускать параллельно или игнорировать outer, пока inner активен.

ОператорПоведение при новом outer emitПараллельность innerТипичный сценарий
switchMapОтписывается от предыдущего innerМаксимум 1 active innerSearch: нужен только ответ последнего запроса
mergeMapПодписывается на новый inner, старые продолжаютВсе inner параллельно (или лимит N)Параллельные HTTP; чанки с mergeMap(fn, 2)
concatMapСтавит inner в очередь1 inner, остальные ждут completeПоследовательные записи, порядок важен
exhaustMapИгнорирует outer, пока текущий inner не завершён1 inner; новые outer droppedЗащита от double-submit
// switchMap: при новом term предыдущий HTTP отменяется (unsubscribe inner)
searchControl.valueChanges.pipe(
  debounceTime(300),
  distinctUntilChanged(),
  switchMap((term) => this.api.search(term)),
);

// mergeMap(2): не более 2 одновременных translateChunk — проект
from(chunks).pipe(mergeMap((c) => this.translateChunk(c), 2));

// exhaustMap: повторные клики Submit игнорируются до завершения save
submitClick$.pipe(exhaustMap(() => this.api.save(formValue)));

Типичные ошибки выбора оператора:

  • mergeMap без лимита на 100 элементов → 100 параллельных HTTP → rate limit, исчерпание лимита браузера на соединения (~6 на origin)
  • switchMap на submit формы → при быстрых кликах предыдущие save отменяются, данные могут не сохраниться → нужен exhaustMap
  • concatMap для search → очередь запросов, UI показывает устаревшие результаты с задержкой → нужен switchMap

Компромиссы:

  • switchMap — отмена устаревших запросов экономит сеть, но теряются in-flight результаты, если они всё ещё нужны.
  • mergeMap с concurrency — баланс скорости и нагрузки на API; лимит подбирается под rate limits (в проекте: 2).
  • concatMap — гарантия порядка ценой latency; для независимых чанков перевода — избыточен.
Проект: MyMemoryTranslationService.translateText — mergeMap(..., 2) из-за лимита MyMemory API и размера чанка 500 байт. Tarot load — прямой subscribe без higher-order. Sanctum — merge нескольких timer (не mapping operator, а объединение потоков).

Документация: Higher-order Observables · switchMap · mergeMap

20. Что такое ControlValueAccessor (CVA)?

ControlValueAccessor — интерфейс-мост между моделью формы Angular (FormControl) и кастомным UI-компонентом. Без CVA Angular не знает, как читать/писать значение вашего виджета (slider, date picker, rich editor).

Регистрация через multi-provider:

{ provide: NG_VALUE_ACCESSOR, useExisting: forwardRef(() => MyControl), multi: true }

Методы интерфейса (документация):

  • writeValue(value) — форма → компонент. Вызывается при инициализации и при setValue/patchValue снаружи.
  • registerOnChange(fn) — сохранить callback; вызывать при каждом изменении значения пользователем, чтобы обновить модель.
  • registerOnTouched(fn) — вызывать при blur, чтобы control стал touched.
  • setDisabledState(isDisabled) — реагировать на control.disable() / enable().

Когда нужен: переиспользуемый form control, который должен работать и с formControlName, и с [(ngModel)], участвовать в validation/touched/dirty/pristine.

Когда НЕ нужен: одноразовый wrapper вокруг <input> с [value] + (input) внутри одного экрана.

Компромиссы:

CVA vs инжект NgControl: CVA — правильный путь для библиотечных контролов. Инжект NgControl + valueAccessor = this — legacy-паттерн, сложнее и хрупче. OnChange-only: некоторые контролы вызывают onChange только при commit (datepicker on close) — важно не спамить валидацию на каждый keystroke, если UX этого не требует.

Проект: Taiga UI form controls уже реализуют CVA внутри — в формах login/register используем tuiInput, tuiPassword через ReactiveFormsModule. Кастомный CVA — учебный паттерн для интервью; в production предпочитаем готовые контролы библиотеки.

Документация: ControlValueAccessor

21. Кастомный form control с Reactive Forms

Пошаговый рецепт (Form validation guide):

  1. Standalone component с implements ControlValueAccessor.
  2. Provider: NG_VALUE_ACCESSOR + forwardRef — нужен, потому что класс ещё не объявлен в момент metadata.
  3. Внутри: хранить value; при user input вызывать сохранённый onChange; при blur — onTouched.
  4. Validation classes: через inject(NgControl, { optional: true, self: true }) или host bindings [class.ng-invalid] / [class.ng-touched].
  5. Родитель: typed FormGroup + formControlName.
// Родитель
form = new FormGroup({ rating: new FormControl(0, Validators.required) });

// Шаблон
<ngKitty-rating formControlName="rating" />

// Доступ к ошибкам
@if (form.controls.rating.invalid && form.controls.rating.touched) {
  <span>Обязательное поле</span>
}

Typed Reactive Forms (Angular 14+): FormBuilder.nonNullable.group<MyForm>() — тип значения CVA должен совпадать с типом control. FormGroup.controls.field даёт автокомплит.

Disabled state: [disabled]="true" на шаблоне deprecated — используй formControl.disable(); CVA получит setDisabledState.

Компромиссы:

Reactive vs Template-driven для кастомных контролов: Reactive — явная модель, проще тестировать (patchValue в spec). Template-driven — быстрее для прототипов, но cross-field validation и сложная логика хуже масштабируются.

Проект: формы вынесены в *FormService (LoginFormService, RegisterFormService, ConfessFormService); facade отдаёт form компоненту. UI — Taiga + ReactiveFormsModule. Валидационные сообщения — tuiValidationErrorsProvider в app.config.ts, ключи маппятся на i18n.

Документация: Custom form controls

22. Кастомный validator для template-driven forms

ValidatorFn — (control: AbstractControl) => ValidationErrors | null. Работает одинаково для Template-driven и Reactive forms — разница только в способе подключения.

Уровни валидации (angular.dev — Form validation):

  • Control-level — Validators.required, regex, min/max на одном поле.
  • Group-level (cross-field) — validator на FormGroup; сравнение password/confirmPassword.
  • Async validators — AsyncValidatorFn, возвращает Observable или Promise; control в состоянии PENDING до завершения.
// Cross-field validator — возвращает null на group,
// ошибки ставит на дочерний control
export const passwordConfirmationValidator = (
  controlName: string,
  matchingControlName: string
): ValidatorFn => {
  return (abstractControl: AbstractControl): ValidationErrors | null => {
    if (!isFormGroup(abstractControl)) return null;
    const control = abstractControl.controls[controlName];
    const matching = abstractControl.controls[matchingControlName];
    // ...сравнение, setErrors на matching, сохранение других ошибок
    return null;
  };
};

// Reactive: validators на group
this.fb.nonNullable.group({ password: [''], confirm: [''] }, {
  validators: passwordConfirmationValidator('password', 'confirm'),
});

Template-driven: <input ngModel required #email="ngModel"> или директива с @Directive({ providers: [NG_VALIDATORS] }).

Тестирование: pure validator тестируется без TestBed — создай FormGroup, вызови validator(group), assert control.errors.

Компромиссы:

setErrors в validator: императивная установка ошибок на sibling control — мощно, но легко затереть чужие ошибки. Проектный паттерн: фильтровать otherErrors перед setErrors. updateOn: 'change' | 'blur' | 'submit' на FormGroup — контролирует, когда валидация срабатывает.

Проект: passwordConfirmationValidator в shared/validators/ — group-level, сохраняет несвязанные ошибки на matchingControl. Spec без TestBed: password-confirmation.validator.spec.ts. dirtyFormGuard проверяет form.dirty перед уходом с login/register.

25. Что такое TestBed?

TestBed — изолированная среда Angular для тестов: компилятор шаблонов + DI-контейнер (Component testing basics).

Основной workflow:

  1. TestBed.configureTestingModule({ imports, providers }) — конфигурация как mini-приложение.
  2. await TestBed.compileComponents() — компиляция шаблонов (нужно при templateUrl).
  3. TestBed.createComponent(MyComponent) или TestBed.inject(MyService).
  4. fixture.detectChanges() — запуск change detection.
beforeEach(async () => {
  await TestBed.configureTestingModule({
    imports: [LoginComponent],           // standalone component
    providers: [
      { provide: ActivatedRoute, useValue: mockRoute },
      LoginPageFacade,
    ],
  }).compileComponents();
});

Продвинутые API:

  • TestBed.overrideComponent() — подменить template/providers конкретного компонента.
  • TestBed.runInInjectionContext(() => ...) — тест functional guards/interceptors/resolvers с inject().
  • TestBed.inject() — получить сервис из тестового injector.
  • TestBed.tick() — flush signal effects (Angular 19+).
  • TestBed.flushEffects() — выполнить все pending effects.

Компромиссы:

configureTestingModule вызывается в beforeEach — каждый тест получает чистый injector. Не кэшируй TestBed config с mutable state между тестами.

Документация: TestBed

26. ComponentFixture и DebugElement

ComponentFixture<T> — обёртка над созданным компонентом:

  • componentInstance — доступ к классу компонента.
  • detectChanges() — OnPush/signals: запускает CD для этого компонента и детей.
  • whenStable() — Promise, резолвится когда нет microtasks/macrotasks (async pipe, HTTP).
  • autoDetectChanges(true) — CD после каждого async callback (осторожно в unit tests).
  • debugElement — корневой DebugElement.
  • nativeElement — raw DOM (в jsdom — симулированный).

DebugElement — тестовый API поверх DOM:

const btn = fixture.debugElement.query(By.css('[data-testid="submit"]'));
btn.triggerEventHandler('click', null);
fixture.detectChanges();

// Дочерние элементы
fixture.debugElement.queryAll(By.directive(MyDirective));

// Injector конкретного узла
btn.injector.get(MyService);

By.css, By.directive, By.debugEl — поиск. Предпочитай data-testid или role-based queries (Testing Library) вместо хрупких CSS-селекторов.

Компромиссы:

nativeElement — browser-specific API, ломается в non-DOM платформах. DebugElement + triggerEventHandler — platform-agnostic. Для signals: после действия вызывай detectChanges() или TestBed.tick().

27. Тестирование directives и pipes

Pure pipes — тестируй как обычную функцию, TestBed не нужен:

const pipe = new MachineSpiritStatePipe();
expect(pipe.transform(5)).toBe('pleased');

Pure pipe пересчитывается только при изменении input reference — важно для performance-тестов.

Impure pipes — вызываются каждый CD cycle; тестируй через component fixture или проверяй pure: false в metadata.

Attribute directives — host component pattern:

@Component({
  template: '<div ngKittyScanEffect>content</div>',
  imports: [ScanEffectDirective],
})
class HostComponent {}

const fixture = TestBed.createComponent(HostComponent);
fixture.detectChanges();
expect(fixture.nativeElement.querySelector('div').classList).toContain('scan');

Structural directives — assert presence/absence DOM-элементов после detectChanges().

Компромиссы:

  • Pure pipe без TestBed — быстрый unit-тест функции transform, но не проверяет binding и CD в шаблоне.
  • Host component для directive — реалистичный DOM-контекст, но больше setup, чем тест одной функции.
  • Impure pipe — в изолированном тесте не видно, что pipe вызывается на каждом CD cycle; нужен fixture.
Проект: MachineSpiritStatePipe — custom pipe в header/altar. ScanEffectDirective, EyeBlinkDirective — attribute directives; тест через host component.

29. Тестирование template-driven и reactive forms

Reactive Forms (Reactive forms guide):

  1. Импортируй компонент + ReactiveFormsModule (или standalone imports).
  2. component.form.patchValue({ email: 'bad' }) или взаимодействие с DOM input.
  3. fixture.detectChanges().
  4. Assert: form.valid, form.controls.email.errors, текст ошибки в DOM.
  5. Spy на submit: vi.spyOn(facade, 'login'); клик submit; expect вызов с payload.

Template-driven: нужен FormsModule; симулируй input events:

const input = fixture.debugElement.query(By.css('input')).nativeElement;
input.value = 'test@mail.com';
input.dispatchEvent(new Event('input'));
fixture.detectChanges();
expect(fixture.componentInstance.form.value.email).toBe('test@mail.com');

Состояния control: valid/invalid, pristine/dirty, touched/untouched, pending (async validators).

Компромиссы:

Тестируй через facade.form (публичный API), не лезь в приватный FormGroup компонента. E2E-like DOM interaction — для component tests; чистая логика validator — unit без TestBed.

Проект: login/register — Reactive Forms через LoginPageFacade. dirtyFormGuard + spec на Observable из modal. passwordConfirmationValidator.spec.ts — unit без DOM.

31. Изоляция тестов

Тесты должны быть детерминированными и не влиять друг на друга:

  • Свежий TestBed — beforeEach с новой конфигурацией; afterEach(() => TestBed.resetTestingModule()) при кастомных override.
  • HTTP cleanup — httpMock.verify() в afterEach: нет незавершённых запросов.
  • Mocks — создавай в beforeEach, не шарь mutable objects. vi.clearAllMocks() / mockReset().
  • No global state — не мутируй singleton services без restore. Override providedIn: 'root' в TestBed providers.
  • Random/time — фиксируй vi.setSystemTime() для date-dependent logic.
  • DOM cleanup — Vitest/jsdom изолирует; при manual DOM append — cleanup в afterEach.

Arrange-Act-Assert — один logical assert на тест; несколько expect ok, если проверяют один сценарий.

Компромиссы:

Integration tests с реальными сервисами — медленнее, но ловят wiring bugs. Unit с mocks — быстрее, но mocks могут расходиться с реальностью. Проект: mock на границе (API services), реальный facade logic.

32. Как работает иерархия injector в Angular?

Angular DI — иерархическая система инжекторов: при inject(MyService) фреймворк ищет провайдер снизу вверх.

Два типа инжекторов:

  • Инжектор окружения (environment injector) — вне DOM: корень приложения (bootstrapApplication + app.config.ts) и инжекторы маршрутов (providers на route).
  • Элементный инжектор (element injector) — у каждого экземпляра компонента или директивы в DOM-дереве.

Алгоритм разрешения:

  1. Старт в element injector текущего компонента/директивы.
  2. Подъём по DOM к родительским компонентам.
  3. Если не найден — переход в environment injector ветки (route injector → root injector).
  4. NullInjectorError — токен нигде не зарегистрирован.

Shadowing (перекрытие): дочерний providers: [X] создаёт новый экземпляр X для поддерева; родительский экземпляр не затрагивается.

Компромиссы:

  • Root singleton — один источник правды (auth, theme), но сложнее изолировать в тестах; mutable state в root легко «протекает» между фичами.
  • Route providers — изоляция фичи + сервис уезжает в lazy chunk, но нужно явно регистрировать на entry route; забытый provider = runtime error при навигации.
  • Component providers — локальный UI-state, но риск дублирования экземпляров и путаницы «почему сервис разный в двух местах».
Проект: TarotService — route-scoped на main. AuthService — root singleton. Guards используют route injector и видят route providers.

Документация: Hierarchical DI

33. Как ограничить сервис поддеревом компонента?

Три уровня области видимости:

// 1. Component — новый instance на каждый instance компонента + дети
@Component({ providers: [WizardStateService] })

// 2. Route — на всё поддерево маршрута, пока route активен
{ path: 'main', providers: [MainPageFacade, TarotService], loadComponent: ... }

// 3. viewProviders — только view children, НЕ projected content (ng-content)
@Component({ viewProviders: [ViewOnlyService] })

Lifecycle: route-scoped уничтожается при deactivate маршрута; component-scoped — при ngOnDestroy компонента. Functional guards/resolvers на route используют route injector.

Компромиссы:

  • providedIn: 'root' — просто подключить, но сервис всегда в initial bundle и один instance на всё приложение.
  • Route providers — feature isolation + тестируемость, но больше boilerplate в app.routes.ts.
  • viewProviders vs providers — viewProviders не видят projected content; ошибка выбора = «сервис undefined» в ng-content subtree.
Проект: MainPageFacade, TarotService, MyMemoryTranslationService — main route. SanctumRitualService — sanctum route. CandlesService, ConfessService — root (shared domain). @Service({ autoProvided: false }) блокирует автоматический root registration.

Документация: Component providers · Route providers

34. Tree-shaking: providedIn: 'root' vs явные providers

@Injectable({ providedIn: 'root' }) — compiler регистрирует factory в root injector. Если ни один injection site не ссылается на класс — bundler может выкинуть класс из бандла (tree-shaking).

Варианты providedIn: 'root' (app-wide singleton), 'platform' (несколько Angular apps на странице), 'any' (legacy lazy NgModule — с standalone редко нужен).

Явный providers: [MyService] — сервис bundled вместе с route/component chunk; новый instance per injector; tree-shaking слабее, если chunk уже загружен.

Формы провайдеров: useClass, useValue (моки), useFactory (конфиг при создании), useExisting (алиас токена).

Компромиссы:

  • Root + providedIn — минимум конфигурации и tree-shakeable, но нельзя получить per-feature instance без override.
  • Explicit route providers — chunk splitting и изоляция, но класс попадает в bundle как только route загружен хоть раз.
  • useValue — быстрые моки в тестах, но один shared object: осторожно с мутациями между тестами.
  • useFactory — гибкая инициализация (URL из InjectionToken), но сложнее отлаживать цепочку deps.

Документация: Tree-shakable providers

35. Environment injectors и element injectors — в чём разница?

Environment injectorElement injector
ApplicationConfig, route providersОдин на component/directive instance
HttpClient, Router, global stores, interceptorsComponent-local services, viewProviders
Переживает destroy дочерних компонентовУмирает с компонентом
inject() в app.config factories, APP_INITIALIZERinject() в constructor / field initializer

Флаги inject(Token, options):

  • optional: true — null вместо ошибки.
  • self: true — только текущий injector, не подниматься.
  • skipSelf: true — начать с parent injector (обойти shadowing в текущем узле).
  • host: true — до root element injector (для директив на host).

InjectionToken<T> — для non-class зависимостей (config, интерфейсы). multi: true — массив значений (HTTP_INTERCEPTORS, APP_INITIALIZER).

Компромиссы:

  • Глобальные сервисы в environment — удобный доступ откуда угодно, но скрытые зависимости усложняют рефакторинг и тесты.
  • Локальные в element — явная граница поддерева, но легко ошибиться с viewProviders vs providers.
  • skipSelf / self — точный контроль shadowing, но код читается хуже — используй только когда действительно нужно обойти локальный provider.
Проект: guards — inject(AuthService) + inject(Router). UI_STATE InjectionToken для начального state в uiStateStore. provideAppInitializer(() => inject(AuthService).initialize()).

Signals

36. Что такое Resource API и зачем он нужен?

Без Resource для async-данных обычно вручную синхронизируют три вещи: данные, loading, error — плюс отмена предыдущего запроса при смене параметров.

Resource API (resource()) инкапсулирует это:

  • params() — reactive deps; при изменении — автоматический reload (предыдущий loader отменяется через abortSignal).
  • loader({ params, abortSignal }) — async-функция, возвращает Promise<T>.
  • value() — текущие данные (undefined до первого resolve).
  • status() — 'idle' | 'loading' | 'resolved' | 'error' | 'reloading'.
  • error(), reload(), isLoading() (computed).
quotesByPool = resource({
  params: () => this.activeLang(),
  loader: async ({ params: lang, abortSignal }) => {
    if (abortSignal.aborted) return fallback;
    return this.loadQuotes(lang);
  },
});

Экосистема signals (контекст):

APIНазначение
signal()Writable state
computed()Derived state, кэшируется
linkedSignal()Writable, сбрасывается при изменении source
effect()Side effects (не для derived — для этого computed)
toSignal(obs$)Мост Observable → signal с auto-unsubscribe

Компромиссы:

  • Resource vs ручные signals — меньше boilerplate и встроенная отмена, но меньше контроля над промежуточными состояниями кастомного пайплайна.
  • Resource vs RxJS в компоненте — Resource проще для «загрузил → показал»; RxJS — для сложной композиции (debounce, merge, retry chains).
  • effect() — удобен для side effects, но мутация unrelated signals внутри effect → риск circular updates; derived state только через computed.
Проект: PriestQuotesService — resource() + Map cache по языку. MainPageFacade — signal, computed(isLoading), linkedSignal (сброс tarot при смене role/intent), effect для translation side effects.

Документация: Resource API · resource()

37. В чём разница между resource и rxResource?

resource()rxResource()httpResource()
loader → Promisestream → ObservableHTTP GET wrapper
One-shot async resultMulti-value over timeTyped REST без custom RxJS
Firestore, fetch, async/awaitRxJS pipelines, progressive UIПростые GET endpoints
Отмена: abortSignalОтмена: unsubscribe при смене paramsHttpClient под капотом

Общее: params() перезапускает loader/stream; defaultValue — начальное значение; статусы одинаковые.

ritualSession = rxResource({
  params: () => this._ritualRequest(),
  defaultValue: EMPTY_RITUAL_SESSION,
  stream: ({ params }) => {
    if (!params) return EMPTY;
    return createRitualTimelineStream(params).pipe(
      tap(state => this.sanctumSound.play(...))
    );
  },
});

untracked(): чтение signal в computed без создания dependency — когда нужно прочитать, но не пересчитываться.

Компромиссы:

  • resource — проще mental model для CRUD/load, но не подходит для stream, который эмитит 10+ раз за сессию.
  • rxResource — идеален для progressive UI (ritual litany line-by-line), но тянет RxJS complexity и требует дисциплины с unsubscribe.
  • httpResource — быстрый старт для GET, но кастомный interceptor pipeline / chunk translation → лучше обычный HttpClient + facade или rxResource.
  • Observable с одним emit — можно обернуть в resource через firstValueFrom; не нужен rxResource «на всякий случай».
Проект: SanctumRitualService.ritualSession — rxResource + createRitualTimelineStream. PriestQuotesService — resource(). toSignal(translocoService.langChanges$) — bridge для params.

Components

38. Как обрабатывать динамические компоненты?

Динамический компонент — тип и/или момент создания определяется в runtime, а не в static template.

Паттерны:

  1. ViewContainerRef.createComponent() — императивно: inputBinding, outputBinding, setInput, destroy, projectableNodes.
  2. NgComponentOutlet — декларативно в шаблоне (вопрос 39).
  3. Dialog/overlay services — компонент вне DOM-иерархии (Taiga TuiDialogService, CDK Overlay).
  4. *ngTemplateOutlet — переключение шаблонов без полноценного component instance.

Lazy dynamic: import('./widget').then(m => createComponent(m.Widget)) — code splitting + runtime creation.

Компромиссы:

  • Dynamic vs @if + static imports — dynamic гибче (plugin/CMS), но обходит AOT template checking → ошибки bindings только в runtime.
  • createComponent vs outlet — createComponent даёт полный контроль lifecycle; outlet проще, но меньше hooks для projection и insertion order.
  • Overlay/dialog — компонент вне change detection tree родителя; нужно явно управлять focus trap и destroy.
Проект: ModalService — TuiDialogService.open(TUI_CONFIRM) для dirty form guard. Profile — ngTemplateOutlet для секций вместо dynamic component overhead.

Документация: Programmatic rendering

39. Что такое ngComponentOutlet и когда его использовать?

NgComponentOutlet — директива для рендера standalone component по ссылке на класс:

<ng-container *ngComponentOutlet="
  activeTabComponent;
  inputs: { userId: id(), mode: 'edit' };
  outputs: { saved: onSaved($event) }
" />

Когда уместен: tab panel / wizard steps; widget registry (тип из API → component map); конечный набор альтернативных UI-блоков.

Inputs/Outputs (17.3+): inputs и outputs bindings без ручного setInput/subscribe.

Компромиссы:

  • vs createComponent — outlet декларативен и проще читать; createComponent нужен для projectableNodes, manual destroy timing, вставки в конкретный index.
  • vs static @if — outlet когда тип в переменной; @if когда набор типов фиксирован на compile time (безопаснее, лучше tree-shaking).
  • Требование standalone — все dynamic types должны быть standalone; NgModule-declared components не подходят.

Документация: NgComponentOutlet

40. Что такое deferrable views (@defer) и как они ускоряют приложение?

@defer — lazy loading на уровне шаблона: код deferred блока — отдельный chunk, грузится по триггеру.

@defer (on viewport; prefetch on idle) {
  <ngKitty-heavy-chart [data]="chartData()" />
} @placeholder (minimum 100ms) {
  <div class="skeleton-chart" />
} @loading (minimum 200ms) {
  <ngKitty-spinner />
} @error {
  <p>Не удалось загрузить график</p>
}

Триггеры: on idle, on viewport, on interaction, on hover, on immediate, on timer, when condition(). prefetch — скачать chunk заранее.

@deferloadComponent (route)
Гранулярность внутри страницыГранулярность на уровне route
Placeholder/loading/error blocksНет встроенных блоков
Триггеры viewport/interactionТриггер = навигация

Компромиссы:

  • @defer below the fold — меньший initial bundle и лучший TTI; но задержка первого показа виджета после триггера.
  • @defer выше первого экрана (above the fold) — ухудшает LCP (контент появляется позже); критичный UI не defer-ить.
  • vs route lazy load — defer для тяжёлых кусков внутри уже загруженной страницы; route lazy — для целых фич. Комбинируют оба.
Проект: @defer не используется — loadComponent на маршрутах + UserStateStrategy preloading (guest/auth routes). Та же цель — меньший initial bundle без усложнения шаблонов.
