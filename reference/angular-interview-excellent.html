Angular Interview — уровень Excellent

Глубокие ответы с trade-offs, сравнениями подходов и привязкой к проекту ngKittyDebug. Основной источник: angular.dev.

HTTP

1. Что такое HttpClientModule и зачем он нужен?

Исторически: HttpClientModule — NgModule-способ зарегистрировать HttpClient и его DI-токены. Он подключал HttpClientXsrfModule, связывал interceptors через DI multi-providers и делал HttpClient доступным для инъекции во всём приложении.

Современный подход (Angular 15+): в standalone-приложениях вместо модуля используется provideHttpClient() в ApplicationConfig. Функционально то же самое, но с tree-shaking и композицией через feature-функции: withInterceptors(), withFetch(), withXsrfConfiguration().

Trade-off: модульный подход тащил всё разом; функциональные providers позволяют подключать только нужное. Interceptors переехали с class-based HTTP_INTERCEPTORS на HttpInterceptorFn — проще тестировать, не нужен @Injectable().
Проект: app.config.ts — provideHttpClient(withXhr(), withInterceptors([httpErrorInterceptor])). Явно выбран XHR-бэкенд; глобальный toast об ошибках через functional interceptor.

2. Как делать HTTP-запросы через HttpClient?

Инжектируем HttpClient и вызываем типизированные методы — get<T>(), post, put, patch, delete, head, options. Каждый возвращает cold Observable: один emit и complete (или error). Запрос ленивый — ничего не уходит в сеть до subscribe.

private readonly http = inject(HttpClient);

getReading(params: TarotParams): Observable<TarotResponse> {
  return this.http.get<TarotResponse>(this.tarotUrl, { params: { ... } });
}

Опции: headers, params (HttpParams), responseType, observe ('body' | 'events' | 'response'), reportProgress, context (метаданные запроса для interceptors).

vs fetch: withFetch() использует Fetch API — лучше для SSR/edge; XHR даёт progress загрузки. vs Promise: Observable поддерживает отмену через unsubscribe, retry, композицию — критично при destroy компонента.
Проект: тонкий API-слой — TarotService (GET tarot), MyMemoryTranslationService (параллельный перевод чанков через forkJoin), TranslocoHttpLoader (i18n JSON).

3. Observable vs Promise для HTTP-ответов?

HttpClient возвращает Observable, потому что HTTP в UI — это потоковая задача: progress events, retry, гонки запросов, объединение нескольких вызовов. lastValueFrom() / firstValueFrom() — мост к Promise, когда нужен async/await (guards, loader в resource()).

Не конвертируй всё в Promise — потеряешь отмену при destroy компонента посреди запроса. Предпочитай takeUntilDestroyed() или async pipe.

4. Как обрабатывать ошибки HTTP-запросов?

Слои (defense in depth):

  1. Interceptor — сквозная UX-логика (toast, логирование, redirect при auth). Пробрасывает ошибку дальше, чтобы caller тоже мог обработать.
  2. Service/Facade — маппит HttpErrorResponse в доменные error signals/сообщения.
  3. Component — показывает error state из facade; редко ловит HTTP напрямую.
// Interceptor — глобальное уведомление, re-throw
return next(req).pipe(
  catchError((error: HttpErrorResponse) => {
    if (!req.url.includes('/i18n/')) showToast(error);
    return throwError(() => error);
  })
);

// Facade — доменная обработка
.pipe(
  catchError((err) => {
    this._error.set(err instanceof HttpErrorResponse ? err.message : 'Unknown');
    return EMPTY;
  }),
  finalize(() => this._loading.set(false))
)
Только interceptor: теряется контекст фичи — facade всё равно нужен для специфичных сообщений. catchError в каждом сервисе: дублирование — разделяй ответственность.
Проект: httpErrorInterceptor пропускает /i18n/ (отсутствие перевода не должно показывать toast). MainPageFacade различает HttpErrorResponse и неизвестные ошибки, записывая в signal.

5. Оптимизация HTTP-запросов и кэширование?

  • Дедупликация запросов — shareReplay(1) для hot shared streams; Resource API дедуплицирует по params.
  • In-memory cache — Map по URL/params/lang; инвалидация при мутации.
  • HTTP cache headers — уважать Cache-Control; interceptors могут добавлять If-None-Match.
  • Lazy loading — loadComponent откладывает загрузку чанка до визита на route.
  • Batching — объединить N вызовов в один (forkJoin) или ограничить concurrency (mergeMap(n)).
  • Prefetch — кастомная PreloadingStrategy для вероятных следующих маршрутов.
Кэш vs актуальность: паттерн stale-while-revalidate — показать кэш, обновить в фоне. Перекэширование i18n или user-specific данных даёт баги.
Проект: PriestQuotesService — Map<lang, quotes> перед Firestore. MyMemoryTranslationService — чанки с лимитом concurrency. UserStateStrategy выборочно прелоадит auth/guest routes.

6. Что такое HttpInterceptor и как он работает?

Interceptor стоит в цепочке между вашим кодом и бэкендом. Каждый получает (req, next) и возвращает Observable<HttpEvent<unknown>>. Вызов next(req) передаёт запрос дальше; изменять req только через req.clone({...}) (immutable).

Современный стиль: HttpInterceptorFn — обычная функция с inject() для зависимостей. Регистрация через withInterceptors([fn1, fn2]). Порядок важен: первый в массиве обрабатывает исходящий запрос первым, входящий ответ — последним.

Class interceptors (HTTP_INTERCEPTORS) ещё работают, но functional предпочтительнее — нет DI-класса, проще unit-тест через TestBed.runInInjectionContext.

7. Когда использовать interceptor для обработки ошибок?

Хорошо подходит: глобальный toast/snackbar, централизованное логирование, 401 → logout/redirect, retry на 503, нормализация формата ошибки.

Плохо подходит: фича-специфичные validation messages, ошибки которые на одном экране глотаются, а на другом показываются, бизнес-логика принятия решений.

Используй HttpContext tokens для opt in/out на уровне запроса (SKIP_ERROR_TOAST). В проекте фильтрация по URL-паттерну для i18n — та же идея.

8. Аутентификация и авторизация через interceptors?

export const authInterceptor: HttpInterceptorFn = (req, next) => {
  const token = inject(AuthService).getToken();
  if (!token) return next(req);
  return next(req.clone({
    setHeaders: { Authorization: `Bearer ${token}` }
  }));
};

Auth (кто ты): прикрепить token/cookie к каждому API-вызову.

Authorization (что тебе можно): обычно на сервере; на клиенте — guards (canMatch, canActivate) блокируют маршруты, а не interceptors. Interceptor обрабатывает 401/403 глобально.

Firebase Auth в проекте идёт через SDK напрямую, не через Bearer headers — interceptors менее центральны. Для REST API с JWT auth interceptor — стандарт.
Проект: authGuard / guestGuard как CanMatchFn с inject(AuthService) — auth на уровне route, не HTTP interceptor.

RxJS

9. Что такое RxJS и зачем он в Angular?

RxJS (Reactive Extensions for JavaScript) — библиотека для работы с асинхронными потоками данных через Observable (rxjs.dev). Паттерн: push-based — producer пушит значения подписчикам, а не pull (как iterator).

Где Angular использует RxJS из коробки:

  • HttpClient — каждый запрос возвращает Observable
  • Router — events, paramMap, guards с Observable return
  • Forms — valueChanges, statusChanges
  • async pipe в шаблонах
  • HTTP interceptors — pipeline из операторов
  • PreloadingStrategy, resolvers

Angular 16+ и signals: RxJS смещается на async boundaries (сеть, таймеры, DOM events), а UI state держат signals. Мост — пакет @angular/core/rxjs-interop (документация):

APIНазначение
toSignal(obs$, { initialValue })Observable → signal (auto-unsubscribe)
toObservable(signal)signal → Observable
takeUntilDestroyed(destroyRef)Отписка при destroy без destroy$ Subject
rxResource()Observable stream как async resource
Signals vs RxJS: signals — для state (loading, user, theme). RxJS — для событий во времени (HTTP sequences, debounced search, progressive streams). Не конвертируй всё в signals — потеряешь операторы композиции. Не держи весь state в Subjects — хуже DX чем signals в Angular 22.
Проект: RxJS — HTTP (Tarot, translation API), ritual timeline (timer + merge), ball charging (timer(1800)). Signals — loading/error/result в MainPageFacade. toSignal(langChanges$) в PriestQuotesService.

10. Observable, Observer и Subscription

Три ключевых понятия RxJS (Observable guide):

Observable — «рецепт» потока. Ленивый: producer-функция выполняется только при subscribe(). Может emit 0..N значений, затем complete или error.

Observer — потребитель. Контракт:

interface Observer<T> {
  next: (value: T) => void;
  error?: (err: any) => void;
  complete?: () => void;
}

Можно передать три отдельных callback вместо объекта: .subscribe(next, error, complete).

Subscription — disposable handle:

  • unsubscribe() — отмена, вызов teardown logic producer'а
  • closed — boolean флаг
  • add(teardown) — регистрация дополнительного cleanup

Teardown logic: при создании Observable через new Observable(subscriber => { ... return () => cleanup }) — return function вызывается при unsubscribe. Критично для intervals, WebSocket, event listeners.

const sub = http.get('/api').subscribe({
  next: (data) => this.result.set(data),
  error: (err) => this.error.set(err),
  complete: () => console.log('stream finished'),
});
// позже:
sub.unsubscribe();
Забытый subscribe() без отписки на infinite stream (interval, Subject) = memory leak. HTTP GET complete после одного emit, но unsubscribe всё равно полезен если компонент destroy до ответа.

Cancellable (unsubscribe)Не отменяется (только AbortSignal обход)

Мосты:

  • lastValueFrom(obs$) / firstValueFrom(obs$) — Observable → Promise (для async/await)
  • from(promise) — Promise → Observable (один emit + complete)
  • async pipe — управляет подпиской в template, auto-unsubscribe

В Angular: HttpClient → Observable потому что HTTP в UI — stream problem: progress events, retry, race, combine. Guards/resolvers могут возвращать Observable, Promise или boolean.

Не конвертируй все HTTP в async/await + Promise — потеряешь отмену и композицию. firstValueFrom ok для one-shot в resource() loader. В компонентах prefer async pipe или takeUntilDestroyed, не голый subscribe.

12. Базовые RxJS-операторы в Angular

Операторы — чистые функции в .pipe(...) (Operators guide). Группы:

Creation (создают Observable): of, from, timer, interval, fromEvent, defer, EMPTY, throwError.

Transformation:

  • map — transform каждого value (DTO → domain model)
  • pluck / scan — extract field / accumulator
  • switchMap, mergeMap, concatMap, exhaustMap — higher-order (см. вопрос 19)

Filtering: filter, take(n), takeUntil, takeWhile, distinctUntilChanged, debounceTime, throttleTime, skip.

Combination:

  • forkJoin — ждёт complete всех sources, emit массив последних values (параллельные HTTP)
  • combineLatest — emit при изменении любого source (form field A + B)
  • merge — все sources в один поток (timeline events)
  • concat — последовательно, один за другим
  • race — первый emit wins

Utility: tap (side effect), delay, finalize (cleanup always), catchError, retry, shareReplay.

// Проектный паттерн: parallel translation
forkJoin({ cards: translateCards(), verdict: translateVerdict() }).pipe(
  map(({ cards, verdict }) => ({ ...reading, cards, verdict_text: verdict }))
);

// Chunk translation с concurrency limit
from(chunks).pipe(
  mergeMap(chunk => translateChunk(chunk), 2), // max 2 parallel
  toArray(),
  map(results => results.sort(...).join(' '))
);
Проект: MyMemoryTranslationService — forkJoin + mergeMap(2) + toArray + per-chunk catchError. createRitualTimelineStream — timer + map + merge. MainPageFacade — finalize. BallComponent — timer(1800).

13. Кастомный Observable через new Observable()

Когда готовые creators не подходят — обёртка callback/polling API (Creating observables):

export function createRitualTimelineStream(request: RitualRequest): Observable<RitualSessionState> {
  const judgment = analyzeBranch(...);
  const lineEvents = judgment.litany.map((line, index) =>
    timer((index + 1) * DELAY_MS).pipe(
      map(() => ({ litanyLines: judgment.litany.slice(0, index + 1), judgment: null }))
    )
  );
  const verdictEvent = timer(totalDelay).pipe(
    map(() => ({ litanyLines: judgment.litany, judgment }))
  );
  return merge(...lineEvents, verdictEvent);
}

Hand-rolled через new Observable:

new Observable<T>((subscriber) => {
  const ws = new WebSocket(url);
  ws.onmessage = (e) => subscriber.next(JSON.parse(e.data));
  ws.onerror = (e) => subscriber.error(e);
  ws.onclose = () => subscriber.complete();
  return () => ws.close(); // teardown при unsubscribe
});

Правила:

  • Вызывай subscriber.next(), затем complete() или error()
  • После complete/error — никаких emit
  • Return teardown function для cleanup
  • Не забудь обработать unsubscribe до первого emit
Prefer timer, fromEvent, defer когда возможно. В Angular 22 для async state рассмотри resource()/rxResource() вместо custom Observable + manual loading signals.
Проект: ritual timeline — не new Observable, а композиция timer + merge (читаемее, тестируемее). Подключён к rxResource в SanctumRitualService.

14. Subject и BehaviorSubject

Subject — одновременно Observable и Observer (Subject guide). Multicast: один producer → много subscribers. Hot — не хранит начальное значение.

const clicks$ = new Subject<MouseEvent>();
clicks$.subscribe(e => console.log('A', e));
clicks$.next(event); // только подписчики в момент emit получат

BehaviorSubject<T> — Subject + текущее значение:

  • Новый subscriber сразу получает latest value
  • getValue() — синхронное чтение (осторожно, outside reactive context)
  • Исторически: currentUser$ = new BehaviorSubject<User | null>(null)

ReplaySubject(n) — буфер последних N values для новых подписчиков.

AsyncSubject — emit только последнее value при complete (редко).

В Angular 22: для app state → signal() / signalStore. Subjects остаются для:

  • event bus между несвязанными модулями
  • мост к legacy API, возвращающему callbacks
  • takeUntil(destroy$) паттерн (legacy; заменён на takeUntilDestroyed)
BehaviorSubject ≈ signal, но без интеграции в template/CD. Root Subject без complete() при destroy приложения — leak. shareReplay(1) часто лучше Subject для shared HTTP cache.
Проект: нет BehaviorSubject/Subject для state — signals everywhere. destroy$ Subject не используется; takeUntilDestroyed вместо этого.

15. Hot vs Cold Observables

Фундаментальное различие (Hot vs Cold):

ColdHot
Producer на каждого subscriberОдин producer, много observers
Unicast (по умолчанию)Multicast
HttpClient, of, ajax, timerDOM events, Subjects, shared streams
Два subscribe = два HTTP запросаДва subscribe = те же events

Cold → Hot конвертация:

const shared$ = coldHttp$.pipe(
  shareReplay({ bufferSize: 1, refCount: true })
);
// refCount: true — unsubscribe source когда subscribers = 0

ConnectableObservable — publish() + connect() — ручной контроль старта hot stream (редко в app code).

Практический тест: два subscribe на HttpClient без share → два network request. С shareReplay(1) → один request, оба получат cached result.

shareReplay без refCount — source никогда не отписывается (memory leak на long-lived HTTP). refCount: true — preferred default.
Проект: HttpClient cold — каждый loadTarot() новый request (ожидаемо). PriestQuotesService — in-memory Map cache до RxJS share. Ritual timeline hot-like через merge таймеров в одном subscribe rxResource.

16. Как правильно отписываться от Observable

Memory leaks — главный RxJS-риск в SPA. Иерархия предпочтений:

  1. async pipe в template — Angular управляет subscribe/unsubscribe при destroy. Идеально для display-only streams.
  2. takeUntilDestroyed(destroyRef) — inject DestroyRef, pipe перед subscribe. Работает в constructor (Angular 16+).
  3. toSignal(obs$) — автоматическая подписка/отписка при destroy компонента.
  4. effect + onCleanup — для подписок внутри signal effects: 
    effect((onCleanup) => {
  const sub = service.translate(...).subscribe(...);
  onCleanup(() => sub.unsubscribe());
});
  5. takeUntil(destroy$) — classic: Subject + ngOnDestroy → destroy$.next(); destroy$.complete(). Legacy, но ещё встречается.
  6. Finite streams — HTTP GET auto-completes, но unsubscribe при destroy всё равно отменяет in-flight request.

НЕ нужна отписка: Observable завершился (complete/error) до destroy; firstValueFrom one-shot.

Голый .subscribe() в компоненте без cleanup — code smell. Если subscribe в сервисе root-level — stream должен быть infinite-safe или self-completing. Subscription.add() — группировка нескольких subs для bulk unsubscribe.
Проект: MainPageFacade.loadTarot() — takeUntilDestroyed(destroyRef). Translation effect — onCleanup(() => subscription.unsubscribe()). BallComponent — timer().pipe(takeUntilDestroyed). Нет destroy$ Subject нигде.

18. Обработка ошибок и retry в RxJS

Стратегии обработки ошибок (Error handling operators):

1. catchError — перехват в pipeline, recovery или rethrow:

.pipe(
  catchError((err: HttpErrorResponse) => {
    if (err.status === 404) return of(fallbackData);  // замена потока
    return throwError(() => err);                      // проброс дальше
  })
)

2. retry / retryWhen — переподписка на source:

retry({ count: 3, delay: 1000 })
retry({ delay: (err, retryCount) => timer(retryCount * 1000) }) // backoff

Только для идемпотентных операций (GET). POST без idempotency key — опасно.

3. finalize — выполняется при complete, error или unsubscribe (сброс loading):

.pipe(finalize(() => this._loading.set(false)))

4. Слои в Angular app:

  1. Interceptor — global toast, re-throw
  2. Service/Facade — map to domain error signal, fallback value
  3. Component — display from facade (редко catch HTTP)

5. Per-item fallback (проект):

mergeMap(chunk => translateChunk(chunk).pipe(
  catchError(() => of(originalChunk)) // один чанк failed → оригинал
))
catchError returning of(null) глотает ошибку — UI не узнает о failure. Лучше explicit error state signal. retry на infinite без backoff — DDoS свой же API.
Проект: interceptor — toast + re-throw (кроме /i18n/). MainPageFacade — HttpErrorResponse vs unknown в error signal; translation fallback на source text при ошибке перевода. Translation chunks — per-chunk catchError(() => of(text)).

19. Higher-order mapping operators — в чём разница?

Higher-order mapping — outer stream emit value → создаётся inner Observable → flatten в output (Higher-order observables). Самая частая RxJS-тема на интервью.

ОператорConcurrencyОтмена предыдущего innerUse case
switchMap1 innerДа — unsubscribe previousSearch-as-you-type, route params → fetch
mergeMap / flatMapВсе параллельно (или limit N)НетParallel HTTP, N chunks (mergeMap(fn, 2))
concatMap1 inner, очередьЖдёт complete предыдущегоSequential writes, order matters
exhaustMap1 innerИгнорирует новые outer пока busyDouble-submit protection
// switchMap — только последний search
searchInput$.pipe(
  debounceTime(300),
  distinctUntilChanged(),
  switchMap(term => this.api.search(term)) // отменяет предыдущий HTTP
);

// mergeMap(2) — max 2 parallel (проект)
from(chunks).pipe(mergeMap(c => translate(c), 2));

// exhaustMap — кнопка submit
submit$.pipe(exhaustMap(() => this.api.save(data))); // клики пока save — ignored

Marble diagram intuition: switch = переключатель; merge = все сразу; concat = очередь; exhaust = занят, не принимаю новые.

Выбор оператора = выбор semantics отмены и concurrency. Неправильный оператор → race conditions, duplicate POST, stale search results.

mergeMap без concurrency limit на 100 items → 100 parallel HTTP → rate limit / browser connection cap. Всегда указывай limit или используй concatMap для sequential. switchMap на submit form — потеряешь предыдущие saves (нужен exhaustMap).
Проект: MyMemoryTranslationService.translateText — mergeMap(..., 2) для rate-limited translation API. Route params search не используется; tarot load — простой subscribe без higher-order. Sanctum timeline — merge (не mapping), несколько timer streams параллельно.

20. Что такое ControlValueAccessor (CVA)?

ControlValueAccessor — интерфейс-мост между моделью формы Angular (FormControl) и кастомным UI-компонентом. Без CVA Angular не знает, как читать/писать значение вашего виджета (slider, date picker, rich editor).

Регистрация через multi-provider:

{ provide: NG_VALUE_ACCESSOR, useExisting: forwardRef(() => MyControl), multi: true }

Методы интерфейса (документация):

  • writeValue(value) — форма → компонент. Вызывается при инициализации и при setValue/patchValue снаружи.
  • registerOnChange(fn) — сохранить callback; вызывать при каждом изменении значения пользователем, чтобы обновить модель.
  • registerOnTouched(fn) — вызывать при blur, чтобы control стал touched.
  • setDisabledState(isDisabled) — реагировать на control.disable() / enable().

Когда нужен: переиспользуемый form control, который должен работать и с formControlName, и с [(ngModel)], участвовать в validation/touched/dirty/pristine.

Когда НЕ нужен: одноразовый wrapper вокруг <input> с [value] + (input) внутри одного экрана.

CVA vs инжект NgControl: CVA — правильный путь для библиотечных контролов. Инжект NgControl + valueAccessor = this — legacy-паттерн, сложнее и хрупче. OnChange-only: некоторые контролы вызывают onChange только при commit (datepicker on close) — важно не спамить валидацию на каждый keystroke, если UX этого не требует.
Проект: Taiga UI form controls уже реализуют CVA внутри — в формах login/register используем tuiInput, tuiPassword через ReactiveFormsModule. Кастомный CVA — учебный паттерн для интервью; в production предпочитаем готовые контролы библиотеки.

21. Кастомный form control с Reactive Forms

Пошаговый рецепт (Form validation guide):

  1. Standalone component с implements ControlValueAccessor.
  2. Provider: NG_VALUE_ACCESSOR + forwardRef — нужен, потому что класс ещё не объявлен в момент metadata.
  3. Внутри: хранить value; при user input вызывать сохранённый onChange; при blur — onTouched.
  4. Validation classes: через inject(NgControl, { optional: true, self: true }) или host bindings [class.ng-invalid] / [class.ng-touched].
  5. Родитель: typed FormGroup + formControlName.
// Родитель
form = new FormGroup({ rating: new FormControl(0, Validators.required) });

// Шаблон
<ngKitty-rating formControlName="rating" />

// Доступ к ошибкам
@if (form.controls.rating.invalid && form.controls.rating.touched) {
  <span>Обязательное поле</span>
}

Typed Reactive Forms (Angular 14+): FormBuilder.nonNullable.group<MyForm>() — тип значения CVA должен совпадать с типом control. FormGroup.controls.field даёт автокомплит.

Disabled state: [disabled]="true" на шаблоне deprecated — используй formControl.disable(); CVA получит setDisabledState.

Reactive vs Template-driven для кастомных контролов: Reactive — явная модель, проще тестировать (patchValue в spec). Template-driven — быстрее для прототипов, но cross-field validation и сложная логика хуже масштабируются.
Проект: формы вынесены в *FormService (LoginFormService, RegisterFormService, ConfessFormService); facade отдаёт form компоненту. UI — Taiga + ReactiveFormsModule. Валидационные сообщения — tuiValidationErrorsProvider в app.config.ts, ключи маппятся на i18n.

22. Кастомный validator для template-driven forms

ValidatorFn — (control: AbstractControl) => ValidationErrors | null. Работает одинаково для Template-driven и Reactive forms — разница только в способе подключения.

Уровни валидации (angular.dev — Form validation):

  • Control-level — Validators.required, regex, min/max на одном поле.
  • Group-level (cross-field) — validator на FormGroup; сравнение password/confirmPassword.
  • Async validators — AsyncValidatorFn, возвращает Observable или Promise; control в состоянии PENDING до завершения.
// Cross-field validator — возвращает null на group,
// ошибки ставит на дочерний control
export const passwordConfirmationValidator = (
  controlName: string,
  matchingControlName: string
): ValidatorFn => {
  return (abstractControl: AbstractControl): ValidationErrors | null => {
    if (!isFormGroup(abstractControl)) return null;
    const control = abstractControl.controls[controlName];
    const matching = abstractControl.controls[matchingControlName];
    // ...сравнение, setErrors на matching, сохранение других ошибок
    return null;
  };
};

// Reactive: validators на group
this.fb.nonNullable.group({ password: [''], confirm: [''] }, {
  validators: passwordConfirmationValidator('password', 'confirm'),
});

Template-driven: <input ngModel required #email="ngModel"> или директива с @Directive({ providers: [NG_VALIDATORS] }).

Тестирование: pure validator тестируется без TestBed — создай FormGroup, вызови validator(group), assert control.errors.

setErrors в validator: императивная установка ошибок на sibling control — мощно, но легко затереть чужие ошибки. Проектный паттерн: фильтровать otherErrors перед setErrors. updateOn: 'change' | 'blur' | 'submit' на FormGroup — контролирует, когда валидация срабатывает.
Проект: passwordConfirmationValidator в shared/validators/ — group-level, сохраняет несвязанные ошибки на matchingControl. Spec без TestBed: password-confirmation.validator.spec.ts. dirtyFormGuard проверяет form.dirty перед уходом с login/register.

23. Какие типы тестирования поддерживает Angular?

Angular не навязывает один runner, но экосистема делится на уровни (Testing guide):

24. Основные инструменты и библиотеки

  • @angular/common/http/testing — HttpTestingController, provideHttpClientTesting().

25. Что такое TestBed?

TestBed — изолированная среда Angular для тестов: компилятор шаблонов + DI-контейнер (Component testing basics).

Основной workflow:

  1. TestBed.configureTestingModule({ imports, providers }) — конфигурация как mini-приложение.
  2. await TestBed.compileComponents() — компиляция шаблонов (нужно при templateUrl).
  3. TestBed.createComponent(MyComponent) или TestBed.inject(MyService).
  4. fixture.detectChanges() — запуск change detection.
beforeEach(async () => {
  await TestBed.configureTestingModule({
    imports: [LoginComponent],           // standalone component
    providers: [
      { provide: ActivatedRoute, useValue: mockRoute },
      LoginPageFacade,
    ],
  }).compileComponents();
});

Продвинутые API:

  • TestBed.overrideComponent() — подменить template/providers конкретного компонента.
  • TestBed.runInInjectionContext(() => ...) — тест functional guards/interceptors/resolvers с inject().
  • TestBed.inject() — получить сервис из тестового injector.
  • TestBed.tick() — flush signal effects (Angular 19+).
  • TestBed.flushEffects() — выполнить все pending effects.
configureTestingModule вызывается в beforeEach — каждый тест получает чистый injector. Не кэшируй TestBed config с mutable state между тестами.

26. ComponentFixture и DebugElement

ComponentFixture<T> — обёртка над созданным компонентом:

  • componentInstance — доступ к классу компонента.
  • detectChanges() — OnPush/signals: запускает CD для этого компонента и детей.
  • whenStable() — Promise, резолвится когда нет microtasks/macrotasks (async pipe, HTTP).
  • autoDetectChanges(true) — CD после каждого async callback (осторожно в unit tests).
  • debugElement — корневой DebugElement.
  • nativeElement — raw DOM (в jsdom — симулированный).

DebugElement — тестовый API поверх DOM:

const btn = fixture.debugElement.query(By.css('[data-testid="submit"]'));
btn.triggerEventHandler('click', null);
fixture.detectChanges();

// Дочерние элементы
fixture.debugElement.queryAll(By.directive(MyDirective));

// Injector конкретного узла
btn.injector.get(MyService);

By.css, By.directive, By.debugEl — поиск. Prefer data-testid или role-based queries (Testing Library) вместо хрупких CSS-селекторов.

nativeElement — browser-specific API, ломается в non-DOM платформах. DebugElement + triggerEventHandler — platform-agnostic. Для signals: после действия вызывай detectChanges() или TestBed.tick().

27. Тестирование directives и pipes

Pure pipes — тестируй как обычную функцию, TestBed не нужен:

const pipe = new MachineSpiritStatePipe();
expect(pipe.transform(5)).toBe('pleased');

Pure pipe пересчитывается только при изменении input reference — важно для performance-тестов.

Impure pipes — вызываются каждый CD cycle; тестируй через component fixture или проверяй pure: false в metadata.

Attribute directives — host component pattern:

@Component({
  template: '<div ngKittyScanEffect>content</div>',
  imports: [ScanEffectDirective],
})
class HostComponent {}

const fixture = TestBed.createComponent(HostComponent);
fixture.detectChanges();
expect(fixture.nativeElement.querySelector('div').classList).toContain('scan');

Structural directives — assert presence/absence DOM-элементов после detectChanges().

Проект: MachineSpiritStatePipe — custom pipe в header/altar. ScanEffectDirective, EyeBlinkDirective — attribute directives; тест через host component.

31. Изоляция тестов

Тесты должны быть детерминированными и не влиять друг на друга:

  • Свежий TestBed — beforeEach с новой конфигурацией; afterEach(() => TestBed.resetTestingModule()) при кастомных override.
  • HTTP cleanup — httpMock.verify() в afterEach: нет незавершённых запросов.
  • Mocks — создавай в beforeEach, не шарь mutable objects. vi.clearAllMocks() / mockReset().
  • No global state — не мутируй singleton services без restore. Override providedIn: 'root' в TestBed providers.
  • Random/time — фиксируй vi.setSystemTime() для date-dependent logic.
  • DOM cleanup — Vitest/jsdom изолирует; при manual DOM append — cleanup в afterEach.

Arrange-Act-Assert — один logical assert на тест; несколько expect ok, если проверяют один сценарий.

Integration tests с реальными сервисами — медленнее, но ловят wiring bugs. Unit с mocks — быстрее, но mocks могут расходиться с реальностью. Проект: mock на границе (API services), реальный facade logic.

Dependency Injection

32. Иерархия injector в Angular

Angular DI — иерархическая система injectors (Hierarchical DI). Два типа:

  1. Environment injectors — вне DOM-дерева:
    • PlatformInjector — платформенные сервисы (редко в app code).
    • RootInjector — bootstrapApplication(App, config) providers.
    • Route injectors — providers на каждом route; создаются при навигации, уничтожаются при уходе.
  2. Element injectors — по одному на каждый component/directive instance в DOM-дереве.

Алгоритм разрешения (Debugging DI):

  1. Старт в element injector текущего компонента.
  2. Подъём по DOM-дереву (parent components).
  3. Если не найден — fall through в environment injector этой ветки (route → root).
  4. NullInjectorError — токен нигде не зарегистрирован.

Child injector shadowing: provider в child перекрывает parent token — получаешь новый instance, parent не затронут.

Понимание иерархии критично для багов «почему два разных instance AuthService» или «почему TarotService undefined» — почти всегда missing route provider или shadowing.

33. Как ограничить сервис поддеревом компонента?

Три уровня scope:

// 1. Component providers — один instance на instance компонента + дети
@Component({ providers: [LocalStateService] })

// 2. Route providers — на всё поддерево маршрута
{ path: 'main', component: MainComponent,
  providers: [MainPageFacade, TarotService] }

// 3. viewProviders — только view children, НЕ content-projected
@Component({ viewProviders: [ViewOnlyService] })

Lifecycle: route-scoped services уничтожаются при navigate away (если route deactivated). Component-scoped — при destroy компонента.

Functional guards/resolvers на route используют route injector — видят route providers.

providedIn: 'root' — singleton на всё приложение. Route providers — feature isolation + lazy bundle splitting. Не клади feature API в root без причины — усложняет тесты и увеличивает initial bundle.
Проект: MainPageFacade, TarotService, MyMemoryTranslationService — только на main route. SanctumRitualService, PriestQuotesService — sanctum route. AuthService, CandlesService, ConfessService — root (shared domain). Декоратор @Service({ autoProvided: false }) блокирует auto root registration.

34. Tree-shaking: providedIn: 'root' vs explicit providers

@Injectable({ providedIn: 'root' }) — Angular compiler регистрирует factory в root injector. Если ни один injection site не ссылается на класс — tree-shakeable (не попадёт в bundle).

Варианты providedIn:

  • 'root' — один singleton app-wide.
  • 'platform' — shared между несколькими Angular apps на странице (micro-frontends).
  • 'any' — отдельный instance per lazy-loaded module (legacy NgModule); с standalone редко нужен.
  • SomeModule — привязка к модулю (legacy).

Explicit providers: [MyService] — сервис bundled вместе с route/component chunk. Новый instance per injector. Не tree-shakeable на уровне класса, если chunk загружен.

Provider shapes:

  • useClass — создать instance класса (можно заменить implementation).
  • useValue — готовый объект/mock.
  • useFactory — factory: (dep) => new X(dep), deps: [OtherService].
  • useExisting — алиас на другой token.
Singleton (root) vs per-feature (route): AuthService — root. TarotService — route. useFactory — когда нужна конфигурация при создании (API URL из injection token).

Signals

36. Resource API и асинхронная загрузка данных

Signals — примитив fine-grained reactivity в Angular (Signals guide). Перед Resource API — обзор экосистемы:

APIНазначение
signal(initial)Writable state; чтение s(), запись s.set(v) / s.update(fn)
computed(() => ...)Derived state; кэшируется, пересчитывается при изменении зависимостей
linkedSignal(source)Writable, но сбрасывается при изменении source signals
effect(() => ...)Side effects (logging, sync, subscriptions); cleanup через onCleanup
asReadonly()Expose writable signal как ReadonlySignal наружу

Resource API (resource() из @angular/core) — обёртка async loading:

quotesByPool = resource({
  params: () => this.activeLang(),  // reload при смене lang
  loader: async ({ params: lang, abortSignal }) => {
    if (abortSignal.aborted) return fallback;
    return this.loadQuotes(lang);
  },
});

// В шаблоне / классе:
quotesByPool.value()    // T | undefined
quotesByPool.status()   // 'idle' | 'loading' | 'resolved' | 'error' | 'reloading'
quotesByPool.error()    // ошибка loader
quotesByPool.reload()   // принудительный reload

Reactive contexts — signal читается «под капотом» при вызове в template, computed, effect, linkedSignal, resource params. Это регистрирует dependency для CD.

Мост RxJS ↔ Signals: toSignal(obs$), toObservable(signal), takeUntilDestroyed.

Signals — для state. RxJS — для async event streams (HTTP, timers). Не конвертируй всё в signals — effect не для derived state (используй computed). Effects не должны мутировать unrelated signals (риск circular updates).
Проект: MainPageFacade — signal, computed(isLoading), linkedSignal (сброс tarot при смене role/intent), effect для translation. uiStateStore — NgRx signalStore с patchState. PriestQuotesService — resource() + Map cache.

Components

38. Что такое компоненты в Angular и как они являются основой структуры приложения?

Компонент — фундаментальная единица UI в Angular (Components guide): TypeScript-класс + HTML-шаблон + стили + metadata (@Component).

Angular-приложение — дерево компонентов. Каждый узел:

  • имеет свой element injector (DI scope);
  • проходит lifecycle hooks;
  • участвует в change detection;
  • может содержать дочерние компоненты, директивы, pipes.

Standalone (современный дефолт): компонент сам объявляет imports: [...] — не нужен NgModule. Bootstrap: bootstrapApplication(AppComponent, appConfig).

Композиция: smart (container) компоненты оркестрируют данные через facade/service; dumb (presentational) — получают input(), эмитят output(), не знают об HTTP.

Дроби UI на мелкие переиспользуемые компоненты, но не создавай «компонент на каждый div» — balance между cohesion и overhead. Facade pattern отделяет orchestration от presentation.
Проект: LayoutComponent (shell: sidebar + header + router-outlet) → feature components (MainComponent, TarotReadingComponent). Shared UI в shared/ui/ (CardComponent). Префикс селекторов ngKitty.

39. Как настраивается селектор, шаблон и стиль через @Component?

Декоратор @Component (API) — metadata, которую компилятор использует для генерации фабрики, шаблона и стилей:

@Component({
  selector: 'ngKitty-tarot-reading',       // element selector
  standalone: true,
  imports: [TuiIcon, TranslocoPipe, UpperCasePipe],
  templateUrl: './tarot-reading.component.html',
  styleUrl: './tarot-reading.component.scss',
  encapsulation: ViewEncapsulation.Emulated, // default
})

Ключевые поля:

  • selector — element (ngKitty-main), attribute ([ngKittyHighlight]) или class. Должен быть уникальным в приложении.
  • template / templateUrl — inline HTML или внешний файл. AOT компиляция на build.
  • styles / styleUrl(s) — scoped стили. styleUrl (singular) — Angular 17+.
  • encapsulation — Emulated (default, _ngcontent attributes), ShadowDom, None (глобальные стили).
  • changeDetection — OnPush (default в Angular 22) или Default.
  • host — bindings на host element ({ '(click)': 'onClick()', '[class.active]': 'isActive' }).
Inline template — для <10 строк. External files — для Prettier, подсветки, code review. styleUrl + SCSS includePaths в angular.json — для shared mixins.
Проект: SCSS с includePaths: ["src", "src/styles"] — импорт @use 'styles/...' без глубоких relative paths. Taiga UI themes из node_modules + src/styles.css.

40. Жизненный цикл компонента и основные хуки

Lifecycle hooks — методы интерфейсов, вызываемые Angular в строгом порядке (Lifecycle):

ХукКогдаТипичное использование
constructorСоздание instanceТолько inject() / DI, без тяжёлой логики
ngOnChangesПри изменении @Input (до ngOnInit и далее)Реакция на новые props; не срабатывает для signal inputs
ngOnInitПосле первого set inputsОдноразовая инициализация, загрузка данных
ngDoCheckКаждый CD cycleКастомный dirty checking (редко)
ngAfterContentInitПосле первого ng-content projectionРабота с projected content
ngAfterContentCheckedПосле каждой проверки projected content—
ngAfterViewInitПосле инициализации child viewsDOM доступен; viewChild populated
ngAfterViewCheckedПосле каждой проверки child views—
ngOnDestroyПеред уничтожениемCleanup: unsubscribe, clearInterval

Современная альтернатива хукам:

  • effect() — side effects при изменении signals (с onCleanup).
  • afterNextRender() / afterRender() — DOM operations после render (SSR-safe).
  • takeUntilDestroyed() — вместо ngOnDestroy + destroy$ для Observable.
Не ставь бизнес-логику в ngAfterViewChecked — вызывается очень часто. Signal input() + effect / computed заменяют ngOnChanges для большинства reactive cases.
Проект: TarotReadingComponent — effect() в constructor: при новом reading закрывает все <details> карт через viewChildren('tarotCard'). Cleanup подписок — takeUntilDestroyed в facades, не ngOnDestroy.

41. Двустороннее vs одностороннее связывание данных

Angular data binding (Template binding):

СинтаксисНаправлениеПример
{{ expr }}Component → DOM (interpolation){{ facade.result()?.verdict }}
[property]="expr"Component → DOM (property binding)[reading]="facade.result()"
(event)="handler"DOM → Component (event binding)(click)="facade.loadTarot()"

[prop]="x" (propChange)="x=$event"Two-way contractОснова [(ngModel)]

Односторонний flow — предсказуемее: данные текут сверху вниз (inputs/signals), события снизу вверх (outputs). Легче отлаживать и тестировать.

Two-way binding:

  • [(ngModel)] — template-driven forms, нужен FormsModule.
  • Reactive Forms — через formControlName; модель и view синхронизированы через FormControl.value, не [(ngModel)].
  • Custom components: value = input(); valueChange = output() → [(value)]="x".
Two-way удобен для простых полей. В сложных формах — Reactive Forms: явные valid/dirty/touched, cross-field validators, typed FormGroup. Не смешивай ngModel и formControlName на одном элементе.
Проект: login/register — Reactive Forms через facade (formControlName). Main page — односторонний flow: facade signals → [tarotReading]="facade.result()" в TarotReadingComponent.

42. Отдельные (standalone) компоненты

Standalone component — standalone: true (implicit default в Angular 19+ CLI). Не требует NgModule; зависимости явные:

@Component({
  standalone: true,
  imports: [RouterLink, ReactiveFormsModule, TarotReadingComponent],
  // ...
})

Преимущества (Importing):

  • Tree-shaking — неиспользуемые imports не в bundle.
  • Lazy loading через loadComponent: () => import('...').then(m => m.X) — отдельный chunk без NgModule wrapper.
  • Route-scoped providers заменяют feature modules.
  • Явные зависимости в файле — проще навигация и code review.

Bootstrapping:

// main.ts
bootstrapApplication(AppComponent, appConfig);

// app.config.ts — глобальные providers
export const appConfig: ApplicationConfig = {
  providers: [provideRouter(routes), provideHttpClient(), ...],
};
NgModules ещё работают (legacy), но новый код — standalone only. Не создавай SharedModule-баррели — они ломают tree-shaking. Импортируй только то, что нужно конкретному компоненту.
Проект: ноль NgModules в src/app/. Все фичи — standalone. Route providers в app.routes.ts вместо FeatureModule.forRoot().

43. Что такое ViewChild и ViewChildren?

Запросы к элементам собственного шаблона (view children), не projected content (Query API).

Современный signal-based API (Angular 17+):

// Один элемент
readonly header = viewChild<ElementRef>('headerRef');
readonly child = viewChild(TarotCardComponent);

// Несколько
readonly cards = viewChildren<ElementRef<HTMLDetailsElement>>('tarotCard');

Доступны после render — в ngAfterViewInit, effect(), afterNextRender(). Signal queries обновляются при изменении DOM.

Legacy decorators: @ViewChild('ref') el!: ElementRef — всё ещё работают, но signal queries предпочтительнее.

Content queries: contentChild() / contentChildren() — для projected nodes (ng-content).

Когда нужны: focus management, scroll, интеграция с non-Angular widgets, imperative DOM (редко). Prefer data binding.

Прямой DOM access через nativeElement — escape hatch; ломает SSR abstraction. Renderer2 — platform-safe, но binding предпочтительнее. { read: Token } — получить directive/service вместо ElementRef.
Проект: TarotReadingComponent — viewChildren('tarotCard') + effect: при новом reading сбрасывает open = false на всех <details> картах.

44. Change Detection: Default vs OnPush

Change Detection (CD) — механизм синхронизации model → view (Change detection).

Default (исторически): при любом async event в Zone.js Angular проверяет всё дерево (или с оптимизациями).

OnPush: компонент проверяется только когда:

  • изменился reference @Input;
  • событие произошло в самом компоненте или его детях;
  • async pipe получил новое значение;
  • прочитан signal в template (Angular 17+);
  • вызван markForCheck() / detectChanges() вручную.

Angular 22: OnPush — default для новых компонентов. Signals интегрированы: чтение signal() в template регистрирует dependency → CD при .set()/.update().

Zone.js vs Zoneless:

  • С Zone (provideZoneChangeDetection) — CD триггерится zone hooks.
  • Zoneless (provideExperimentalZonelessChangeDetection) — CD только через signals, events, explicit marks. Будущее Angular.
// app.config.ts — проект на Zone с coalescing
provideZoneChangeDetection({ eventCoalescing: true })
OnPush + immutable patterns = performance. Мутация объектов in-place без смены reference — OnPush не увидит (с signals эта проблема уходит). ChangeDetectorRef.detach() — ручное отключение CD (virtual scroll). Не вызывай detectChanges() без необходимости — bypass оптимизаций.
Проект: UI на signals (facade.result(), facade.isLoading() в templates). Explicit OnPush не указан — default A22. eventCoalescing: true — меньше CD runs при burst events.

45. Динамические компоненты

Динамический компонент — тип и/или момент создания определяется в runtime, а не в static template (Programmatic rendering).

1. ViewContainerRef.createComponent() — императивный API:

const ref = viewContainerRef.createComponent(DynamicComponent, {
  bindings: [
    inputBinding('data', () => item),
    outputBinding('selected', (e) => handle(e)),
  ],
});
// Обновление
ref.setInput('data', newItem);
// Уничтожение
ref.destroy();

2. NgComponentOutlet — декларативный (см. вопрос 46).

3. Overlay / Dialog — компонент вне DOM-иерархии (Taiga TuiDialogService, CDK Overlay). Portal pattern.

4. *ngTemplateOutlet — переключение шаблонов без полноценного component (легче, если нет своей логики).

Lazy loading dynamic: import('./widget').then(m => createComponent(m.Widget)) — code splitting.

Dynamic components обходят AOT template checking — ошибки bindings только в runtime. Tree-shaking слабее. Prefer static imports + @if switching когда набор типов конечен и известен на compile time.
Проект: ModalService — Taiga TuiDialogService.open(TUI_CONFIRM) для confirm при dirty form guard. Profile — *ngTemplateOutlet для переключения секций без dynamic component overhead.

46. ngComponentOutlet — когда использовать?

NgComponentOutlet (API reference) — директива для рендера standalone component по ссылке на класс:

<ng-container *ngComponentOutlet="
  activeTabComponent;
  inputs: { userId: id(), mode: 'edit' };
  outputs: { saved: onSaved($event) }
" />

Когда использовать:

  • Tab panel / wizard steps — конечный набор компонентов.
  • Widget registry / plugin system.
  • CMS-driven blocks (тип из API → component map).

vs createComponent: NgComponentOutlet — template-driven, проще, автоматический lifecycle. createComponent — полный контроль (insertion index, projectable nodes, manual destroy timing).

Inputs/Outputs (17.3+): inputs и outputs bindings без ручного setInput/subscribe.

Все dynamic types должны быть standalone. Для content projection в dynamic child — используй createComponent с projectableNodes.

47. Deferrable views (@defer)

@defer (Defer guide) — встроенный lazy loading на уровне шаблона. Код deferred блока — отдельный chunk, грузится по триггеру.

@defer (on viewport; prefetch on idle) {
  <ngKitty-heavy-chart [data]="chartData()" />
} @placeholder (minimum 100ms) {
  <div class="skeleton-chart" />
} @loading (minimum 200ms) {
  <ngKitty-spinner />
} @error {
  <p>Не удалось загрузить график</p>
}

Триггеры:

  • on idle — requestIdleCallback.
  • on viewport — Intersection Observer (видимость).
  • on interaction / on hover — user gesture.
  • on immediate — сразу после initial render.
  • on timer(500ms) — задержка.
  • when condition() — signal-based условие.
  • prefetch on idle — загрузить chunk заранее, показать по основному триггеру.

@defer vs loadComponent:

@deferloadComponent (route)
Гранулярность внутри страницыГранулярность на уровне route
Placeholder/loading/error blocksНет встроенных блоков
Триггеры viewport/interactionТриггер = навигация
@defer идеален для тяжёлых виджетов below the fold (charts, maps, rich editors). Не defer-и критичный above-the-fold UI — ухудшит LCP. Комбинируй: lazy route + @defer для тяжёлого child.
Проект: @defer не используется — вместо него route-level loadComponent (profile, login, sanctum…) + кастомная UserStateStrategy preloading (guest routes для гостей, auth routes для залогиненных). Та же цель — меньший initial bundle.

51. Решения и сложности

  • Facade pattern — UI никогда не вызывает HTTP напрямую; тестируемый orchestration layer.
  • Route-scoped providers — tarot services не засоряют root injector.
  • Signals вместо Subjects — проще state; RxJS только для async streams.
  • Shared domain в core/ — CandlesService, ConfessService переиспользуются между фичами.
  • Пример сложности: chunk translation с rate limits → mergeMap(3) + per-chunk catchError fallback.
  • Пример сложности: cross-field password validator, сохраняющий несвязанные ошибки на sibling control.
